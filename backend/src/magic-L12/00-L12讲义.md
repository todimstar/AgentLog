# L12 讲义 · CLI 与浏览器设备配对（OAuth 设备授权流）

> 深讲义标准：**每个概念第一次出现就地讲透**。本课是 M2「智能体接入层」的开幕——
> 从「人用浏览器」跨到「AI 工具用 CLI」接入平台。

---

## 0. 本课要解决的真实问题

前 11 课，用户永远是**坐在浏览器前的人**：浏览器有 Cookie、能存 Session、能弹登录页。
但从本课起，第二类客户端登场——**跑在你电脑上的 CLI**（未来给 Codex / Claude Code 这类 AI 工具当「手」）。

CLI 的困境：**它没有浏览器**。你不能让一个命令行程序弹出登录页、更不能让它替你输邮箱密码。
那它怎么证明「我代表某个主人」？

答案是业界标准 **OAuth 2.0 设备授权流（Device Authorization Grant, RFC 8628）**——
你在**智能电视上登 Netflix**、在终端跑 `gh auth login` 用的就是它：
**让无浏览器的设备，借用你另一块屏幕上已登录的浏览器完成授权。**

验收目标（课程卡）：`CLI 配对成功` + `过期处理`。

## 1. 三方握手全景（先看整体，再拆细节）

```
  CLI (无浏览器)              后端                      浏览器 (你已登录)
    │ ① POST device-pairings   │                              │
    │   {installationCode,      │  建 installation + pairing    │
    │    deviceName}            │  生成 deviceCode + userCode    │
    │ ◄─────────────────────────┤  {deviceCode,userCode,        │
    │                           │   verificationUri,...}        │
    │                           │                              │
    │ ② 控制台打印：             │                              │
    │   "浏览器打开 verificationUri，输入配对码 userCode"          │
    │                           │            你输入 userCode ──►│
    │                           │ ◄──── ③ POST /web/.../confirm ─┤ (Session+CSRF)
    │                           │  校验 userCode → CONFIRMED     │
    │                           │  绑定 installation 到你         │
    │ ④ 轮询 POST .../token      │                              │
    │   {deviceCode} ──────────►│  未确认→PENDING                │
    │   (每 pollInterval 秒)     │  已确认→签发 owner 令牌         │
    │ ◄─────────────────────────┤  {ownerAccessToken,refresh}   │
    │   存 credentials.json      │                              │
```

### 🔍 就地讲透：为什么要 deviceCode 和 userCode **两个**码？

这是设备流最精妙、最容易被误解的一点。两个码走**两条安全属性完全不同的通道**：

| | deviceCode | userCode |
|---|---|---|
| 谁用 | CLI（机器） | 人（在浏览器输） |
| 长什么样 | 长随机串 `device_xk3n...`（43 字符） | 短码 `ABCD-EFGH`（8 位） |
| 传输通道 | HTTPS 机器轮询（可高熵） | **人眼看、人手打**（必须短） |
| 作用 | 长期凭证的兑换券 | 一次性确认凭据 |

**为什么不能只用一个码？**
- 如果只用短码：短码熵低（8 位约 40 bit），当长期凭证会被暴力猜——不安全。
- 如果只用长码：43 字符的串**人没法在浏览器里手输**——不可用。

所以设备流把「**能安全轮询的通道**」和「**人能手输的通道**」拆开：
长码（deviceCode）机器私藏轮询，短码（userCode）只用于「人确认这一下」，10 分钟即弃。
**这就是 RFC 8628 的核心洞察。**

## 2. 令牌怎么存：Opaque Token + HMAC 摘要

配对成功后，后端要签发 `OwnerAccessToken`。这个令牌怎么存进库？本课选定 **Opaque Token（不透明令牌）+ 令牌表** 模型。

### 🔍 就地讲透：什么是 Opaque Token？为什么不存明文？

- **Opaque（不透明）令牌** = 一串**没有内部结构的随机字符串**。服务端要验证它，必须**查表**（与之相对的是 JWT，自带签名可自验证、无需查表）。
- 本项目认证是**双轨**的：浏览器走 Session（L05 定），**CLI/Agent 走 opaque token**。选 opaque 而非 JWT 的理由：opaque 令牌**可即时吊销**（删表行即失效），符合「主人随时能踢掉某台设备」的需求。

**关键安全动作：库里只存令牌的摘要，不存明文。**

看 [TokenService.java](../../../shared/security/TokenService.java)：
```java
public byte[] digest(String rawToken) {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(props.getPepper().getBytes(UTF_8), "HmacSHA256"));
    return mac.doFinal(rawToken.getBytes(UTF_8));   // → 32 字节，存 BINARY(32)
}
```

- **为什么不存明文令牌**：万一数据库被脱库，攻击者拿到的只是**摘要**。没有服务端的 `pepper`（密钥），他**算不出明文令牌**，无法冒用。这与密码存 bcrypt 同理——**可验证、不可逆推**。
- **为什么用 HMAC 而不是纯 SHA-256**：HMAC 带一个密钥（pepper）。纯哈希对短输入可能被「彩虹表/预计算」撞库；HMAC 没有 pepper 就无从预计算。`pepper` 走环境变量 `AGENTLOG_TOKEN_PEPPER`，**不进 git**（见 [application.yml](../../resources/application.yml) `agentlog.token.pepper`）。

同样地，`deviceCode` 也只存 `device_code_digest BINARY(32)`（见迁移）。明文 deviceCode / 令牌**只在 HTTP 响应里回客户端一次**，之后服务端再也拿不到明文。

## 3. 三张表与状态机

看 [V010__create_device_pairing.sql](../../resources/db/migration/V010__create_device_pairing.sql)。

> 🔍 就地讲透·迁移编号：课程卡写 V007，但主线 V006–V009 已被占用，**实际用 V010**
> （DRIFT-REGISTER D-02 备案，照抄蓝图编号会 Flyway 撞车）。

| 表 | 作用 | 状态列 |
|---|---|---|
| `client_installation` | 一台设备（一次 CLI 安装）一条 | PENDING → ACTIVE（绑定主人后）|
| `device_pairing_request` | 一次 `auth login` 一条 | PENDING → CONFIRMED → CONSUMED；超时 EXPIRED |
| `owner_access_session` | 配对成功签发的令牌会话（一行存 access+refresh 两个摘要）| ACTIVE / REVOKED |

配对请求的状态机（见 [PairingStatus.java](../../java/com/agentlog/identity/pairing/domain/PairingStatus.java)）：
```
PENDING ──(浏览器确认)──► CONFIRMED ──(CLI 首次换 token)──► CONSUMED
   │                                                          ▲
   └──────────(超过 10min)──────► EXPIRED         再来换 = 拒（防重放）
```

### 🔍 就地讲透：为什么要 CONSUMED 这个「一次性」状态？

`deviceCode` 换到令牌后，pairing 立即置 **CONSUMED**。若不置——攻击者若截获了 deviceCode，
就能反复调 `.../token` 换出**多个**有效令牌。置 CONSUMED 后，同一个 deviceCode 第二次来换直接 409 拒绝。
**一次性兑换券**，这是防重放的关键（对应集成测试 `deviceCodeOneShot`）。

## 4. 三个端点：谁匿名、谁要登录

### 4.1 两个 CLI 端点——**匿名**

看 [CliDevicePairingController.java](../../java/com/agentlog/identity/pairing/api/CliDevicePairingController.java)：
- `POST /api/v1/cli/device-pairings` — 发起配对
- `POST /api/v1/cli/device-pairings/token` — 轮询换令牌

### 🔍 就地讲透：匿名端点安全吗？

安全。CLI 此刻**还没有任何令牌**（配对的目的就是拿第一个令牌），所以这两个端点必须匿名。
它们靠 **deviceCode 自身**保护：长随机（高熵猜不中）+ 10 分钟过期 + 库里只存摘要 + 一次性。
「配对入口匿名」是设备流的固有设计，不是漏洞。

安全配置见 [ApiSecurityConfiguration.java](../../java/com/agentlog/shared/security/ApiSecurityConfiguration.java)：
这两个端点加进 `permitAll()`（免登录）**和** `csrf().ignoringRequestMatchers()`（免 CSRF——CLI 没有 Cookie，拿不到 CSRF token）。

### 4.2 浏览器确认端点——**要登录 + CSRF**

看 [WebDevicePairingController.java](../../java/com/agentlog/identity/pairing/api/WebDevicePairingController.java)：
- `POST /api/v1/web/device-pairings/confirm` — 主人输入 userCode 批准

关键一行：
```java
long currentUserId = CurrentUser.requireId();   // 从 Session 派生，绝不由客户端传入
pairingService.confirmPairing(currentUserId, request.userCode());
```

### 🔍 就地讲透：为什么 currentUserId 必须从 Session 取、不能让前端传？

如果让前端传 `ownerUserId`，攻击者就能把别人 CLI 的配对确认到**自己**名下（或反之）。
铁律（module-contracts.md）：**所有 owner 域操作的 currentUserId 一律从认证 principal 派生**。
浏览器已登录 → Session 里有 userId → 后端自己取。这是**防越权**的根基。

> 🔍 就地讲透·D-08 漂移：OpenAPI 契约原本只列了两个 CLI 端点，**没有浏览器确认端点**。
> 但设备流缺了「人在浏览器批准」这一步就跑不通。所以新增此端点属于**改动冻结的契约面**，
> 按铁律登记为漂移 D-08，回写活契约 + Pack 副本。（D-xx 命名的深意见结课说明。）

### 4.3 这里已经能看到「双轨认证」的雏形

同样是配对功能，**CLI 端点匿名、浏览器端点要 Session+CSRF**——因为它们是两类客户端：
```
浏览器 → Session + CSRF（Cookie 认证）
CLI    → 匿名配对 → 拿 opaque 令牌（L13 起用 Bearer 认证）
```
本课签发的 OwnerAccessToken **暂时还没有过滤器消费它**——「铸令牌」在 L12，
「用令牌的 Bearer 过滤器 + 独立 CLI 认证链（Chain 2）」是 **L13** 的教学重点。每课单一职责。

## 5. 应用服务：三个方法就地讲透

看 [DevicePairingService.java](../../java/com/agentlog/identity/pairing/application/DevicePairingService.java)。

**createPairing**：同 installationCode 复用 installation（一台设备多次配对不重复建）→ 生成 deviceCode+userCode → 存摘要 → 返回。verificationUri 来自配置（`agentlog.pairing.verification-uri`，默认指向前端 5173 的 hash 路由）。

**confirmPairing**：按 userCode 查 → 检查过期/状态 → 置 CONFIRMED + 记 confirmedByUserId + confirmedAt → 绑定 installation 到主人并转 ACTIVE。

**exchangePairing**：按 deviceCode 摘要查 → 过期返回 `EXPIRED` → PENDING 返回 `PENDING`（让 CLI 继续轮询）→ CONFIRMED 则签发 access+refresh、落 owner_access_session、置 CONSUMED、返回 `APPROVED`。

### 🔍 就地讲透：为什么注入 `Clock`，不用 `Instant.now()`？

```java
Instant now = Instant.now(clock);   // 注入的 Clock，不是 Instant.now()
```
过期逻辑依赖「现在几点」。若硬编码 `Instant.now()`，测试就没法验证过期——总是当前时间。
注入 `Clock`（生产是 `Clock.systemUTC()`）让时间**可控可测**。这是可测试性设计的通用手法。
（本课测试用 SQL 直接把 `expires_at` 改到过去来模拟超时，同样有效。）

### 🔍 就地讲透：为什么 PENDING/EXPIRED 返回 200，不是抛异常？

`exchangePairing` 是**轮询端点**。PENDING（还没批准）和 EXPIRED（超时）都是**正常的轮询结果**，
不是错误——CLI 需要根据 `status` 字段决定「继续轮询 / 放弃」。所以用 200 + 工厂方法
`ExchangePairingResponse.pending()/expired()/approved()` 表达。
只有**真正的错误**（配对不存在、已消费重放）才抛 `ApiException` → ProblemDetail（404/409）。
**「业务状态」和「错误」要分清**：轮询状态不是异常。

## 6. 模块归属：为什么放 `identity/pairing/**` 子命名空间

配对本质是「设备+令牌生命周期」，域上独立于「用户身份/资料」。但三处设计口径
（物理模块树无 pairing、模块契约归 IdentityFacade、赶工版先例）都指向 **identity 模块**。
折中：放在 **`identity/pairing/**` 子命名空间**——既不破坏 Modulith 边界（仍是 identity 内部包），
又按特性聚合、预留「未来质量够了抽独立 `access` 授权服务器模块」的接缝。
（ModularityTest 已验证边界没破。）
