📝 课后测验 · CLI 设备配对（OAuth 设备授权流）

    
由浅入深 5 题。先自己说出答案再点开对照——能讲顺 = 真懂了，卡壳的题回到对应线重听。

    
①基础设备流为什么要 deviceCode 和 userCode 两个码？各自给谁用、长什么样？
      
deviceCode：长随机串，给机器（CLI）私藏、轮询换令牌用；userCode：短码（ABCD-EFGH），给人在浏览器手输确认用。拆两个是因为「能安全轮询的通道」和「人能手输的通道」安全属性不同——短码熵低不能当长期凭证，长码人手打不动。这是 RFC 8628 的核心洞察 → 对应视频「线0·三方握手」。

    
②链路从 auth login 到 CLI 拿到令牌，三方握手是哪三步？「浏览器确认」那步为什么必须登录态？
      
① CLI POST /cli/device-pairings（匿名）→ 拿 deviceCode+userCode+verificationUri；② 你在浏览器（已登录）POST /web/device-pairings/confirm 输 userCode 批准；③ CLI 轮询 POST /cli/device-pairings/token 换 owner 令牌。确认必须登录态：currentUserId = CurrentUser.requireId()（WebDevicePairingController L34）从 Session 派生，绝不让前端传——否则能把别人的配对确认到自己名下（防越权）。

    
③原理令牌为什么库里只存 HMAC 摘要、不存明文？pepper 起什么作用？为什么用 HMAC 而不是纯 SHA-256？
      
明文令牌只在响应回客户端一次，库存 HMAC-SHA256(pepper, 明文) 的 BINARY(32) 摘要（TokenService L46）。不存明文：脱库时攻击者拿到的只是摘要，没 pepper（服务端密钥，走 env var 不进 git）算不出明文，无法冒用——同密码存 bcrypt，可验证不可逆推。用 HMAC 不用纯哈希：HMAC 带 pepper 这把密钥，挡住对短令牌的彩虹表/预计算撞库。这是 CLI/Agent 双轨认证的地基。

    
④设计deviceCode 换到令牌后为什么立刻置 CONSUMED？不这样会怎样？
      
exchangePairing 成功后把 pairing 置 CONSUMED（DevicePairingService L185），同一 deviceCode 第二次来换直接 409 PAIRING_ALREADY_HANDLED。不这样：谁截获了 deviceCode 就能反复换出多个有效令牌。一次性兑换券，用完即废——防重放的命门（对应集成测试 deviceCodeOneShot）。另一半安全是「过期」：超 10min 置 EXPIRED（L120/L154）。

    
⑤综合什么是「双轨认证」？本课签发的 owner 令牌为什么「还不能用」？L12 和 L13 怎么分工？
      
双轨认证=按客户端类型分链：浏览器走 Session+CSRF（Cookie 认证，/web/**）、CLI/Agent 走 opaque 令牌（Bearer，/cli/** /agent/**）——L05 就埋下的设计。本课签发的 OwnerAccessToken 还没有过滤器去消费它：L12「铸令牌」（配对握手+签发+落库），L13「用令牌」（Bearer 过滤器 Chain 2 + assume 机娘签 Chain 3 令牌 + refresh）。每课单一职责，所以本课两个 CLI 端点匿名、只往白名单加它俩。
