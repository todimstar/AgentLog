# L11 媒体预签名上传 · 讲义（对话版）

> **一句话**：让用户能传图片(头像/封面),但**文件一个字节都不经过后端**——前端拿一张"临时通行证"直传 MinIO。
> 这是从 L06-L10 的"纯文字内容"跨到"二进制文件"。档位 🟡 3h,media 模块开张,**我写你审**。
>
> ⚠️ 环境:MinIO 容器必须跑(`infra-minio-1`,9000,bucket `agentlog-private`)。复用 L03 建的 V002 `media_object` 表,**无新迁移**。

## 一、最核心的一张图:文件为什么不经过后端(面试必问)

```
❌ 传统做法(文件经后端中转):
   前端 ──[整个10MB图]──> 后端 ──[整个10MB图]──> 对象存储
        后端变成大文件管道:每传一张,10MB 占后端内存+带宽;
        并发上传时,应用服务器先被文件流打爆,轮不到业务逻辑。

✅ 预签名直传(本课做法):
   ① 前端 ──[我要传 test.png, 2MB]──> 后端:"给我张上传通行证"
   ② 后端 ──[预签名PUT URL, 5分钟有效]──> 前端        (后端只算了个签名,没碰文件)
   ③ 前端 ──[整个10MB图, 直接PUT到这个URL]──> MinIO   ← 后端全程不在链路里!
   ④ 前端 ──[我传完了, mediaId=xxx]──> 后端 finalize:HEAD问MinIO"真传了吗多大"→标ACTIVE
```

**一句话记住**:后端从"文件搬运工"退化成"发通行证的门卫 + 事后核对的记账员"。文件的重活全甩给对象存储扛。

**预签名 URL 是什么?** 后端用 access-key/secret-key,对"往 bucket/某key PUT、5分钟内有效"这件事算出一个带签名的 URL。MinIO 收到请求时验签名:签名对、没过期,就放行——**授权信息编码在 URL 里,和文件传输本身解耦**。

## 二、三个接口 + 一张表(接口纵切)

| # | 端点 | 谁能调 | 干什么 |
|---|---|---|---|
| 1 | `POST /owner/media/upload-slots` | 登录+CSRF | 建槽(PENDING) + 签发预签名 PUT URL |
| 2 | `POST /owner/media/{mediaId}/finalize` | 登录+CSRF | HEAD 确认 + PENDING→ACTIVE |
| 3 | `GET /public/media/{mediaId}` | 匿名 | 302 重定向到预签名 GET URL |

表复用 **V002 `media_object`**(L03 就建好了,一直空着,L11 才第一次写入)。关键列:
- `public_id`(med_xxx,对外暴露的随机 id,不暴露自增主键)
- `object_key`(MinIO 里的随机存储键,**不用原始文件名**——防猜测、防同名覆盖)
- `status`(PENDING→ACTIVE→ABANDONED/DELETED 状态机)

## 三、三步逐个读代码

### 第 1 步:建槽 —— `MediaService.createUploadSlot`

```java
// 1. 后端兜底校验(前端可能绕过契约直接调)
if (!ALLOWED_TYPES.contains(request.contentType())) throw MEDIA_TYPE_NOT_ALLOWED;  // 仅 jpeg/png/webp
if (request.declaredSizeBytes() > 5MB) throw MEDIA_TOO_LARGE;

// 2. 生成随机 id 和存储键(不用原始文件名)
String publicId = "med_" + 随机32位;
String objectKey = "uploads/" + publicId + ".png";

// 3. 先在库里建一条 PENDING 记录(占位待确认)
media.setStatus("PENDING");
media.setExpiresAt(now + 5分钟);   // 没 finalize 的,过期由清理 Worker(L17)回收
mediaObjectMapper.insert(media);

// 4. 签发预签名 PUT URL —— 核心一行
PresignedPutObjectRequest presigned = s3Presigner.presignPutObject(...);
return new UploadSlotResponse(publicId, presigned.url().toString(), "PUT", 过期时间);
```

**为什么建槽即 PENDING 而不是直接 ACTIVE?** 因为这一刻文件还没传呢!PENDING = "我给你留了个位置,通行证也发了,但你到底传没传、传的对不对,我还不知道"。

### 第 2 步:前端直传(后端不参与)
前端 `fetch(uploadUrl, {method:'PUT', body: 文件})` ——**不带 Cookie、不带 CSRF**,因为这是发给 MinIO 的,不是发给后端的。MinIO 只认 URL 里的签名。

### 第 3 步:finalize —— `MediaService.finalizeMedia`

```java
// 行级授权:只能 finalize 自己的槽
if (!media.getUploaderUserId().equals(currentUserId)) throw MEDIA_FORBIDDEN;
if ("ACTIVE".equals(media.getStatus())) return toView(media);   // 幂等:重复调不报错

// 【关键】HEAD 对象:不信前端说"传完了",亲自问 MinIO
try {
    head = s3Client.headObject(bucket, objectKey);   // 存在吗?多大?
} catch (NoSuchKeyException e) {
    throw MEDIA_NOT_UPLOADED;    // 槽建了但对象不在 = 前端根本没传/传失败
}
if (head.contentLength() > 5MB) throw MEDIA_TOO_LARGE;   // 防谎报 declaredSize 传超大文件

media.setStatus("ACTIVE");
media.setActualSizeBytes(head.contentLength());   // 用真实大小,不信 declared
media.setExpiresAt(null);   // ACTIVE 不再被清理
```

**finalize 是整课的"不信任客户端"精髓**:前端说传完了不算数,后端 `HEAD` 亲自向 MinIO 核实"对象真在、大小合理",确认了才 ACTIVE。防前端谎报、传一半、或建了槽根本不传。

### 读:302 重定向 —— `PublicMediaController.redirectMedia`

```java
String url = mediaService.createReadRedirectUrl(mediaId);  // 签发预签名 GET URL(15分钟)
return ResponseEntity.status(302).location(URI.create(url)).build();
```

**读为什么也用 302 而不是后端读出来吐给前端?** 同一个道理——后端不当下载管道。bucket 是私有的,前端不能直接摸;后端签个短时 GET 通行证,302 让浏览器**自己**去 MinIO 拿。前端 `<img src="/api/v1/public/media/med_xxx">`,浏览器自动跟随 302,用户无感。

## 四、MinIO 对接的坑:pathStyleAccessEnabled(true)

`S3Configurations` 里两个 Bean(`S3Client` 服务端操作 / `S3Presigner` 只签名),都有一行:

```java
.serviceConfiguration(S3Configuration.builder().pathStyleAccessEnabled(true).build())
```

**为什么必须设?** AWS S3 默认用 **virtual-host-style** 寻址:`http://{bucket}.{host}/{key}`(bucket 拼进域名)。MinIO 用 **path-style**:`http://{host}/{bucket}/{key}`。不设这行,SDK 会把 bucket 名拼成子域名,MinIO 解析不到 → 404 / UnknownHost。**这是对接 MinIO 必踩的第一个坑。**

## 五、一页纸面试速记

| 考点 | 一句话答案 |
|---|---|
| 为什么文件不经后端 | 后端当大文件管道会被打爆;预签名让前端直传对象存储,后端只发通行证 |
| 预签名 URL 原理 | 后端用密钥对"PUT某key、限时"算签名编进URL,存储验签放行,授权与传输解耦 |
| 为什么要 finalize | 不信前端"传完了",后端 HEAD 亲自向存储核实对象存在+大小,才转 ACTIVE |
| PENDING→ACTIVE 状态机 | 建槽即 PENDING(占位),HEAD 确认后 ACTIVE,超时未传由 Worker 清理(L17) |
| 读为什么 302 | 后端不当下载管道,签短时 GET 通行证让浏览器直接找存储拿 |
| pathStyle 为什么 true | MinIO 用 path-style 寻址,不设 SDK 会拼 bucket 进域名导致 404 |
| object_key 为什么随机 | 不用原始文件名,防猜测、防同名覆盖 |
| 直传为什么不带 CSRF/Cookie | 那个 PUT 是发给 MinIO 的,不是发给后端的,MinIO 只认 URL 签名 |
