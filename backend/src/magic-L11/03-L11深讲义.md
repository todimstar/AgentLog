# L11 媒体预签名上传 · 深讲义(背景注解版)

> **写给谁**:L11 是「我写你审」,你对对象存储、AWS SDK、预签名这些**大概率是第一次碰**。所以铁律不变:**每个陌生概念第一次出现就地讲透**——是什么、为什么需要、本课怎么用。目标是你读完能在面试里被追问也不虚。
>
> **一句话**:让用户能传图片(头像/封面),但**文件一个字节都不经过后端**——前端拿一张"限时通行证"直接把图传给对象存储 MinIO。

## 〇、先补三个背景,不然第一段就看不懂

L11 一上来就是"对象存储""预签名",这些 L01-L10 从没出现过。先花三分钟把地基垫平。

### 背景1:什么是"对象存储"?MinIO 是什么?

你以前存数据用 **MySQL**(存结构化的行)。但图片是**二进制大文件**,塞进数据库很蠢(撑爆、慢)。业界用**对象存储**存文件:

- **对象存储** = 一个"超大网盘 API"。你给它一个 **key**(文件名,如 `uploads/med_abc.png`)和文件字节,它存起来;你拿 key 找它要,它吐给你。代表产品:AWS **S3**。
- **MinIO** = 一个**开源的、能自己部署的 S3**。API 跟 S3 一模一样(所以能用 AWS 的 SDK 连它)。我们本地用 Docker 跑一个 MinIO 当对象存储,生产可无缝换成真 S3。
- **bucket(桶)** = 对象存储里的"顶级文件夹",我们的桶叫 `agentlog-private`(私有,不能匿名访问)。
- **object key(对象键)** = 桶里文件的完整路径名,如 `uploads/med_abc.png`。

> 记住这个类比:**bucket = 网盘根目录,object key = 文件路径,对象存储 = 网盘的 HTTP API**。

### 背景2:什么是"预签名 URL"?(本课最核心的概念)

问题:桶是**私有**的,前端没有密钥,怎么让它往里传文件?

笨办法:前端把文件发给后端,后端用密钥传进 MinIO。但这样**文件要过后端一遍**(下一节讲为什么这很糟)。

聪明办法——**预签名 URL(presigned URL)**:
- 后端手里有 MinIO 的密钥(access-key + secret-key)。
- 后端用密钥,对"**允许往 `agentlog-private/uploads/med_abc.png` 做一次 PUT,5 分钟内有效**"这句话,算出一个**带签名的长 URL**。
- 这个 URL 交给前端。前端拿它直接 PUT 文件。MinIO 收到后,**验证 URL 里的签名**:签名对、没过期,就放行——**它不需要前端有密钥,签名本身就是授权凭证**。

> **背景注解 · 签名怎么算的(面试可能问)**:AWS SigV4 算法。后端把"HTTP 方法 + 桶 + key + 过期时间 + 一堆头"拼成一个规范字符串,用 secret-key 做 **HMAC-SHA256** 哈希,得出签名,附在 URL 的 `X-Amz-Signature=` 参数里。MinIO 收到后用同样的 secret-key 重算一遍,一致才放行。**secret-key 从不出现在 URL 里,只用来算签名**,所以 URL 泄露了顶多在过期前被人用一次,密钥本身安全。
>
> 一个真实的预签名 URL 长这样:
> ```
> http://localhost:9000/agentlog-private/uploads/med_abc.png
>   ?X-Amz-Algorithm=AWS4-HMAC-SHA256
>   &X-Amz-Credential=agentlog/...
>   &X-Amz-Date=20260704T...
>   &X-Amz-Expires=300              ← 300秒=5分钟
>   &X-Amz-Signature=3f8a...        ← 签名在这
> ```

### 背景3:两个 HTTP 小知识(后面要用)

- **PUT vs POST**:都是 HTTP 方法。上传文件到对象存储用 **PUT**(语义:"把这个文件放到这个 key")。
- **HEAD 请求**:跟 GET 一样,但**只要响应头、不要响应体**。用来问"这个对象存在吗?多大?"而**不下载整个文件**。finalize 会用到它。
- **302 重定向**:后端回一个状态码 302 + 一个 `Location: 某URL` 头,浏览器会**自动再去请求那个 URL**。用来"指路"而不亲自搬运。

## 一、地图:本课有「五条线」

```
线1【建槽签发】createUploadSlot:  校验 → 建 PENDING 记录 → 签发预签名 PUT URL
线2【前端直传】(前端):           拿 URL 直接 PUT 文件给 MinIO —— 后端不在链路
线3【finalize确认】finalizeMedia: HEAD 核实对象真在 → PENDING 转 ACTIVE
线4【读重定向】redirectMedia:     签发预签名 GET URL → 302 让浏览器直接找 MinIO 取
线0【配置横切】S3Configurations:  两个 Bean + pathStyle 坑 + 状态机 + 复用 V002 表
```

**一句话串起来**:后端从"文件搬运工"退化成"发通行证的门卫(线1)+ 事后核对的记账员(线3)+ 指路的向导(线4)",文件的重活全甩给 MinIO 扛(线2)。

## 二、线0【配置】:先打地基,顺带避开最大的坑

### 两个 Bean:S3Client 和 S3Presigner,分工不同

看 [S3Configurations.java](backend/src/main/java/com/agentlog/media/infrastructure/S3Configurations.java),它造了两个"零件"(Spring 的 `@Bean`):

- **`S3Client`** = **真去操作对象**的客户端。finalize 时用它发 HEAD 请求问 MinIO"对象在不在"。它会真的发网络请求。
- **`S3Presigner`** = **只算签名、不发请求**的签名器。用它生成预签名 PUT/GET URL。它**只做数学(算签名)**,一个字节都不传。

> **面试官追问**:"为什么不用一个客户端?" 答:"职责不同。Presigner 只负责'签发通行证'(纯计算,给前端用),Client 负责'服务端亲自操作'(HEAD 核实、读元数据)。分开更清晰,也符合最小权限——签发和操作是两件事。"

### 最大的坑:`pathStyleAccessEnabled(true)`

两个 Bean 都有这一行:
```java
.serviceConfiguration(S3Configuration.builder().pathStyleAccessEnabled(true).build())
```

**为什么必须设?**(这是对接 MinIO 100% 会踩的坑,面试讲这个很加分)

对象存储有两种"寻址风格"——即桶名放在 URL 的哪里:

```
virtual-host-style(AWS 默认):  http://{bucket}.{host}/{key}
                                http://agentlog-private.localhost:9000/uploads/x.png
                                             ↑ 桶名拼成了子域名

path-style(MinIO 用):          http://{host}/{bucket}/{key}
                                http://localhost:9000/agentlog-private/uploads/x.png
                                                      ↑ 桶名在路径里
```

AWS SDK **默认用 virtual-host-style**,会把桶名拼成子域名 `agentlog-private.localhost`。但 `localhost` 没有这种子域名解析,MinIO 也不认——结果就是 **404 或 UnknownHost**。设 `pathStyleAccessEnabled(true)` 强制用 path-style,桶名回到路径里,MinIO 才认。

### 表和状态机(复用 V002,无新迁移)

L11 **不建新表**,复用 L03 就建好的 `media_object` 表(一直空着,L11 才第一次写)。关键列:

```
media_object(节选)
  public_id      med_xxx,对外暴露的随机id(不暴露自增主键)
  object_key     uploads/med_xxx.png,MinIO 里的存储键(随机,不用原始文件名)
  status         PENDING → ACTIVE → (ABANDONED/DELETED)   ← 状态机
  declared_size_bytes  前端声明的大小(不可信)
  actual_size_bytes    HEAD 拿到的真实大小(可信)
  expires_at     PENDING 的过期时间,给清理 Worker(L17)用
```

> **面试官追问**:"object_key 为什么用随机 id 不用原始文件名?" 答:"两个原因——① 防猜测,别人猜不到你的图 URL;② 防覆盖,两个人都传 `avatar.png` 不会打架。原始文件名只存 `original_filename` 字段做展示,不做存储键。"

## 三、线1【建槽签发】：`createUploadSlot`

看 [MediaService.java](backend/src/main/java/com/agentlog/media/application/MediaService.java) 的 `createUploadSlot`,三个环节:

### 环节1:后端兜底校验
```java
if (!ALLOWED_TYPES.contains(req.contentType())) throw MEDIA_TYPE_NOT_ALLOWED;  // 仅 jpeg/png/webp
if (req.declaredSizeBytes() > 5MB)               throw MEDIA_TOO_LARGE;
```
**为什么后端还要校验?** 契约(OpenAPI)里写了限制,前端也会拦,但**前端可能被绕过**(用 Postman、脚本直接调接口)。**后端才是底线**。这是"不信任客户端"的第一处。

### 环节2:建一条 PENDING 记录
```java
media.setStatus("PENDING");
media.setExpiresAt(now + 5分钟);
mediaObjectMapper.insert(media);
```
**为什么建槽即 PENDING,不直接 ACTIVE?** 因为**这一刻文件还没传呢**。PENDING 的语义是:"我给你留了位置、通行证也发了,但你到底传没传、传得对不对,我还不知道。" 带个 5 分钟过期时间,没去 finalize 的,将来由清理 Worker(L17)回收成 ABANDONED。

> **面试官追问**:"如果用户建了槽但一直不传,会怎样?" 答:"留一条 PENDING 记录 + 5 分钟过期标记。后台定时 Worker 扫 `status=PENDING AND expires_at<now` 的,回收成 ABANDONED,顺便删掉 MinIO 里可能的半成品。这是'占位待确认'状态机的兜底。"

### 环节3:签发预签名 PUT URL(核心一行)
```java
PresignedPutObjectRequest presigned = s3Presigner.presignPutObject(...);
return new UploadSlotResponse(publicId, presigned.url().toString(), "PUT", 过期时间);
```
`s3Presigner` 用密钥对"往这个 key 做 PUT、5 分钟有效"算出签名,拼成预签名 URL,连同 `mediaId`(=publicId)一起返回给前端。**后端到此没碰一个文件字节**。

## 四、线2【前端直传】：文件为什么不经后端(本课灵魂)

这条线在**前端**,后端完全不参与。前端就一句:
```js
fetch(uploadUrl, { method: 'PUT', body: 文件 })   // 不带 Cookie、不带 CSRF
```

### 为什么"文件不经后端"这么重要?

```
❌ 文件经后端中转:
   前端 ─[10MB图]─> 后端 ─[10MB图]─> MinIO
   后端每传一张图要吃 10MB 内存 + 双倍带宽(进+出);
   100 个人同时传,后端先被文件流打爆,业务逻辑都轮不上。

✅ 预签名直传:
   前端 ─[10MB图, 直接PUT]─> MinIO
   后端只在建槽时算了个签名(几微秒),文件洪流直接砸向对象存储,
   对象存储天生为此设计,能扛。后端轻装上阵,可水平扩展。
```

### 为什么直传不带 Cookie / CSRF?

> **背景注解 · CSRF / Cookie 是什么**:你登录后,浏览器存了个会话 Cookie,之后每次请求**自动带上**证明"我是登录的 Alice"。CSRF 令牌是防"别的网站冒用你 Cookie"的额外校验。这俩都是**后端认你身份**用的。

那个 PUT 请求是**发给 MinIO 的,不是发给后端的**。MinIO 不认你的登录会话,它**只认 URL 里的签名**。所以带 Cookie/CSRF 没意义(还可能干扰)。

> **验收佐证(面试可讲的实证)**:我在集成测试里,特意用一个**全新的、不带任何 Cookie 的独立 HttpClient** 去 PUT 那个预签名 URL,照样传成功(返回 200)。这直接证明了"授权全在签名里,与登录会话无关"。curl 手工验收也复现了这一点。

## 五、线3【finalize确认】：不信客户端,HEAD 亲自核实

前端传完了,告诉后端 `mediaId`。后端信吗?**不信。** 看 `finalizeMedia`:

```java
if (!media.getUploaderUserId().equals(currentUserId)) throw MEDIA_FORBIDDEN;  // 只能 finalize 自己的
if ("ACTIVE".equals(media.getStatus())) return toView(media);                 // 幂等:重复调直接返回

try {
    head = s3Client.headObject(bucket, objectKey);   // 【核心】HEAD 亲自问 MinIO
} catch (NoSuchKeyException e) {
    throw MEDIA_NOT_UPLOADED;                         // 对象不在 = 前端根本没传
}
if (head.contentLength() > 5MB) throw MEDIA_TOO_LARGE; // 用真实大小再校验一遍(防谎报)

media.setStatus("ACTIVE");
media.setActualSizeBytes(head.contentLength());        // 记真实大小,不信 declared
media.setExpiresAt(null);                              // ACTIVE 不再被清理
```

### 为什么必须 HEAD 核实?

这是整课"**不信任客户端**"的精髓。前端说"传完了"完全可能是假的:没真传、传了一半、传了个超大文件谎报成小的。后端发一个 **HEAD 请求**(只要头不要体,轻量)问 MinIO:"这对象真在吗?多大?"
- 查不到 → `MEDIA_NOT_UPLOADED`(槽建了但对象不在)。
- 查到但超大 → `MEDIA_TOO_LARGE`(防前端谎报 `declaredSize=100` 实际塞 10MB)。
- 都通过 → 转 ACTIVE,记的是 **HEAD 拿回来的真实大小**,不是前端声明的。

> **面试官追问**:"为什么不建槽时就信前端的大小?" 答:"declaredSize 是前端**声明**的,不可信——前端可以说传 100 字节实际传 10MB。真实大小只有对象存储知道,所以 finalize 时 HEAD 拿真实的 `contentLength` 覆盖声明值。这叫'以服务端观测为准'。"

> **面试官追问**:"finalize 为什么要幂等?" 答:"网络抖动/用户手抖可能重复调 finalize。用 `if 已 ACTIVE return` 保证重复调不报错、不重复改状态。幂等是所有'确认类'接口的基本功。"

## 六、线4【读重定向】：读图也不当管道

私有桶前端不能直接摸。看 [PublicMediaController.java](backend/src/main/java/com/agentlog/media/api/PublicMediaController.java):

```java
String url = mediaService.createReadRedirectUrl(mediaId);   // 签发预签名 GET URL(15分钟)
return ResponseEntity.status(302).location(URI.create(url)).build();   // 302 指过去
```

**为什么用 302 而不是后端读出文件流吐给前端?** 跟上传对称——后端不当**下载**管道。后端签一个短时(15 分钟)的预签名 **GET** URL,回 302,浏览器**自动跟随**跳转,直接从 MinIO 拉图。

前端用法:`<img src="/api/v1/public/media/med_xxx">`,浏览器请求这个地址 → 后端 302 → 浏览器再请求 MinIO 的真图 URL → 显示。用户全程无感。

> **这就是接 L10 头像的地方**:L10 的 `AuthorView.avatarMediaId`(=`med_xxx`)前端拼成 `/api/v1/public/media/med_xxx`,正好命中这条线。L10 产出头像 id,L11 提供读端点,两课在此闭环。

> **面试官追问**:"302 的 URL 有效期 15 分钟,过期了图不就裂了?" 答:"每次请求 `/public/media/{id}` 都**重新签**一个新的 15 分钟 URL,不是缓存固定 URL。浏览器加载 `<img>` 时命中读端点→拿到当次新鲜的预签名 URL→立即加载,15 分钟绰绰有余。真要 CDN 缓存是另一套方案(签更长时效或用公有读桶),本课不做。"

## 七、一页纸面试速记

| 考点 | 一句话答案 |
|---|---|
| 文件为什么不经后端 | 后端当大文件管道会被内存/带宽打爆;预签名让前端直传对象存储,后端只签发+核对 |
| 预签名 URL 原理 | 后端用 secret-key 对"PUT某key+限时"做 HMAC-SHA256 签名编进 URL;MinIO 重算验签放行;密钥不出现在 URL |
| S3Client vs S3Presigner | 前者真发请求(HEAD 核实),后者只算签名(发通行证);职责分离 |
| 为什么要 finalize | 不信前端"传完了",后端 HEAD 亲自核实对象存在+真实大小,才 PENDING→ACTIVE |
| finalize 幂等 | 重复调用(网络抖动)用"已 ACTIVE 直接返回"兜底,不重复改状态 |
| 读为什么 302 | 后端不当下载管道,签短时 GET URL 让浏览器直接找 MinIO;每次请求重签 |
| pathStyle 为什么 true | MinIO 用 path-style 寻址,AWS 默认 virtual-host 会把桶拼进域名 → 404 |
| 直传为什么不带 Cookie | 那个 PUT 发给 MinIO 不是后端,MinIO 只认 URL 签名,不认登录会话 |
| object_key 为什么随机 | 防猜测(猜不到图地址)、防同名覆盖;原始文件名只存展示字段 |
