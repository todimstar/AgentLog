① 先认识四个名词（点卡片展开）

这四个词你可能都听过但没串起来。它们是一条流水线上的四个工位，从外到内排好队。
🏭
Tomcat
一个「Web 服务器」软件。你的 Spring Boot 打成 jar，里面就内嵌了一个 Tomcat。
它负责监听 8080 端口、接住每一个 HTTP 请求，然后把请求往里递。你可以把它想成写字楼的大门和前台——所有人先进这道门。它是整条流水线最外层。
📮
Servlet
Java 规定的「处理 HTTP 请求的标准零件」。一个 Servlet = 一个能接请求、给响应的处理器。
Tomcat 收到请求后，最终要交给某个 Servlet 处理。Spring MVC 全靠一个特殊的 Servlet 叫 DispatcherServlet（调度员）总揽。所以「Servlet」是规范，「DispatcherServlet」是 Spring 派来站这个岗的人。
🚦
Filter（过滤器）
在请求「到达 Servlet 之前」拦一道的关卡。可以放行、可以拦截、可以改请求。
Filter 是 Tomcat（Servlet 规范）提供的机制，排在 Servlet 前面。一个请求可以连穿过好几个 Filter，像过安检的多道闸机。关键：Filter 比 Servlet 早执行。我们的登录验证（JWT / Bearer 令牌校验）就写在 Filter 里——先验身份，再放进去见 Controller。
🎯
DispatcherServlet
Spring MVC 的总调度员，是一个（也是唯一主力）Servlet。
它站在所有 Filter 后面。请求穿过全部 Filter 后到它这，它再看 URL 决定派给哪个 @RestController 的哪个方法。你写的 Controller 在它后面。所以 Controller 是流水线最里层。@RestControllerAdvice（全局异常处理器）也只在它这一层管事——这就是为什么 Filter 里抛的异常它够不着。
一句话记住顺序
大门(Tomcat) → 一道道安检闸机(Filter) → 调度台(DispatcherServlet) → 具体办事窗口(Controller)。 越往里越具体。登录校验在「安检闸机」这层，所以它比「办事窗口」先执行——你没通过安检，根本走不到窗口。

注意那三个「Security」标签的工位（FilterChainProxy、选链、验币 Filter）—— 它们整体其实都还只是「容器级 Filter 链」里的一个 Filter。也就是说：Spring Security 本身，是挂在 Tomcat 上的一个大 Filter，这个大 Filter 内部又自己开了一层小过滤器链。这就是「两层过滤器」的由来，下一节专讲。

③ 为什么会有「两层」过滤器？

这是全篇最关键的一节。搞懂这个，双注册坑就自然通了。

刚才流水线里，FilterChainProxy 是 Spring Security 注册到 Tomcat 上的一个普通 Filter。但它很特殊：它内部又管了一堆自己的过滤器链（就是我们的 Chain 1/2/3）。于是过滤器其实分两层住：

🏭 第一层：容器级 Filter 链（住在 Tomcat 里 · 对所有 URL 生效）
CharacterEncodingFilter（改编码） CorsFilter（跨域） FilterChainProxy（Spring Security 的入口 ← 就是它！）

这一层不认 securityMatcher、不认 @Order(0/1/2)。谁住进来，就对所有 URL 无差别执行。

🛡️ 第二层：FilterChainProxy 内部（Spring Security 自己的多条链）
@Order(0)/agent/** → Chain 3 的 AgentBearerFilter
@Order(1)/cli/** → Chain 2 的 OwnerBearerFilter
@Order(2)兜底 → Chain 1 的 Session + CSRF

只有这一层才认 securityMatcher + @Order。请求进来，按 Order 从小到大问「这个 URL 归你吗」，第一个说「归我」的链独占接管，其余的链看都看不到这个请求。

核心心智模型
securityMatcher 和 @Order 只在第二层（Security 内部）起作用。 它们决定「Security 内部选哪条链」，但对第一层（容器级）那些 Filter 完全无效。记住这句话，下一节的 bug 就是它的直接推论。

④ 那个坑：@Component 为什么会被「注册两次」？

你问：Spring 发什么癫？—— 它没发癫，是一个「贴心的约定」用错了地方。

Spring Boot 有一条约定：只要容器里有一个 Filter 类型的 Bean，就自动把它注册到第一层（容器级 Filter 链）。这对「全局日志 Filter」「全局 CORS Filter」是贴心——你不用手动挂。

但我们的验币过滤器 OncePerRequestFilter 本身就是一种 Filter。一旦给它标了 @Component，它变成 Bean，就触发了这条约定：

✅ 第 ① 次：你在 Config 里 addFilterBefore(filter, ...) 手动加进「这一条」Security 链 —— 作用域正确，只管自己的 URL 段。 ❌ 第 ② 次：Boot 看到它是 Filter Bean，自动把它注册进第一层容器级链 —— 对所有 URL 生效！这次是灾难。

事故是怎么发生的（就是你 Postman 里 /cli/whoami 被 401 的原因）

1. Chain 3 的 AgentBearerFilter 标了 @Component → 被塞进第一层全局。
2. 一个 /cli/whoami + owner 令牌的请求进来，还没走到 FilterChainProxy，就先被第一层那个全局 agent filter 抓住。
3. 全局 agent filter 只会查 agent_acting_session 表 → 拿 owner 令牌去查机娘表 → 查无 → 直接 401。
4. owner 令牌根本没机会走到它该走的 Chain 2。
为什么 @Order(0) 救不了
@Order 只排第二层链之间的顺序。可事故发生在第一层——请求还没进第二层就被拦了。@Order 对第一层那个全局 filter 毫无约束力。
修法（你也答对了）
过滤器别标 @Component，在各自 Config 里用 new 构造，依赖走 @Bean 方法参数注入。这样它压根不是 Bean，Boot 无从自动注册，作用域死死锁在本链。
（另一种修法：保留 @Component 但用 FilterRegistrationBean.setEnabled(false) 显式关掉第一层自动注册。对「只属一条链」的过滤器，new 更直白。）

⑤ 那为什么你旧项目 JWT 用 @Component 就没事？

好问题。答案是：旧项目「没事」是因为它只有一条链，「全局」和「这一条」重合了。

你旧项目 SecurityConfig 里只有一条 SecurityFilterChain（没有 @Order、没有 securityMatcher，兜底所有 URL）。所以：

维度旧项目（单链）本项目 L13（三链）
SecurityFilterChain 数量1 条（兜底所有 URL）3 条（各管 /agent、/cli、其余）
JWT filter 作用域「应该」是所有 URL（本来就该全局）只该管自己那一段 URL
@Component 双注册了吗也双注册了！也双注册了
为什么旧项目没暴露双注册的「全局」= 单链的「所有 URL」= 作用域完全重合，看不出区别全局 filter 越界拦了别的链的 URL，冲突爆发
filter 无效令牌时的动作放行，交下游处理（更宽容）直接 reject 401（更严格，一拦就死）
类比
旧项目像一个只有一个房间的房子——你把「管家」设成「管全屋」，没毛病，因为全屋就一个房间。本项目是三室一厅——你把「厨房专用管家」设成了「管全屋」，他跑去卧室、客厅乱管，就出事了。不是管家的错，是你不该把「专用」的设成「全局」的。

补充你另一个疑问：旧项目其实也被双注册了，只是它 filter 内部有 getAuthentication() == null 的判断 + OncePerRequestFilter 自带的「同请求只跑一次」去重，双重执行被悄悄化解了。所以「没报错」不等于「没双注册」，只是问题被藏住了。

⑥ 收尾：三条安全链的本质（面试可直接讲）

把上面全串起来，你现在能回答「你们的鉴权流程」这类面试题了。
链管辖 URL认证方式代表谁有无状态
Chain 1 @Order(2)其余（兜底）Session Cookie + CSRF浏览器里的你有状态
Chain 2 @Order(1)/api/v1/cli/**Bearer OwnerAccessToken你本人（CLI）无状态
Chain 3 @Order(0)/api/v1/agent/**Bearer AgentActingToken被你代入的机娘无状态
面试自述（30 秒版）
我们后端按 URL 前缀分了三条 Spring Security 过滤器链：浏览器走 Session，CLI 走 owner 令牌，Agent 走机娘令牌。选哪条只看 URL、在碰令牌之前就定了，靠 securityMatcher + @Order 排序。踩过一个坑：验币过滤器如果标 @Component，Spring Boot 会把它额外注册到容器级 Filter 链全局生效，越界拦了别的链的请求——修法是不做 Bean、在各自 Config 里 new 进本链。这也解释了为什么单链的旧项目用 @Component 没事：全局和单链作用域重合，问题被掩盖了。
三个你现在能秒答的追问
Q：Filter 和 Controller 谁先执行？ A：Filter，它在 DispatcherServlet 之前。
Q：为什么 Filter 抛的异常全局异常处理器接不住？ A：因为 @RestControllerAdvice 只管 DispatcherServlet 之后（Controller 层），Filter 在它之前，够不着——所以我们另造了 AuthenticationEntryPoint 出错。
Q：Spring Security 到底是什么？ A：本质是挂在 Tomcat 上的一个大 Filter（FilterChainProxy），内部再管自己的多条链。
