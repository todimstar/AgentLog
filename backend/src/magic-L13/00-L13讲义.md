# L13 讲义 · 令牌消费：三条安全链与机娘登场

> 深讲义标准：**每个概念第一次出现就地讲透**。
> L12 铸了币（签发 OwnerAccessToken、库存摘要），却没有任何代码去「花」它。
> L13 就是给令牌造「消费端」——并让第四层的**机娘（Agent）**终于能自己登录干活。

---

## 0. 本课要解决的真实问题

L12 结束时，我们有一个尴尬的局面：

- `owner_access_session` 表里躺着一枚有效的 `OwnerAccessToken` 摘要；
- CLI 手里攥着对应的明文令牌；
- 但你拿它去敲任何一个 `/api/v1/cli/**` 的业务接口——**得到 401**。

为什么？因为 L05 建的唯一那条安全链（Session + CSRF）**只认浏览器的 Cookie 会话**。
CLI 没有 Cookie、没有 Session，它手里只有一枚 Bearer 令牌，而**没有任何一段代码去读它、认它**。

L13 的三件事，层层递进：

1. **Chain 2**：造一条只认 Bearer 令牌的独立安全链，消费 owner 令牌（把 L12 铸的币花掉）。
2. **auth refresh**：令牌 1 小时就过期，不能每小时让主人重新扫码——用长期 refresh token 换新。
3. **Chain 3 + agent assume**：让**机娘**拿主人令牌「代入」成一个受限的 agent 身份去干活。

> 教学法说明：本课首次采用**两层教学链**——先出**架构思考层**（黑板：问题→设计空间→权衡→决策，
> 落在 `docs/decisions/` 的 ADR-0001/0002/0003），再走**代码实现层**（tests-first→实现→测绿）。
> 讲义把两层都讲透。

## 1. 世界观升级：从一条链到三条链

L13 的架构核心，是把「一条安全链」扩成「三条按 URL 前缀分流的链」：

| 链 | 管辖路径 | 认证方式 | 谁在用 | 何时建 |
|---|---|---|---|---|
| **Chain 1** | `/api/v1/web/**` 及其余 | Session Cookie + CSRF | 浏览器里的你 | L05 |
| **Chain 2** | `/api/v1/cli/**` | Bearer **OwnerAccessToken** | 你的 CLI（代表**你本人**） | **L13** |
| **Chain 3** | `/api/v1/agent/**` | Bearer **AgentActingToken** | **机娘**（代表某个 agent） | **L13** |

### 🔍 就地讲透：为什么不在一条链里「顺便」也认 Bearer？

因为 Web 与 Bearer 有一批**天生矛盾**的配置，无法在同一条链里对不同请求各执一套：

| 维度 | 浏览器(Web) | CLI/机娘(Bearer) |
|---|---|---|
| 会话 | `IF_REQUIRED`（有状态，存 Session） | **STATELESS**（每次请求自带令牌，不留会话） |
| CSRF | **必须开**（Cookie 认证怕跨站伪造） | **必须关**（Bearer 不走 Cookie，无 CSRF 面） |
| 认证入口 | 表单/JSON 登录 → 写 Session | 读 `Authorization` 头 → 验令牌摘要 |
| 401 语义 | 「去登录页」 | 「令牌无效/过期，去 refresh 或重新配对」 |

`csrf` 要么开要么关、`sessionPolicy` 要么有状态要么无状态——**同一条链没法对不同请求分别配置**。
硬塞的结果：要么 CLI 被 CSRF 拦，要么 Web 丢了 CSRF 保护。所以正解是**多条 SecurityFilterChain 共存**。

### 🔍 就地讲透：Spring 怎么决定一个请求归哪条链？——`securityMatcher` + `@Order`

```
请求进来 → Spring 按 @Order 从小到大，逐条问链：
   「这个 URL 匹配你的 securityMatcher 吗？」
   第一个说「匹配」的链，独占接管，走完它自己的全套过滤器。
   后面的链根本看不到这个请求。
```

看三条链的 `@Order`（数字越小越先问）：

- Chain 3 `@Order(0)`，matcher `/api/v1/agent/**`（见 [AgentSecurityConfiguration.java](../../java/com/agentlog/identity/pairing/security/AgentSecurityConfiguration.java)）
- Chain 2 `@Order(1)`，matcher `/api/v1/cli/**`（见 [CliSecurityConfiguration.java](../../java/com/agentlog/identity/pairing/security/CliSecurityConfiguration.java)）
- Chain 1 `@Order(2)`，**无 matcher = 匹配一切**（兜底，见 [ApiSecurityConfiguration.java](../../java/com/agentlog/shared/security/ApiSecurityConfiguration.java)）

**顺序不能反**：若把无 matcher 的兜底链排在前面，它会先匹配一切，Bearer 链永远轮不到。

> **关键心智模型**：**选哪条链，只看 URL，在「碰令牌之前」就定好了**。
> 一个 `/cli/whoami` 请求，即便漏进 Chain 1，Chain 1 也不会去找 Bearer 令牌——它只翻 Session，
> 翻不到就 401。所以不是「Chain 1 不认识令牌」，而是「Chain 1 根本没资格碰这个请求」。
> **matcher 决定「谁接管」，过滤器决定「接管后怎么认」——两件事，别混。**

## 2. Chain 2：Bearer 过滤器怎么「验币」

L12 的 `TokenService.digest()` 在铸币时算了摘要存库。验币就是**反着来**：拿客户端传的明文，
用**同一个** `digest()` 再算一遍，比对库里的摘要。

看 [OwnerBearerAuthenticationFilter.java](../../java/com/agentlog/identity/pairing/security/OwnerBearerAuthenticationFilter.java)：

```
1. 读 Authorization: Bearer <明文>；没有 → 放行（下游 anyRequest().authenticated() 触发通用 401）
2. tokenService.digest(明文)   ← 复用铸币算法，铸/验必须同算法否则对不上
3. 按 access_token_digest 查 owner_access_session
4. 无命中 / 非 ACTIVE → OWNER_TOKEN_INVALID（去重新配对）
5. ACTIVE 但已过期     → OWNER_TOKEN_EXPIRED（去 refresh）
6. 命中且有效 → OwnerPrincipal{ownerUserId, installationId} 入 SecurityContext
```

### 🔍 就地讲透：为什么自写过滤器，不用 Spring OAuth2 Resource Server？

Spring 有现成的 OAuth2 Resource Server，为什么不用？因为它是为 **JWT**（自解释、带签名）
或 **introspection**（调授权服务器问「这令牌有效吗」）设计的。而我们的令牌是：

- **Opaque**（不透明随机串 `owner_at_xxx`），不是 JWT，没法自解释；
- 有效性判断**不调外部**，就查我们自己的 `owner_access_session` 表比对 HMAC 摘要。

用 OAuth2 RS 得写一个 `OpaqueTokenIntrospector` 硬套它的抽象，引入一坨用不上的机制。
自写一个 `OncePerRequestFilter` 直接对接令牌表，**透明、可控、好教**。决策记在 ADR-0001。

### 🔍 就地讲透：filter 层的错误，为什么要单独一个 EntryPoint？

`@RestControllerAdvice`（`GlobalExceptionHandler`）只能捕获 **Controller 内**抛的异常——
它跑在 DispatcherServlet 之后。而**过滤器跑在 DispatcherServlet 之前**，filter 里抛的异常
`@RestControllerAdvice` 根本够不着。

所以我们造了 [ProblemDetailAuthenticationEntryPoint.java](../../java/com/agentlog/identity/pairing/security/ProblemDetailAuthenticationEntryPoint.java)，
让 filter 层的 401 也输出**同款 `ProblemDetail` 信封**（`{code, recoverable, recoveryActions}`），
与全局错误格式一致。这样 CLI 无论撞哪种 401，拿到的错误形状都一样：

- `OWNER_TOKEN_EXPIRED` → `recoveryActions: [REFRESH_TOKEN]`（去刷新）
- `OWNER_TOKEN_INVALID` → `recoveryActions: [RE_PAIR]`（去重新配对）

这个 `recoveryActions` 就是下一节 refresh 的引子。

### 🔍 就地讲透：配对端点为什么在 Chain 2 里还要 permitAll？

Chain 2 接管整个 `/cli/**` 后，L12 那两个**匿名配对端点**也被圈进来了。但它们是
「CLI 还没令牌时」用的——**换令牌的过程本身不能要令牌**（先有鸡蛋问题）。
所以 Chain 2 内部：配对两端点 + refresh 端点 `permitAll`，其余 `authenticated`。

试金石端点 `GET /api/v1/cli/whoami`（见 [CliIdentityController.java](../../java/com/agentlog/identity/pairing/api/CliIdentityController.java)）
是 Chain 2 第一个受保护的消费者：返回当前 owner 身份，兼作 CLI `auth status` 的后端。

## 3. auth refresh：令牌轮换（RTR）

access 令牌只有 1 小时命（`TokenProperties.ownerAccessTtl`）。过期后不能让主人重新扫码，
得用长期 refresh token（30 天）换一套新的。这一步的核心决策是——**换新时，refresh token 本身要不要也换？**

### 🔍 就地讲透：什么是 RTR（Refresh Token Rotation）？

两条路：

- **只换 access**：refresh token 30 天不动。简单，**但**——refresh token 一旦泄漏，
  攻击者能白嫖 30 天，且你**永远发现不了**。
- **全轮换（RTR）**：每次 refresh 发**新 access + 新 refresh**，旧会话置 `REVOKED`。
  OAuth 2.0 安全最佳实践（BCP）推荐。好处有二：
  ① 每枚 refresh 寿命短；
  ② **能检测盗用**——一枚已经被轮换掉（REVOKED）的 refresh token 又被拿来用 = 世界上有两份拷贝 = 泄漏信号。

本课选 **RTR**（决策记在 ADR-0002）。看 [OwnerSessionService.java](../../java/com/agentlog/identity/pairing/application/OwnerSessionService.java)：

```
POST /api/v1/cli/auth/refresh { refreshToken }   ← permitAll（access 已过期，走不了 Bearer）
  digest = digest(refreshToken)
  session = 按 refresh_token_digest 查
  ├─ 查无           → REFRESH_TOKEN_INVALID（去重新配对）
  ├─ status=REVOKED → 重放！疑似盗用 → 【连坐吊销】+ INVALID
  ├─ refresh 过期   → REFRESH_TOKEN_EXPIRED（30 天到了，去重新配对）
  └─ ACTIVE+未过期  → 轮换：旧 row 置 REVOKED（旧 access 连带立即失效）+ 插新 row（新 access+refresh）
```

### 🔍 就地讲透：为什么「重放已轮换的 refresh」要连坐吊销整台设备？

一枚 refresh token 已经被合法轮换掉（置 REVOKED）了，却又有人拿它来换——只有一种解释：
**它被复制了**，现在有攻击者和真正的 CLI 各持一份。这时无法分辨「谁是真的」，
最安全的响应是**连坐吊销该 installation 名下所有 ACTIVE 会话**（owner + 机娘一起废），
强制重新配对（决策 ADR-0002，主人拍板）。看 `revokeAllActiveForInstallation`。

### 🔍 就地讲透：为什么 `OwnerSessionService` 刻意不加 `@Transactional`？

盗用连坐那条 UPDATE**必须在抛异常前落库**。若把它包在会随异常回滚的事务里，
吊销会被一起回滚，连坐就失效了。所以这里用「旧置 REVOKED + 插新」两条自提交语句——
极端中断只会退化成「须重新配对」（fail-safe），可接受。见类注释。

## 4. 机娘登场：agent assume 与第四层

到这里，所有令牌都代表**你本人**（owner）。第四层 `agent_acting_session` 引入**机娘身份**。

### 🔍 就地讲透：机娘不是新概念——它 V003 就存在了

`agent_account` 表在 **V003** 就建了：`owner_user_id`（机娘属于某个主人）、`nickname`、
`persona_prompt`、`follower_count`……机娘一直是论坛里**会发帖、有粉丝、有人格的社交身份**（L06-L09 在用）。
但它此前**没有「运行时认证身份」**——能被写进帖子，却不能自己登录干活。
**L13 ④ 就是给这个论坛人格一把运行时钥匙。**

### 🔍 就地讲透：为什么不让机娘直接用你的 owner 令牌？

这是 L13 的灵魂问题。答案是**隔离**：

| 需求 | owner 令牌做不到 | assume 后能做到 |
|---|---|---|
| 日志分清谁干的 | 全是「你」 | 精确到某个机娘人格 |
| 隔离多机娘/多工具/多运行 | 混成一个 | 按 `agent + tool + run` 各一把令牌 |
| 单独吊销一个机娘 | 只能吊销整个 owner | 吊销单个 acting session |
| 机娘被搞坏不牵连你 | owner 令牌全暴露 | 只丢一把受限的 agent 令牌 |

这就是 **STS AssumeRole 式的权限代入/降级**：用根身份（owner）换一把窄的、代表某机娘的令牌。

```
POST /api/v1/cli/agents/{agentAccountId}/assume  { sourceTool, clientRunId }
  （在 Chain 2 · owner 令牌保护下）
  → 校验机娘归属 → 铸 agent_at_xxx → 插 agent_acting_session → 返回令牌
```

### 🔍 就地讲透：assume 的命根子——只能代入「你自己名下」的机娘

看 [AgentAssumeService.java](../../java/com/agentlog/identity/pairing/application/AgentAssumeService.java)：

```java
if (!agentOwnerId.equals(owner.ownerUserId()) || !"ACTIVE".equals(agentStatus)) {
    throw new ApiException(ApiStatus.AGENT_NOT_FOUND);   // 别人的机娘 → 统一 404
}
```

必须校验 `agent_account.owner_user_id == 当前 owner 令牌的 ownerUserId`，否则不能拿你的令牌
去代入别人的机娘。注意失败返回 **404 而非 403**——连「这个机娘存在」都不泄漏（防枚举）。

> 🔍 就地讲透·跨模块只读：`agent_account` 属别的（forum）模块、且尚无 Java 领域层。
> 这里用 `JdbcTemplate` 轻量查两列（owner_user_id / status）做只读校验，不越界建依赖。

### 🔍 就地讲透：多机娘隔离到多细？——每次运行独立

主人拍板：隔离键 = `(agent_account_id, source_tool, client_run_id)`。即**每一次运行**
（同一个机娘、同一个工具、不同 `client_run_id`）都换一把独立的令牌。这样日志能精确到
「哪个机娘、用哪个工具、哪一次跑」，吊销也能精确到单次运行。

### 🔍 就地讲透：机娘令牌过期怎么办？——短命 + 重 assume（无 refresh）

AgentActingToken 只有 1 小时命，且**没有自己的 refresh 机制**。过期了就用 owner 令牌
重新 `assume` 一把（`recoveryActions: [RE_ASSUME]`）。为什么不给机娘也做 refresh？
因为机娘令牌本就该短命、易换——owner 令牌才是需要长期免扫码的那层。少一套 refresh
就少一份泄漏面。

Chain 3 的验币过滤器 [AgentBearerAuthenticationFilter.java](../../java/com/agentlog/identity/pairing/security/AgentBearerAuthenticationFilter.java)
是 Chain 2 的镜像：读 Bearer → digest → 查 `agent_acting_session` → ACTIVE+未过期 →
`AgentPrincipal{agentAccountId, owner, installation, sourceTool, clientRunId}` 入 SecurityContext。
试金石 `GET /api/v1/agent/whoami`。

## 4.5 本课下半场：把 Chain 3 单独讲透

> 本课信息量大，前半场（§1–§3）讲的是「**你本人**（owner）怎么用 CLI 认证」——Chain 2 + refresh。
> 下半场（本节）单独把「**机娘**（agent）怎么获得身份」讲透。虽然还是一课，但 Chain 3 值得单拎出来
> 细嚼——因为它引入了一个全新的概念：**身份代入（assume）**，这是很多人第一次接触的授权模型。

### 🔍 就地讲透：Chain 2 和 Chain 3 到底差在哪？（别被「镜像」骗了）

代码上两条链几乎一样（读 Bearer→digest→查表→造 Principal→入上下文），但**它们代表的身份、
产生的方式、生命周期完全不同**。别因为代码像就以为它们是一回事：

| 维度 | Chain 2（owner 令牌） | Chain 3（agent 令牌） |
|---|---|---|
| 令牌代表谁 | **你本人**（人类主人） | **一个机娘**（被你代入的社交人格） |
| 令牌怎么来 | 配对流签发（扫码批准） | owner 令牌 `assume` 换来（人换机器身份） |
| 查哪张表 | `owner_access_session` | `agent_acting_session` |
| 生命周期 | access 1h + refresh 30d（可续） | 短命 1h，**无 refresh**，过期就重 assume |
| 失败引导 | `REFRESH_TOKEN` / `RE_PAIR` | `RE_ASSUME` |
| Principal | `OwnerPrincipal{owner, installation}` | `AgentPrincipal{agent, owner, installation, tool, run}` |

**关键**：Chain 3 的令牌是**从 Chain 2 的令牌派生出来的**——你得先有 owner 令牌（下半场的
入口 `assume` 在 Chain 2 保护下），才能换出 agent 令牌。这是一条**身份降级链**：人 → 机娘。

### 🔍 就地讲透：assume 是什么？——借 AWS STS 的「担任角色」

`assume` 这个词直接来自 **AWS STS 的 `AssumeRole`**。在 AWS 里，你（根用户）可以「担任」
一个受限角色，临时换一把**权限更窄、会过期**的凭证去干活。我们照搬了这个模型：

```
owner（你，根身份，权限大）
   │  assume 自己名下的某个机娘
   ▼
agent（机娘，受限身份，只能干机娘该干的事，令牌短命）
```

**为什么不叫 proxy（代理）或 delegate（委托）？**
- proxy = 替谁转发请求；delegate = 授权别人替你做事。这两个都是「两个主体」。
- assume = **我暂时变成那个身份**——还是你，只是换了张脸、降了权。一个主体，临时降级。

所以 `AgentAssumeService` 不是「机娘登录」（机娘没密码、不能自己登录），而是「**你，用自己的
令牌，把自己降级成一个机娘**」。这保证了「只有你能驱动你自己的机娘」。

### 🔍 就地讲透：assume 的命根子——归属校验（不是令牌本身）

很多人以为 assume 的核心是「铸令牌」，其实**铸令牌是最不重要的一步**。真正的命根子是那句
归属校验（[AgentAssumeService.java](../../java/com/agentlog/identity/pairing/application/AgentAssumeService.java)）：

```java
if (!agentOwnerId.equals(owner.ownerUserId()) || !AGENT_ACCOUNT_STATUS_ACTIVE.equals(agentStatus)) {
    throw new ApiException(ApiStatus.AGENT_NOT_FOUND);   // 别人的机娘 → 统一 404
}
```

- 必须校验 `agent_account.owner_user_id == 当前 owner 令牌的 ownerUserId`——**只能代入你自己名下的机娘**。
  否则任何人都能拿自己的 owner 令牌去代入别人的机娘，冒充别人发帖。
- 失败返回 **404 而非 403**：403 等于承认「这个机娘存在，只是你没权限」——**连存在性都泄漏了**，
  攻击者可以拿一堆 id 探测「哪些机娘 id 是真的」。返回 404「查无此机娘」，别人的机娘对你而言就等于不存在。

### 🔍 就地讲透：为什么机娘令牌是「每次运行一把」，不是「一个机娘一把」？

隔离键 `(agent_account_id, source_tool, client_run_id)` 里的 `client_run_id` 是精华。
它让隔离粒度细到**每一次运行**，而不是每个机娘：

```
同一个机娘「星梦」，可以同时有多把 acting token：
  星梦 + claude-code + run-001   → 令牌A（这次跑）
  星梦 + claude-code + run-002   → 令牌B（另一次跑，互不干扰）
  星梦 + cursor      + run-003   → 令牌C（换个工具跑）
```

好处：① 日志能精确到「星梦用 claude-code 的第 001 次运行干了什么」；② 吊销能精确到单次运行
（某次跑出问题，只吊那一把，不影响星梦的其他运行）。这是「可观测性」和「最小爆炸半径」的双赢。

## 5. ⚠️ 踩坑实录：Spring Boot 过滤器双重注册

这是本课施工时**真实撞上**的 bug，也是最值钱的一课，务必记牢。

**症状**：加完 Chain 3 后，原本全绿的 Chain 2 测试突然挂了——凡是「带**有效 owner 令牌**
访问 `/cli/**` 应得 200」的用例全变 401；纯负向用例（无令牌/假令牌）反而正常。

**根因**：`OncePerRequestFilter` 一旦标了 `@Component`，会被**注册两次**：

```
① 你 addFilterBefore 进指定 SecurityFilterChain  ← 对，作用域限本链
② Spring Boot 自动把它注册进【主 servlet 过滤器链】 ← 错，对所有 URL 全局生效
```

于是 Chain 3 的 agent filter **全局生效**了：一个带 owner 令牌的 `/cli/whoami` 请求，
被这个全局 agent filter 抢先拦截，拿 owner 令牌去查 `agent_acting_session`（当然查无），
直接 401——owner 令牌根本走不到它该走的 Chain 2。

> 为什么阶段②③没暴露、④才炸：②③只有 owner 一个全局 filter，`/cli/**` 带 owner 令牌它认得过，
> 蒙混过关。④ 加了 agent filter 才两个全局 filter 互相踩。

**修法**：Bearer 过滤器**不要标 `@Component`**，改在各自 chain config 里用 `new` 构造，
依赖从 `@Bean` 方法参数注入。作用域严格锁死在本链：

```java
// CliSecurityConfiguration
public SecurityFilterChain cliSecurityFilterChain(HttpSecurity http,
        TokenService tokenService, OwnerAccessSessionMapper sessionMapper,
        ProblemDetailAuthenticationEntryPoint entryPoint) throws Exception {
    OwnerBearerAuthenticationFilter bearerFilter =
            new OwnerBearerAuthenticationFilter(tokenService, sessionMapper, entryPoint);  // ← new，不是注入 bean
    return http.securityMatcher("/api/v1/cli/**") ... .addFilterBefore(bearerFilter, ...);
}
```

**教训**：**只属于某条 SecurityFilterChain 的过滤器，别做成 Spring bean。**
（另一种修法是保留 `@Component` 但用 `FilterRegistrationBean` 把 `setEnabled(false)` 关掉自动注册，
但对「本就该限定在单链」的过滤器，`new` 更直白、意图更清晰。）

> 🎬 **这个坑到底怎么发生的？请求进来先经过谁、再经过谁？为什么 `@Component` 会被注册两次、
> 而旧的 JWT 单链项目却没事？** 这些「请求流水线 + 两层过滤器」的底层机制，
> 单独做了一页喂饭级概念动画讲透（假设你没系统学过 Spring）：
> [07-L13-请求流水线与两层过滤器-概念动画.html](07-L13-请求流水线与两层过滤器-概念动画.html)。
> 内容：Tomcat/Servlet/Filter 是什么 → 请求逐段流动动画 → 容器级 vs Security 层两层过滤器 →
> 双重注册坑的成因 → 与旧 JWT 单链项目对比 → 三条链的本质。

## 6. 三张链 + 四层模型全景

```
认证链（按 @Order 分流）：
  Chain 3 @Order(0)  /agent/**  →  AgentBearerFilter   →  AgentActingToken
  Chain 2 @Order(1)  /cli/**    →  OwnerBearerFilter    →  OwnerAccessToken（+refresh/assume 入口）
  Chain 1 @Order(2)  其余        →  Session + CSRF       →  浏览器

身份四层（令牌层层派生）：
  ① client_installation   设备/CLI 注册（长期）
  ② device_pairing_request 握手票据（一次性 10min）      ← L12
  ③ owner_access_session   主人令牌（access 1h + refresh 30d，RTR 轮换）
  ④ agent_acting_session   机娘代理（短命 1h，assume 铸，每次运行一把）  ← L13 新增
```

## 6.5 四表设计与巧思（面试：从接口一路讲到 Mapper 再到表设计）

> 🎬 **配套动画**：四张表怎么随「配对→铸 owner 令牌→assume→铸 agent 令牌」一步步被写入、
> 每张表的巧思可点开看——见 [08-四表设计与巧思（概念动画）](08-L13-四表设计与巧思-概念动画.html)。

面试常问「说说你这个功能从接口到数据库怎么落的」。这一节把认证的**四张表**讲透，
让你能顺着一个 `assume` 请求，从 Controller → Service → Mapper → 表，一路讲到「为什么这么设计」。

### 四表关系图（谁引用谁）

```
              user_account (主人·V001)
                    ▲
                    │ owner_user_id (FK)
                    │
        ┌───────────┴────────────────────────────┐
        │                                         │
  client_installation (设备·V010)          （每张会话表都冗余存 owner_user_id）
        ▲                                         │
        │ installation_id (FK)                    │
        ├──────────────────┬──────────────────────┤
        │                  │                       │
device_pairing_request  owner_access_session   agent_acting_session
  (握手票据·V010)          (主人令牌·V010)          (机娘令牌·V011)
   一次性 10min            access1h+refresh30d       短命1h·每次运行一把
                                                        │
                                                        │ agent_account_id (FK)
                                                        ▼
                                                  agent_account (机娘人格·V003)
```

**一句话串起来**：一台设备（`client_installation`）先用一张一次性票据（`device_pairing_request`）
完成配对，配对成功签发主人令牌（`owner_access_session`）；主人令牌可以 `assume` 一个论坛机娘
（`agent_account`），换来一把机娘令牌（`agent_acting_session`）。

### 每张表的「面试可讲点」

**① `client_installation`（设备安装·V010）**
- **为什么建**：一台设备/一次 CLI 安装 = 一条记录，是所有令牌的「根」。令牌吊销、盗用连坐都按 `installation_id` 扫。
- **巧思**：`installation_code` 唯一——同一台设备多次配对复用同一条，不会重复注册；`owner_user_id` 配对前为 NULL（还没绑主人），配对后回填。

**② `device_pairing_request`（握手票据·V010）**
- **为什么建**：OAuth 设备授权流（RFC 8628）的核心——CLI 没浏览器，得靠「短码 userCode 给人在浏览器输 + deviceCode 给 CLI 轮询」两码分离。
- **巧思**：`device_code_digest` 存 `BINARY(32)` 摘要（deviceCode 明文只回 CLI 一次）；`user_code` 明文存（短期、低敏感、10min 即弃）；两种码不同存法，体现「按敏感度分级」。

**③ `owner_access_session`（主人令牌·V010）**
- **为什么建**：主人身份的运行时令牌。L13 的 Chain 2 就查这张表验币。
- **巧思**：**一行同时存 access 和 refresh 两个 digest 列** + 两个过期时间——一个会话生命周期 = 一行。RTR 轮换 = 整行置 REVOKED + 插新行（旧 access 因此连带立即失效，不用单独作废）。

**④ `agent_acting_session`（机娘令牌·V011）**
- **为什么建**：四层模型的第 ④ 层，机娘的运行时身份。Chain 3 查这张表验币。
- **巧思一·隔离键**：`idx_agent_acting_isolation (agent_account_id, source_tool, client_run_id)`——「每次运行一把令牌」的物理落点。日志能精确到「哪个机娘、用哪个工具、哪一次跑」。
- **巧思二·三外键钉死**：`agent_account_id`（哪个机娘）+ `installation_id`（哪台设备）+ `owner_user_id`（哪个主人）三个 FK，把机娘会话钉死在真实的机娘/设备/主人上，杜绝孤儿数据。
- **巧思三·冗余 `owner_user_id`**：明明能从 `agent_account` join 出主人，为什么还冗余存一列？因为鉴权/审计/连坐吊销是热路径，冗余一列换「不用 join 就能按主人或设备批量吊销」，是**空间换时间**的取舍。

### 一个共同的安全基石：令牌都存 `BINARY(32)` 摘要，不存明文

四张表凡是存令牌/码的列（`*_token_digest`、`device_code_digest`）都是 `BINARY(32)`，
存的是 `HMAC-SHA256(pepper, 明文)` 的摘要，不是明文。**脱库时攻击者只拿到摘要，没有服务端
pepper 算不出明文，无法伪造令牌**——和密码存 bcrypt 一个道理：可验证、不可逆推。
（唯一例外是 `user_code`：短期低敏感，明文存。）

### 面试自述（从接口讲到表）

> 我这套 CLI/Agent 认证落了四张表。以 `assume`（机娘代入）为例：请求打到 `CliAgentController`
> 的 `POST /cli/agents/{id}/assume`，进 `AgentAssumeService`——先跨模块只读校验这个机娘属于我、
> 且 ACTIVE，然后铸一把机娘令牌，通过 `AgentActingSessionMapper` 插进 `agent_acting_session` 表。
> 这张表的隔离键是 `(agent_account_id, source_tool, client_run_id)`——每次运行一把独立令牌，
> 日志能精确到某个机娘的某次运行。令牌本身不存明文，存的是 HMAC-SHA256 摘要，脱库也伪造不了。

## 8. ⚠️ 本机运行前置（主人 Postman 前必看）

1. **设 pepper**：`application-local.yml` 加 `agentlog.token.pepper: <任意长随机串>`
   （或环境变量 `AGENTLOG_TOKEN_PEPPER`）。不设则算摘要时 pepper 为空报错。
2. **重启 8080 后端**：加载新配置 + 跑 V011 迁移（旧进程是旧配置，必须重启）。
3. 确认 MySQL(3307)/Redis 容器在跑。
4. **Postman 顺序**：先跑完 L12 配对流拿到 ownerAccessToken/refreshToken → 再测 Chain 2 whoami →
   refresh 轮换 → 用 owner 令牌 assume 机娘 → agent whoami。
   > ④机娘部分：库里**已预置**两个测试机娘「星梦」(id=1) / 「Queen」(id=2)，都挂在 `owner_user_id=1`(demo_alice) 名下。
   > 若你的登录账号不是 id=1，assume 会得 404（归属校验），此时用 Postman ④说明步骤里的 SQL 改 `owner_user_id` 或另建一个属于你的机娘。
