# L08 评论·二级回复 · 讲义（对话版）

> **一句话**：给帖子详情页长出评论区——能发评论、能回复、能回复别人的回复，但底层永远只有两层。
> 这是从 L07 的"看一屏帖 + 看单篇"，扩展到"单篇下能互动"。档位 🟢 2h，**我写你审**节奏。
>
> ⚠️ 本课有两个【血泪故事】值得记牢，都是面试金句：
> ① 第一版模型把"回复回复"误做成了禁止，被你当场揪出——**B站不是禁回复，是把回复扁平成两层**。
> ② 跑 SQL 时发现开发库被赶工版迁移污染到 V017，撞 Flyway 校验——**开发库也是状态，会被污染**。

咱们今天用聊天口吻讲。先把"评论到底该长啥样"这件最容易做错的事讲透，再自顶向下从 Controller 推到表。

## 一、最核心的认知：B站评论是"逻辑无限，物理两层"（面试必问）

先把容易混的两个词分清——**这正是第一版做错的地方**：

```
✅ B站的"无限回复"（逻辑上能一直接话，物理上永远两层）：
楼主评论（一级）
 ├ A 回复楼主        ┐
 ├ B 回复 @A         │ 全是【二级】！都挂在同一个一级评论(楼)下
 ├ C 回复 @B         │ 靠 reply_to 显示"回复@谁"，但 depth 全=2
 └ D 回复 @C         ┘ 平铺在一个楼里，不缩进

❌ 真正要禁的"三级"（树状铺开，UI 会崩）：
楼主评论
 └ A 回复
    └ B 回复 A        ← 缩进加深
       └ C 回复 B     ← 再加深，无限套娃，手机屏幕撑不住
```

**关键区分**：
- 你要**禁**的"三级" = 缩进层级 ≥3，树状铺开。
- 你要**保**的"回复回复" = A→B→C→D 链式对话，但**物理全是二级，挂同一个楼，平铺展示**。

> **第一版的 bug**：我用"父评论 depth≠0 就拒绝"，导致"回复楼主之后谁都不能再接话"——退化成了远古论坛。
> 你一句"B站明明能回复回复"把它打回来了。**正确做法不是检测三级后报错，是让三级根本无法被表达。**

## 二、模型的灵魂：`root_comment_id`（楼）

实现"逻辑无限、物理两层"，靠 comment 表的**三根支柱列**：

| 列 | 含义 | 一级评论 | 二级回复 |
|---|---|---|---|
| `root_comment_id` | **楼**：这条属于哪一层楼 | 指向自己 | 指向所属的那条一级 |
| `parent_comment_id` | 直接父：回复的是谁 | NULL | 指向被回复的那条（可以是另一条二级！） |
| `reply_to_comment_id` | @谁：纯展示"回复 @某人" | NULL | 一般=parent，展示用 |
| `depth` | 楼层深度 | 1 | 2（**永远**） |

看一个真实链路，体会 `root` 怎么把"回复回复"压平：

```
一级#1   root=1  parent=NULL  depth=1
 ├ #2   root=1  parent=1     depth=2  reply_to=1    "评论"
 ├ #3   root=1  parent=2     depth=2  reply_to=2    "回复 @B"   ← 回复二级#2，合法！
 └ #4   root=1  parent=3     depth=2  reply_to=3    "回复 @C"   ← 回复二级#3，还能接着回！
```

**看懂这里就懂了全部**：#3 #4 都是"回复回复"，但因为后端把它们的 `root` 强制设成 #1，
它们**物理上全挂在 #1 这层楼下，depth 永远=2**。前端按 `root` 分组，一个楼里平铺，靠 `reply_to` 渲染"回复@谁"。

**禁三级的真正手段 = 扁平化**：后端算 root 时——
```java
// 目标是一级 → 楼就是它自己；目标是二级 → 楼是它的 root（不是它自己！）
Long floor = target.getDepth() == 1 ? target.getId() : target.getRootCommentId();
comment.setRootCommentId(floor);
comment.setDepth(2);   // 永远 2，不信客户端
```
回复二级#3 时，`floor = #3.root = #1`，于是新评论照样挂在 #1 楼下。**三级状态根本算不出来**。

> **面试金句**："B站的禁三级不是校验拦截，是数据建模——通过 root_comment_id 把任意深度的回复
> 在写入时就压平到第二层，三级在存储模型里无法表达，所以不需要运行时去'防'它。"

## 三、为什么还要 DB 的 `CHECK(depth IN (1,2))`？（你问得很准）

你问："本流程里 depth 永远算出来是 1 或 2，哪里会破坏它？还要这个 CHECK 干嘛？"

**答案：CHECK 救的不是当前这条正确代码，是未来还没写出来的 bug。**

现在 `create()` 算 depth 是对的。但护栏是给将来准备的：
- 哪天加个"管理员批量导入历史评论"的新入口，写的人忘了压平逻辑；
- 哪次重构动了 root 计算；
- 哪条并发新路径绕过了 Service。

任何一个让 `depth=3` 溜进来，**DB 直接拒插**。这就是"不变量下沉到数据库"——
不依赖每个写入者的自觉，把铁律刻在表上。**应用层校验是第一道，DB 约束是最后一道兜底，两者不冲突。**

> **面试点**：被问"既然应用层保证了，为什么还要数据库约束"——答"应用层会演化、会有多个写入入口、会有 bug，
> 数据库约束是单一的、永远生效的最后防线。深度防御（defense in depth）。"

## 四、软删，不硬删（你完整答对了）

`softDelete` 只改 `status='DELETED'`，不删行。为什么不能硬删？**两层都会炸**：

1. **业务层**：硬删一条一级评论（楼主），它下面挂着 3 条二级回复 → 那些回复的 `root`/`parent` 全指向一个不存在的 id，
   前端查它们的父评论查空 → **楼塌了，无故报错**。
2. **数据库层**：更直接——`fk_comment_parent` 外键约束，**根本不让你删**有子评论引用的那条，硬删直接抛约束异常。

所以软删是唯一出路：**留个"该评论已删除"的占位楼层**，结构不塌，子回复还在。

```java
comment.setStatus("DELETED");
commentMapper.updateById(comment);          // 只改状态
commentMapper.bumpCommentCount(postId, -1); // 评论数 -1（占位不算有效评论）
```

视图层做**脱敏**：DELETED 的行，content 不外泄、作者匿名化，只保留楼层结构撑占位：
```java
String content = deleted ? "该评论已删除" : row.getContent();
AuthorView author = deleted ? new AuthorView(null, "已注销") : ...;
```

> **面试金句**："二级评论的软删是必须的，不是可选优化——硬删父评论会让子回复成为孤儿，
> 数据库外键也会拒绝删除。软删用一个 status 字段把'物理存在但逻辑消失'解耦开。"

## 五、评论树躲 N+1（你完整答对了）

**N+1 是什么**：查 1 次评论列表（1），再为每条评论单独查 1 次作者名（N），共 1+N 次 SQL。评论一多，DB 被打爆。

**躲法**：一条 JOIN 全查出来 + 排序键聚楼。

```xml
<!-- CommentMapper.xml：一条 SQL 拉全帖评论 + 作者名 -->
SELECT c.id, c.root_comment_id, c.parent_comment_id, c.reply_to_comment_id, c.depth,
       c.author_user_id, u.display_name AS author_name, c.content, c.status, c.like_count, c.created_at
FROM comment c
JOIN user_account u ON u.id = c.author_user_id      -- ← 作者名一次 JOIN 进来，不逐条查
WHERE c.post_id = #{postId}
ORDER BY c.root_comment_id ASC, c.created_at ASC, c.id ASC   -- ← 按楼聚，楼内按时间
```

**`ORDER BY root_comment_id` 的巧思**：同一层楼的所有评论 root 相同，排序后它们天然挨在一起。
平铺数组就是「楼1(一级) + 楼1的所有二级 → 楼2 + 楼2的二级们」。
**前端拿到这个有序扁平数组，顺序扫一遍按 root 分组就成两层树**——后端不组树，少一层嵌套，前端更灵活。

> 第一版我没有 root 列，被迫用 `COALESCE(parent_comment_id, id)` 凑排序键，又绕又难懂。
> 有了 root 列，排序键就是干净的 `root_comment_id`——**好的数据建模让查询自然变简单**。

> **面试点**："评论树读取的 N+1 防范，靠 JOIN 一次拉全 + 按 root 排序让同楼聚集，
> 把'树形组装'下推给前端做内存分组。后端恒定 1 条 SQL，与评论数量无关。"

## 六、契约的取舍：后端吐扁平，前端组树

OpenAPI 里 `CommentPage.items` 是**一维扁平数组**，`CommentView` 没有 `children` 字段。
这是故意的——**后端按楼层顺序吐平铺评论，前端按 root 分组成两层**。

但契约的 `CommentView` 最小集只有 `id/author/content/likeCount/createdAt`，**少了组树必需的结构字段**。
我们做了**超集**（契约是下限不是上限），补了 5 个前端必需字段：`rootCommentId/parentCommentId/replyToCommentId/depth/status`。

> **认知**："契约定义的是最小保证，实现可以返回更多前端需要的字段。组树的结构信息
> (root/parent/depth)必须由后端给，前端不可能凭空算出谁挂谁。"

## 七、跨模块计数：comment_count 怎么 +1（Modulith 边界）

发评论要给 `post.comment_count + 1`。但 `post` 表的 DO（`PostDO`）在 **content 模块**，
forum **不能 import 它**（ArchUnit 的 `ModularityTest` 会判红）。

怎么办？**forum 用自己的 Mapper 直写 post 物理表**，零 import：
```java
// CommentMapper.xml —— forum 自己的投影，DB 端原子自增
UPDATE post SET comment_count = comment_count + #{delta} WHERE id = #{postId}
```

为什么这样合规？因为 `comment_count` 是 **forum 维护的"互动派生列"**（跟 L23 的 hot_score 一个道理）——
post 这张物理表里，内容字段归 content，互动计数列归 forum。**物理表 ≠ 模块归属**。

而且 `count = count + ?` 是 **DB 端原子自增**，并发安全，不走"先读后写"的竞态。
返回受影响行数：0 行=帖子不存在→抛 `POST_NOT_FOUND`，整笔事务回滚（不留孤儿评论）。

> **L07 学的"跨模块只读→自建投影直查物理表"，这里延伸到"跨模块写派生列→也自己直写"。**
> 注意区分：写**别人领域拥有的核心数据**（如 AI 投稿写 content 草稿）才必须走 Facade；
> 写**自己领域拥有、只是物理上寄存在别人表里的派生列**，自己直写没问题。

## 八、脏库陷阱（本课第二个血泪故事，面试可讲）

跑 SQL 时发现：开发库 `infra-mysql-1` 的 `flyway_schema_history` 已经被那条全自动赶工分支
（L08→L25 一夜跑完那条）迁移到了 **V017**，里面有一张**结构完全不同的旧 V006 comment 表**
（旧版用 `deleted` 布尔 + `author_type`，没有我们要的 `root_comment_id`/`status`）。

**两个独立的坑**：
1. **Flyway 校验冲突**：Flyway 靠 `flyway_schema_history` 记每个版本的 checksum。库里已有"别的 V006"记录，
   我们本地 V006 文件 checksum 对不上 → 启动时 **ValidationException 拒绝启动**。
2. **表结构是旧的**：即便绕过校验，库里那张 comment 表是 L25 版，代码要 `status` 它给 `deleted`，列名对不上。

> **为什么测试没暴露这个？** 因为测试用 **Testcontainers 临时全新库**（每次拉新容器从 V001 跑），
> 跟脏开发库无关。所以"测试全绿 ≠ 启动后端能用"——**手工验收必须用真实开发库才能撞出这个坑**。

**处理**：drop + create `agentlog` 库，让 Flyway 从 V001 干净重跑到我们的新 V006。

> **面试金句**："开发数据库本身也是一种状态，会被历史迁移污染。Flyway 的版本校验机制
> 在'同一个版本号被不同脚本占用'时会拒绝启动——这是它的特性不是 bug，保护你不会在不一致的 schema 上跑。"
