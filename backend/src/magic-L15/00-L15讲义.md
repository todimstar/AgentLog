## 1. 黑板：顺序凭什么可信？

### 1.1 先看清约束

两个 AI 对话，一个在 Claude Code 里、一个在 Codex 里。它们**互相不知道对方存在**，
没有共享内存、没有共享文件、不能互相发消息。它们之间唯一的通道是**你**——你复制一串字符，
从一个终端粘到另一个终端。

这个约束决定了一切。**先认清约束，再谈设计**。

### 1.2 设计空间：三条路

| 方案 | 机制 | 代价 |
|---|---|---|
| ① 主人预先排定 A→B→C | 建会话时就列出全部参与者与顺序 | 要求你**事先知道**要请谁、请几个。真实场景是"写完一段才决定要不要再叫一个"——预排把动态过程冻成静态计划 |
| ② **令牌接力**（蓝图选择） | 每入队一次就签发一张新的"尾令牌"，谁拿到谁能接下一棒 | 令牌要经过你的手（复制粘贴），泄漏面比服务端内部凭证大 → 用 24h 短 TTL + 一次性消费对冲 |
| ③ 抢占式队列 | 任何持 agent 令牌的机娘都能往会话里插队 | 谁都能插 = 无法保证顺序；且跨主人的机娘也能插（多租户破防） |

**选 ②，理由是物理约束不是审美**：令牌是「**可复制粘贴的凭证**」，天然匹配那个物理动作。
方案①要求你有先知，方案③放弃了顺序。

### 1.3 为什么不能用时间戳排序

最偷懒的做法是：各自提交时打个时间戳，服务端按时间戳排。**这个做法会崩**，因为：

- 时间戳是**观测**：B 完全可能手比 A 快、机器时钟比 A 早、网络有时差，甚至有人手工改了系统时间；
- 而 B **只有拿到 A 那张令牌之后**才可能入队——这个"之后"是**因果的**，不是时钟的。

在分布式系统里这叫 **因果序（happens-before）**，Lamport 1978 年那篇
*Time, Clocks, and the Ordering of Events in a Distributed System* 就是在说这件事：
**物理时钟不可信，因果链可信。**

落到我们代码里，因果链就是一列自引用外键：

```sql
-- V012__create_collaboration.sql
predecessor_ticket_id BIGINT NULL,   -- ★ 因果链：前一棒。首棒为 NULL
CONSTRAINT fk_ticket_predecessor FOREIGN KEY (predecessor_ticket_id) REFERENCES contribution_ticket(id)
```

链表式追加，尾巴由 `collaboration_session.tail_handoff_token_id` 指着。
**后发的票必然在链尾**，与谁手快、谁时钟准完全无关。

> 💼 **面试点**：这是一个能讲 3 分钟的好故事。「我们没有用时间戳排序，因为时间戳表达的是观测，
> 而我们需要的是因果。第二个 AI 只有拿到第一个 AI 交出的令牌才可能入队，这个'之后'是因果决定的，
> 物化成 `predecessor_ticket_id` 一列。这样即使有人改系统时间、即使两台机器时钟差几秒，
> 顺序也不会乱。」——从 Lamport 的理论落到一列外键，中间每一步都说得通。

## 2. ★重点段一：为什么 ticket 和 handoff 是两张表

（这是带练时你说"不太清楚"的那题。**下面这一节在你 2026-08-01 提出合表方案后重写过**——
你的方案推翻了我原本的第一条理由，这里如实记录整个推演。）

它们看起来严格一一对应：每入队一个 ticket，就签发一张新令牌。既然一一对应，
为什么不合成一张表？

### 2.1 你提的方案（技术上完全可行，我先认账）

> 把 ticket 做成**双向链表**，每个节点加一个接力棒 code。消费的标志就是 `next_ticket` 有没有值；
> 用接力棒 code 找到末尾非空节点，然后造一个新节点指向旧节点。

```sql
contribution_ticket
  ...
  predecessor_ticket_id      -- 前驱
  next_ticket_id             -- 后继（双向）      ← 新增
  handoff_token_digest       -- 这一棒之后的接力棒 ← 新增
  handoff_expires_at         ← 新增
```

**我讲义原本的「理由一」在这个方案下失效了**，必须撤回：

> ~~理由一：一张令牌关联两个 ticket（`predecessor_ticket_id` + `consumed_ticket_id`），合表装不下。~~

在你的方案里**装得下**——令牌挂在前驱那一行上，「从谁那来」= 这一行自己（隐式），
「被谁消费」= `next_ticket_id`。**双向链表把两个外键都吸收了。**

### 2.2 但「消费标志 = next_ticket 有没有值」有先有鸡还是先有蛋

```sql
UPDATE ticket SET next_ticket_id = ?  WHERE handoff_digest=? AND next_ticket_id IS NULL AND ...
                                 ↑ 这个值从哪来？必须【先建出新票】才有 id
```

**要先建票才能做闸门 UPDATE** ——这正是 §3.4 我踩的那个坑：两线程双双先建票 →
撞 `uk_ticket_sequence` → 败者拿 `DuplicateKeyException` 而不是 409。

绕开的唯一办法是**再加一个 `handoff_consumed_at` 列当闸门**，闸门通过后再回填 `next_ticket_id`。
于是你有了**两个消费标志**，它们可能不一致（闸门成功但回填失败）。这是第一个具体代价。

### 2.3 「双重状态码」的由来：状态空间本来就是二维的

你追问「为什么会有双重状态码？有这么多种情况吗？」——把实际可达组合列全：

| 场景 | ticket 侧 | **这一棒之后的**令牌侧 |
|---|---|---|
| 刚入队、前序没写完 | `WAITING_PREDECESSOR` | `AVAILABLE` |
| 刚入队、前序已完成 | `READY_TO_WRITE` | `AVAILABLE` |
| **正在写字** | `LEASED` | **`AVAILABLE`** |
| 写完了、还没人来接 | `DONE` | `AVAILABLE` |
| 写完了、下一棒接走了 | `DONE` | `CONSUMED` |
| 租约超时（L17） | `FAILED_TIMEOUT` | **`FROZEN`**（禁止新人进来） |
| 主人 retry 后（L18） | `READY_TO_WRITE` | `AVAILABLE`（解冻） |
| 前序失败被连累（L17） | `BLOCKED_BY_PREDECESSOR` | `FROZEN` |
| 主人 terminate（L18） | 保持原状 | `REVOKED` |
| 文章发布后（L20 TX-02 第 11 步） | `DONE` | `REVOKED`（吊销尾令牌） |

**看第三行 `LEASED + AVAILABLE`**：第 N 棒**正在写字的同时**，第 N+1 个 AI 可以拿着尾棒入队。
这就是 `APPROVAL_RECORD` 冻结的「**后序可提前排队，不可提前写**」。

**这一格证明两个维度真的正交**：
- ticket 状态回答「**已经进来的人能不能写**」
- 令牌状态回答「**还能不能有新人进来**」

7×5 理论组合，实际可达约 10 种，且**不存在一方决定另一方的映射**
（同是 `DONE`，令牌可能是 `AVAILABLE`/`CONSUMED`/`REVOKED` 三种）。

> **关键结论：合表并没有减少状态列。**
> 状态空间是二维的，你还是要两个列，只是从「两张表各一个」变成「一张表两个」——
> 而代价是同时失去了外键分离、生命周期分离、清理策略分离。**换了个地方放，没换掉复杂度。**

### 2.4 决定性的那条：基数不是 1:1，Pack 自己写着

`03-api/error-codes.md` 的 ACPP 节：

| code | HTTP | 动作 |
|---|---:|---|
| `ACPP_HANDOFF_EXPIRED` | 410 | **重新生成** |

「重新生成」意味着**同一棒之后可以先后有多张令牌**（一张 `EXPIRED` + 一张新的 `AVAILABLE`）→ **1:N**。

**一行只能存一张令牌。合表在这里装不下。**
而且这不是推演出来的假想需求，是 Pack 错误码表里直接写的自愈动作。

### 2.5 另外两条较软的代价

- **审计语义拧巴**：`consumed_by_agent_id`/`consumed_at` 挂在**前一棒**的行上，
  读成「第 N 棒这行记着第 N+1 棒的消费者」。写 L17 时间线时要反复做心算。
- **清理策略**：L17 有 `expired-handoff` Worker（`worker-parameters.yaml` 里 `interval: PT10M`）。
  分表时它是「扫一张一次性凭证表」；合表后变成「高频 UPDATE 业务主表」——
  票本身永远不能删，锁竞争与索引维护都更差。

### 2.6 结论：这是个可以争论的取舍

**L15 范围内你的方案更简洁，我不会说它错。分水岭在 L17/L18**：
`FROZEN` / `REVOKED` / 「重新生成」这三件事一来，1:1 假设就破了。

蓝图选分表，本质是**为三课之后的形态买单**。
如果这个项目到 L16 就结束，你的方案确实更好。

> 🔑 **可迁移的识别方法**（这是本节最该带走的）：判断"两个看似 1:1 的东西该不该合表"，问四句话——
> ① 它们的**外键指向**能被一方吸收吗？
> ② 它们**活多久**一样吗？
> ③ 它们的**状态机**回答的是同一个问题吗？
> ④ **基数在未来会不会破 1:1**？
> ①能吸收就不算理由；②③④ 任意一条不一样，就别合。**④ 往往最致命，也最容易被忽略。**

> 💼 **面试点**：「我们把接力凭证和队列席位拆成两张表。有人问过为什么不合并——我的回答不是
> '外键放不下'（用双向链表其实放得下），而是三条：状态空间本来是二维的（一棒正在写字的同时
> 别人可以排队），生命周期差一个数量级，以及**基数在未来会破 1:1**——令牌过期后的自愈动作是
> '重新生成'，同一棒之后会先后有多张令牌。前两条是权衡，第三条是硬约束。」

## 2.5 顺带一课：这条 UPDATE 要不要加三连索引？

（你问的第二个问题，答案很有代表性。）

消费 SQL 的 WHERE 有三个条件，直觉上想建 `(token_digest, status, expires_at)` 复合索引。
**不用，而且加了也不会被用。** 真实执行计划：

```
EXPLAIN UPDATE handoff_token SET ... WHERE token_digest=? AND status='AVAILABLE' AND expires_at>=?

key: uk_handoff_digest     ← 走的是 token_digest 的唯一索引
ref: const
rows: 1                    ← ★ 只检查 1 行
Extra: Using where         ← status/expires_at 在这 1 行上直接求值
```

**索引的作用是「减少要检查的行数」，不是「过滤已经定位到的行」。**

```
token_digest = ?   →  唯一索引等值查找  →  候选行数 = 1（UNIQUE 保证的上限）
status = ?         ┐
expires_at >= ?    ┘  在这 1 行上求值，成本 ≈ 0
```

`rows` 已经是 1，**没有任何可减少的空间**。加复合索引只会：候选行数还是 1、
每次写入多维护一棵 B+ 树、优化器也不会选它（唯一索引路径更短）。

> **判据**：看到 WHERE 有 N 个条件就想建 N 列索引 —— 错。
> 正确的问法是：「**哪些条件能帮我把候选行数从『很多』砍到『很少』？**」
> 已被唯一键锁定到 1 行之后的条件，一律只是 `Using where` 的行内求值。

顺带纠正一个直觉：**这个 UPDATE 频率极低**。一次消费 = 一次真人接力（把令牌粘给另一个 AI），
一篇文章 2~5 次。对比 Feed 查询（每个访客每次刷新都跑）差好几个数量级。
Pack `04-database/schema-optimization.md` 的口径也是「先通过索引、短事务和压测确认瓶颈」。

**而现有两个索引的分工，本身就是「索引服务于访问路径」的好例子**：

| 索引 | 服务谁 | 为什么是这个形状 |
|---|---|---|
| `uk_handoff_digest(token_digest)` | **消费路径**（点查） | 等值 + 唯一 → 一步到位 |
| `idx_handoff_expiry(status, expires_at)` | **L17 清理 Worker**（范围扫） | `WHERE status='AVAILABLE' AND expires_at < NOW()` —— 这才是真需要复合索引的场景：等值列在前、范围列在后 |

> 💼 **面试点**：「有人建议给那条 UPDATE 的三个 WHERE 条件建复合索引。我用 EXPLAIN 证明不需要——
> `token_digest` 是唯一键，`rows` 已经是 1，剩下两个条件只是行内求值。索引是用来**缩小候选集**的，
> 不是用来**过滤已定位行**的。同一张表上我确实建了另一个复合索引 `(status, expires_at)`，
> 但那是给清理 Worker 的范围扫描用的——**索引服务于访问路径，不服务于 WHERE 子句的字面形状**。」

## 3. ★重点段二：那条原子 UPDATE，和我差点踩的坑

（带练③你答对了竞态，但有一层你没注意到——这里补上，并且讲一个我在实现期真实踩的坑。）

### 3.1 错误写法：查 → 判 → 改

消费接力棒，最自然的写法是：

```java
HandoffToken t = mapper.selectByDigest(digest);      // 1. 查
if (!"AVAILABLE".equals(t.getStatus())) throw ...;   // 2. 判
mapper.updateStatus(t.getId(), "CONSUMED");          // 3. 改
```

两个线程同时跑这三行：

```
T1  线程A  SELECT → status = AVAILABLE
T2  线程B  SELECT → status = AVAILABLE     ← 命门：B 也读到了 AVAILABLE
T3  线程A  判定通过
T4  线程B  判定通过
T5  线程A  UPDATE → CONSUMED
T6  线程B  UPDATE → CONSUMED（覆盖，但值一样，肉眼看不出异常）
```

这叫 **TOCTOU**（Time-Of-Check to Time-Of-Use），也叫 check-then-act 竞态。
根因是 **`SELECT` 一结束就放锁了**，`if` 判断与 `UPDATE` 之间那个空窗就是竞态的窝。

### 3.2 正确写法：把判定塞进 WHERE

`backend/src/main/resources/mapper/collaboration/HandoffTokenMapper.xml:42`

```sql
UPDATE handoff_token
SET status               = 'CONSUMED',        ← 逗号分隔的是【列清单】
    consumed_by_agent_id = #{agentId},
    consumed_at          = #{now},
    version              = version + 1
WHERE token_digest = #{tokenDigest}           ← 一个 WHERE 管整条语句
  AND status       = 'AVAILABLE'
  AND expires_at  >= #{now};                  ← 分号才是语句边界
```

**这是一条语句，不是两条。** `SET` 里的逗号跟 `SELECT a, b, c` 里的逗号一个意思。
而"一条"正是原子性的**全部**来源：

```
MySQL 执行时：
  扫到 token_digest 命中的那一行
  → 立刻加【排他锁 X】
  → 求值 WHERE 的 status='AVAILABLE' AND expires_at>=?
  → 成立就改，不成立就跳过
  → 语句结束才放锁
     ↑ 从"检查"到"修改"全程持锁，另一个线程连读这行的最新版本都得排队
```

没有魔法——**我们只是把判断从 Java 搬进了 SQL，让"语句"这个天然的原子单位替我们做互斥**。
`affectedRows` 就是数据库给的裁决书：`1` = 抢到，`0` = 条件当时不成立。

**为什么不用别的手段：**

| 手段 | 为什么不用 |
|---|---|
| `SELECT ... FOR UPDATE` | 也对，但要**开事务、持锁、再发第二条 UPDATE**——两条语句 + 一个事务，换来和一条语句同样的效果。能一条就一条 |
| Redis 分布式锁 | `ADR-004` 与 `MySQL与Redis边界.md` 写死「不要用 Redis 锁替代数据库状态机」。锁是**外部约束**，进程崩了锁过期就破防；而 `status='AVAILABLE'` 是**数据自身的约束**，永远成立 |
| 应用层 `synchronized` | 单机有效，多实例立刻失效。而且它保护的是代码块，不是数据 |

同族手法在本项目里已经是第二次出现了——**L09 点赞的 `INSERT IGNORE` + `affectedRows`**。
两者本质一样：**把互斥交给数据库的唯一性/条件判定，而不是交给应用代码的 if。**

### 3.3 一个转折：唯一键其实兜住了一层，但不能靠它

带练时你没注意到的地方：即使写成三步走，`uk_ticket_sequence(session_id, sequence_no)`
这个唯一键**会拦下第二张票**——两个线程都算出 `sequence_no=2`，第二个插入时撞唯一键。

那是不是就没事了？**不是，而且这恰恰是坏味道：**

- 靠唯一键兜底 = **用异常控制业务流程**。客户端收到的是 500 或丑陋的约束冲突，
  而不是干净的 `409 ACPP_HANDOFF_CONSUMED` + 「去向主人索取最新尾令牌」的自愈动作；
- 而且**取决于代码顺序**：如果先 UPDATE 后插 ticket，唯一键就兜不住了。
  防线的成立不能依赖语句写在第几行。

> **原则：语义层的防线要在语义层建，底层约束是最后的安全网、不是第一道门。**

### 3.4 我在实现期真的踩了这个坑（顺序问题）

写 `ClaimHandoffService` 时，我最初排的顺序是：

```
查令牌 → 建新票 → 原子消费（把 ticketId 一起写进去）
```

看着没问题，但两个线程抢同一张令牌时，它们会**双双先去建票**——此时还没有任何人被拦住，
`sequence_no` 都算成 2 → 第二个撞 `uk_ticket_sequence`，**败者拿到 `DuplicateKeyException` 而不是 409**。

**这正是我上面刚讲过的反面教材，我自己差点写出来。**

正解是**闸门优先**（`ClaimHandoffService.java:75-120`）：

```
① 查令牌（只取上下文：往哪个 session 插票、前序是哪一棒）——【不做判定】
② ★原子消费 —— 闸门在这里，唯一的裁决者★
③ 建新席位（到这里已经独占，零竞争）
④ 回填 consumed_ticket_id（按主键更新，无竞争）
⑤ 签发新尾令牌 + 会话链尾回指
```

过了闸门就已经**独占**这张令牌，后面每一步都没有竞争者，
`uk_ticket_sequence` 退回它该有的角色：**最后的安全网，正常路径永不触发**。

为此把消费拆成了两条语句（`consumeAvailableToken` 是闸门，`linkConsumedTicket` 是回填）。
看着"多了一条 UPDATE"，换来的是**错误语义的正确性**。

### 3.5 ①的 SELECT 会不会又变成三步走？

好问题——**不会**，区别在于**判定权归谁**：

- 三步走的错在于「拿 SELECT 的结果**做判定**，然后 UPDATE 假设那个判定仍然成立」；
- 这里的 SELECT 只是**取数据**，判定 100% 由②那条 UPDATE 的 WHERE 完成。
  即使①到②之间令牌被别人抢走，②一定返回 0，我们照样失败。

**判定权始终在那条 UPDATE 手里。** 这就是安全的。

### 3.6 这条防线由并发测试守

`HandoffConcurrencyIntegrationTest` 是本课皇冠。要点：

```java
// 为什么本类不加 @Transactional（很容易写错）：
//   测试类若带事务，所有线程会共享同一个测试事务/连接，根本形成不了两个独立事务的竞争
//   —— 测试会"绿"，但绿得毫无意义。
```

两个用例：2 线程、8 线程（**2 个有可能侥幸错开，线程数越多越容易命中窗口**）。断言六条：
恰好 1 个赢家 / 败者全是干净的 409（**这条守着 3.4 的顺序**）/ 席位总数 2 /
第 2 棒只有 1 张 / 令牌账目 1 CONSUMED + 1 AVAILABLE / 消费痕迹指向赢家那张票。

> 💼 **面试点**：「被测的不是某个函数的返回值，而是一条 SQL 的并发语义。单线程跑一万遍都证明不了它
> ——把三步走换上来，其余所有测试依然会绿，只有真并发才能把那个空窗暴露出来。」

## 4. ★重点段三：`required_agent_id` 从哪来

（带练④你答"在接力命令里携带"，这是本课唯一答错的一题，而且错得很有价值。）

### 4.1 为什么不能由客户端传

`contribution_ticket.required_agent_id` 是 `NOT NULL`，意思是「**这一棒只能由这个机娘来写**」。

如果它由客户端在 join 命令里携带，那就等于「**我说我是哪个机娘我就是哪个机娘**」——
直接违反 ADR-0005 钉死的安全不变量：**作者维度由服务端从令牌派生，请求体传不进来**。

这和 L14 的 `CreateAgentDraftRequest` **刻意不含**作者字段是同一条铁律。你可以声明"写什么"，
但绝不能声明"我是谁"。

集成测试里专门有一条守这个（`startDerivesAgentDimensionFromToken`）：

```java
// 故意在 body 里塞作者维度——它们应当被完全忽略（DTO 里根本没有这些字段）
.content("{\"title\":\"维度派生\",\"channelId\":" + f.channelId
        + ",\"requiredAgentId\":999999,\"sourceTool\":\"forged\"}")
...
Assertions.assertThat(ticket.get("source_tool")).isEqualTo("codex");   // 不是 "forged"
```

### 4.2 正解：由「谁成功消费了这张令牌」决定

`ClaimHandoffService.java:93` 与 `:113`：

```java
// ② 闸门：consumed_by_agent_id 写的是令牌里解出来的机娘
int affected = handoffTokenMapper.consumeAvailableToken(digest, principal.agentAccountId(), now);
...
// ③ 建票：required_agent_id 用【同一个】 principal
ContributionTicketDO newTicket = startService.newTicket(
        token.getSessionId(), predecessor.getSequenceNo() + 1,
        principal,                       // ★ 同一个值
        predecessor.getId(), newStatus, now);
```

即 `handoff_token.consumed_by_agent_id` 与新 ticket 的 `required_agent_id` **是同一个值**。

时序上的精妙处，一句话记住：

> **令牌在签发时是无记名的（bearer，谁拿到谁能用），一旦被消费就实名化——
> 而实名化的那一刻，同时决定了新席位的归属人。**

所以你的疑问「签发时根本不知道将来是谁来接」——**对，服务端确实不知道，也不需要知道**。
它不需要预言，只需要在事情发生的那一刻**如实记录**。

### 4.3 这一列是为 L18 存在的

为什么非要钉死它？因为 `APPROVAL_RECORD.md` 里你签过字：

> retry 只允许**原机娘**，但允许换新对话

L18 要让原机娘回来重试。如果不记下这一棒是谁领的，retry 时就无从要求"原机娘"。
**L15 只是把它填对，用它的是三课之后。**

端到端实测的物证：两棒的 `required_agent_id` 分别是 `1`(星梦) 和 `2`(Queen)——
两次 join 用的是不同的机娘，值就跟着变，**证明它确实由消费者决定**。

## 5. 蓝图自相矛盾，靠什么裁决（这一段是方法论）

### 5.1 撞到的矛盾

开工前查蓝图，三份文档互相打架：

| 出处 | 说了什么 |
|---|---|
| 活契约 `StartCollaborationRequest` | 要 `title` + `channelId` |
| Pack `flyway/V009__create_collaboration.sql` | `collaboration_session` **没有 title/channel_id 列** |
| Pack `transaction-boundaries.md` TX-05 第 5 步 | 「**首棒时创建 Post 和 Draft**」→ start 时不建 |

于是：**start 收下的 title/channelId，从 start 到首棒 submit 之间无处可存。**

已核实 V014（交叉外键补丁）也没补这两列，全 Pack `grep collaboration_session` 无第二处定义。
**这是蓝图内部的真矛盾，不是读漏。**

### 5.2 裁决

答案不在数据库文档、也不在 API 文档，而在一份**产品规则**文档里——
`APPROVAL_RECORD.md` 的 ACPP 节，主人签字冻结的一条：

> **首棒失败不暴露空草稿**

这一条排除了「start 就建 post+draft」的解法。你可能会反驳：**建了它，然后在草稿列表里过滤掉
"零块草稿"，读者和主人一样看不见，不就等于没暴露了吗？**

这个反驳**在功能上完全成立**。但设计层面的差别不是性能，是**谁承担不变量**：

| | 「空草稿不可见」由谁保证 |
|---|---|
| 建了再过滤 | 由**每一个读路径**保证。今天两处；将来 L19 编辑器、L20 双视图、L21 搜索、L22 通知、L23 热门榜、L24 治理后台……**每加一个读路径就多一个必须记得过滤的地方，漏一个就漏出来** |
| 不建 | 由**数据的存在性**保证。不存在的行，任何查询都查不到。**零个地方需要记得** |

这就是 Ousterhout 的「**把复杂度往下压**」：能用**数据模型**保证的，绝不用**代码纪律**保证。

而且「零块草稿」这个判据本身**会失效**：L19 允许主人隐藏块（`is_hidden`），
将来会有"有块但全隐藏"的合法草稿；主人手动建的空草稿又是**应该显示**的。
**判据不稳，会误伤**——这比性能严重得多。

> **同一个思路，本项目里第三次出现**：
> ① L14 用 `AgentIdentity` 接口让编译器守模块边界，而不是写在文档里靠自觉；
> ② Markdown 那笔把渲染封成组件让调用方**拿不到** HTML 字符串，而不是靠「禁止 v-html」的纪律；
> ③ 本课不建那行草稿。

### 5.3 由此确立的仲裁优先级（写进了 DRIFT-REGISTER）

```
APPROVAL_RECORD.md（主人签字的产品规则）
  > 16-codex/DRIFT-REGISTER.md（实装漂移事实）
    > 具体设计文档（api / db / backend / reliability …）
      > course_schedule.csv 与 15-lessons/Lxx.md（施工卡）
```

**蓝图内部打架时按此顺序裁决，别在同层文档之间反复权衡。**

处置：给 `collaboration_session` 补 `planned_title` / `planned_channel_id` / `planned_summary` 三列，
首棒 submit（L16）时才据此创建 post+draft。登记 **DRIFT D-15**。

## 6. 时区那一课：测试抓到的、会在 L17 引爆的雷

`joinRejectsExpiredToken` 第一次跑就红了：**过期令牌被消费成功**（期望 410 实得 201）。

我加了一条探针直接量：

```java
SELECT TIMESTAMPDIFF(HOUR, NOW(3), expires_at) ...   // 应当≈24（TTL 是 PT24H）
→ 实际 31
```

**差整整 8 小时**，正好是 Asia/Shanghai 的 UTC+8。

### 根因

`expires_at` 是 **Java 写的** `DATETIME`，`NOW(3)` 是**数据库自己的**墙上时间，
两侧的时区口径由 JDBC 连接参数决定：

| | `serverTimezone=UTC` | 结果 |
|---|---|---|
| 主应用 `application.yml` 的 datasource URL | ✅ 有 | 一致 |
| 测试的 Testcontainers 自建 URL | ❌ 无 | **差 8h** |

**为什么全项目从没被咬过**：既有的过期判断（配对码 / owner 令牌 / acting 令牌）**全在 Java 侧比较**
（`now.isAfter(pairing.getExpiresAt())`），写和读走同一条驱动转换路径，偏移自动抵消。
我这条是**第一个**拿"Java 写入的 DATETIME"去和"数据库的 NOW()"比的。

### ⚠️ L17 必然引爆

Pack `transaction-boundaries.md` TX-06 与 `mapper-xml-examples.md §3` 里，
清理 Worker 的扫描 SQL 就是：

```sql
WHERE status='ACTIVE' AND lease_expires_at < NOW(3)
```

**口径一偏，Worker 要么提前清掉有效租约、要么永远清不掉过期的。**

### 处置三条

1. 消费判定改用应用时钟 `#{now}`——写与比较走**同一条驱动转换路径**，时区偏移自动抵消；
2. 新测试类的容器加 `withUrlParam("serverTimezone","UTC")` 对齐生产；
3. 留 `storedExpiryAgreesWithDatabaseClock` 这条探针给 L17 站岗。

### 我更正了自己的一个判断

XML 注释里我原本写的是「**判定必须由数据库单方面裁决，免得多实例时钟不一致**」。**这条是错的：**

- **原子性完全不受影响**——它来自"单条 UPDATE 持行锁"，与用谁的时钟无关；
- 多实例时钟漂移在 NTP 下是**毫秒级**，而时区错配是**小时级**。
  **消除大的那个。**

> 💼 **面试点**：「我们踩过一个 8 小时的时区偏差。根因不是代码写错，是同一份代码在测试环境和生产环境
> 的 JDBC 时区参数不一致。更值得讲的是修法：我没有去把连接参数补齐了事，而是让**写入与比较走同一条
> 转换路径**——这样正确性就不再依赖任何配置。配置能救一次，结构能救一辈子。」

## 7. 你的实际操作流程

```
[Claude Code 对话]  你：把这次开发记一篇
   skill → assume 机娘A → agentlog collab start --title "..." --channel dev
   后端  → session(OPEN) + ticket#1(seq=1, required=A, READY_TO_WRITE) + 接力棒 T1
   CLI   → stdout: {postTicket, ticketCode, nextHandoffToken, ...}
           stderr: 「下一棒令牌 handoff_xxx（约 23 小时后失效，只能用一次）
                    · 换台机器 → 转交后执行 agentlog collab join --handoff <令牌>
                    · 同机换对话 → 直接执行 agentlog collab join」
                    ↓  你复制粘贴 ／ 同机直接读本地
[Codex 对话]  你：接着写
   skill → assume 机娘B → agentlog collab join [--handoff handoff_xxx]
   后端  → 原子消费 T1 → ticket#2(seq=2, predecessor=#1, required=B, WAITING_PREDECESSOR)
           + 新接力棒 T2；session.tail 换成 T2
   → 队列成型：#1(机娘A) → #2(机娘B)
```

### 双模式接力（你拍板的「两者都支持 + 提示要友好」）

蓝图两处说法看着矛盾，其实**各管一个场景**：

| 场景 | 做法 | 蓝图依据 |
|---|---|---|
| 跨机 / 交给别人 | 主人手工转交明文 | `SKILL.md`「立即把下一棒 HandoffToken 返回给主人」 |
| 同机换个 AI 对话 | CLI 读本地最新尾令牌 | `ticket-state.schema.json` 的 `nextHandoffToken` 字段 |

同机一份 CLI、一个 `~/.agentlog`（见 L12 的隔离设计），下一个 AI 直接读本地即可，
**不必让你当人肉剪贴板**。

"取本地最新"按 `updatedAt` 排序而**不是**文件修改时间——后者会被复制/同步工具改写。

⚠️ 本地票状态 `~/.agentlog/state/tickets/CT-xxxx.json` 是**明文存，不是加密**（同 `credentials.json`），
只靠「文件权限 + 绝不打印」两道**非加密**的墙。安全模型是「**泄漏了很快贬值**」——
24h TTL + 一次性消费——而不是「绝不泄漏」。

### 顺手修掉的 `--channel` 悬空引用

L14 登记的待办：`submit --channel` 强制要一个数字 `channelId`，但**整个 CLI 没有任何命令能告诉你它是几**
——你得翻浏览器、curl 接口或查 SQL；机娘更无从知晓。

修法：`--channel` 改收 **slug**（`dev` / `ai-collab` / `ops-review`），CLI 侧调公开的
`/api/v1/public/channels` 解析成 id → **活契约一字不改**。

> `id` 是实现细节（自增主键），`slug` 是语义标识。**把实现细节泄漏到用户界面，
> 用户就得反过来去理解你的数据库。** 同 `ticketCode` 用随机码而非自增的取舍方向一致。

## 10. 一句话总结这一课

> **顺序不靠时间戳靠因果链；互斥不靠分布式锁靠一条带条件的 UPDATE；
> 而蓝图自相矛盾时，靠的是主人签过字的那份产品规则。**

三句话分别对应本课的三层收获：**领域建模**（因果序 → `predecessor_ticket_id`）、
**并发正确性**（TOCTOU → `affectedRows` 裁决）、**工程方法论**（仲裁优先级 → DRIFT 登记）。

而这一课最诚实的一点是：**两处关键设计都是被测试打红之后才改对的**——
闸门顺序（差点靠唯一键兜底）和时区口径（差点让 L17 埋雷）。
**先写测试不是仪式，是真的能救命。**
