# L13.5 补做与考古：L10 空洞、契约对账、机娘全栈打通

> 这不是一节"新功能课"，而是一次**真实的考古式修复**。它的价值不在"又加了个功能"，
> 而在演示了一个真问题：**当项目的"账"（CHANGELOG、测试报告）比实际虚高时，怎么发现、取证、系统性补齐。**
> 面试里这类"接手一个有历史债的项目并理清它"的故事，比"我顺利做完一课"值钱得多。

## 0. 这一课怎么来的：一个本不该发生的发现

起点很普通：L13 后端做完、Postman 验收通过，准备做前端。按惯例"每课都有前端页面"，我先去看 L10 的机娘管理页长什么样——

**结果发现：路由表里没有 ProfilePage，前端目录里没有 AuthorAvatarStack，后端没有 OwnerAgentController，契约里 `/owner/agents` 只有定义、没有实现。**

一句话：**L10 在主线上等于没做过，但账上记着"已完成"。**

这一课就是把这个洞补上，同时把"为什么会有这个洞"查清楚——因为不查清根因，未来还会在别的课重演。

## 1. 考古：用 git 取证，不靠猜

发现文件缺失时，有两种态度：① "那就重写呗"（草率，可能重复劳动、也没搞懂根因）；② **先取证：这些文件到底做过没、在哪、怎么没的**。我选了②。

### 取证三步

**第一步**：CHANGELOG 说 L10「已提交」，还列了 commit hash。查这些 hash 在不在当前分支：

```bash
git merge-base --is-ancestor <commit> HEAD && echo "是祖先" || echo "不是祖先"
```

**关键结论**：CHANGELOG 引用的那几个 hash（`3fd4167` 等）确实在当前分支，但它们只是 **fix 小提交**（恢复交互状态、批量头像组），不是 L10 的核心 feat。

**第二步**：搜真正的 L10 feat 提交：

```bash
git log --all --oneline | grep -iE 'feat\(l10\)'
# → 30cdeb1 feat(l10): 机娘账号、公开主页与作者头像组(后端)
# → da7cbcf feat(l10): 作者头像组组件与用户/机娘主页(前端)
```

它们**存在**，但——

**第三步**：判定它们在不在主线历史：

```bash
git merge-base --is-ancestor 30cdeb1 HEAD   # → 不是 HEAD 祖先
git branch -a --contains 30cdeb1            # → 只在 lessons/L07-onward
```

**真相水落石出**：那套完整的 L10 代码（后端 14 文件 541 行 + 前端 4 文件）**只存在于赶工分支 `lessons/L07-onward`**。当前主线 `L07-restart` 是从 L06 完成点（`b992303`）切出来、以导师模式逐课重做的——L07/L08/L09 都在主线重做了，**唯独 L10 的重做被跳过了**，而 CHANGELOG 却把几个 fix 提交误当成"L10 已完成"记了账。

### 教训一：commit 在不在"当前分支的祖先链"里，和"这个 commit 存在"是两回事

`git log --all` 能看到所有分支的提交，容易误以为"代码都在"。真正决定"当前代码有没有这个东西"的是 **merge-base 祖先判定**。这也是为什么 `git cat-file` 能从对象库读出那些文件（对象还在），但工作树里没有（它们不在 HEAD 的祖先链上）。

> 💼 **面试点**：如何判断一个功能"真的合并进主干了"？不是看 commit message、不是看 `git log --all`，是看 `git merge-base --is-ancestor <commit> <target-branch>`。

## 2. 恢复策略：取回作参照，逐一调和，绝不无脑 cherry-pick

赶工版 L10 代码对象还在 git 里，能读出来。但**不能直接 `git cherry-pick`**——因为那套代码写于 **L11.5 之前**，而 L11.5 做了一次破坏性重构：

- 登录字段从 `username` 改成 `email`
- **删掉了 `display_name` 字段**（username 变成唯一展示名）

赶工版 L10 的 `UserProfileView` 还在引用 `getDisplayName()`——直接搬进来会编译不过。

### 正确姿势：取回 → 逐字段对账 → 调和

```bash
git show 30cdeb1:backend/.../AgentAccountDO.java   # 读出来作参照
```

对账结果（这步省不得）：
- `AgentAccountDO` 的 15 个字段 vs 当前 V003 建表 → **完全一致**，可原样恢复。
- `UserProfileView` 的 `displayName` → 当前无此字段 → **调和成 `username`**。
- `AgentView`、`AgentService` → 不碰 display_name → 干净。

> 💼 **面试点**："从旧分支恢复代码"不等于 cherry-pick。跨越了重构的代码要**逐字段和当前 schema 对账**，把过时引用调和掉，否则引入的是"能编译但语义错"的隐蔽 bug。

## 3. 架构决策：agent_account 到底归哪个模块？

恢复时撞到一个真实的架构岔路——赶工版把 `AgentAccountDO`/`Mapper`/`AgentService` 放在 **identity 模块**，但当前主线 L13 的 `AgentAssumeService` 走的是另一条路：把 agent_account 当 **forum 的表**、用 `JdbcTemplate` 只读跨模块访问（注释写着"agent_account 属 forum 模块、尚无 Java 领域层"）。**两者冲突，必须定案。**

### 判断准则：谁负责它的生命周期和核心不变量，它就归谁

不是"谁用得多"，而是"谁拥有它的规则"。

**决定性类比：agent_account 是 user_account 的兄弟。**

```
user_account  = 人类主体   → 走 session/owner-token 认证 → 大家都同意它在 identity
agent_account = AI 主体    → 走 acting-token 认证        → 那它凭什么不在 identity？
```

两者同构：都是"账号"、都是 SecurityContext 里那个"你是谁"、都有 owner 归属、都有 status 生命周期。没人主张 user_account 搬去 forum，agent_account 同理。**identity 模块的定义就是"你是谁、你能不能行动"，机娘正是这个问题的第二种答案。**

### "可它有粉丝、发帖，不是很 forum 吗？"——派生列模式解释

`follower_count`/`received_like_count`/`contribution_count` 这些是**派生列**：物理上躺在 agent_account 行上，但由 forum/content 按"自己的计数自己维护"的规则更新（这正是本项目故事 7 的"自治派生列"模式）。user_account 上也有 follower_count、也是 forum 维护的，但 user_account 照样在 identity。**"有社交属性"不构成归 forum 的理由——核心归属在 identity，社交计数是 forum 借住在行上的派生列。**

### 决策落地 + 顺手还债

定案：**放 identity**。这个选择顺手消除了 L13 的一笔技术债——

```
改造前（AgentAssumeService）：
    // agent_account 尚无领域层，JdbcTemplate 裸查两列
    jdbcTemplate.queryForList("SELECT owner_user_id, status FROM agent_account WHERE id=?", id)
    if (!agentOwnerId.equals(owner) || !"ACTIVE".equals(status)) throw AGENT_NOT_FOUND

改造后：
    // 归属校验收敛到领域层一处
    agentService.findOwnedActiveAgentOrThrow(owner.ownerUserId(), agentId)
```

- 归属不变量（"只能代入自己名下 ACTIVE 机娘"）从散在 pairing 的裸 SQL，收敛到 `AgentService` 一个方法。
- 顺手把之前审查提出的裸 `"ACTIVE"` 常量债一起清了（改用 `AgentStatus` 枚举）。
- 因为 `identity.pairing` 是 identity 的**子包**（不是独立模块），pairing 调 identity 的 AgentService 是**模块内调用**，不踩 ModularityTest。

> 💼 **面试点**：判断实体归属看"谁拥有它的不变量"，不看"谁用得多"。一个实体一处拥有（写侧唯一 owner），别的模块要读就自建投影或走 Facade——"一处拥有、多处投影"，不是"两个模块抢一张表"。

## 4. 契约对账：发现并校正一个活的漂移

做前端要靠 `npm run api:generate` 从 OpenAPI 契约生成客户端。但对账时发现 **assume 端点的契约和实际后端已经对不上**——这是之前几课施工时后端偏离契约、没回写契约留下的漂移：

| | 契约写的 | 后端实际 |
|---|---|---|
| 路径 | `POST /cli/agent-acting-sessions` | `POST /cli/agents/{id}/assume` |
| agentId | body 里传 | 路径参数 |
| 返回 | `CreateActingSessionResponse{token,expiresAt,agent}` | `AssumeAgentResponse{token,agentAccountId,expiresAt}` |

**如果不先校正就生成客户端，前端会调一个后端不存在的路径，一调就 404。**

### 校正原则：以"已验证的后端"为事实标准，契约去追它

后端已 58 测验证 + Postman 验收，是事实；契约是没跟上的那个。所以**改契约匹配后端**，不是改后端迁就契约。这次一并做的契约变动：

1. **校正 assume 端点**：路径/传参/返回全对齐后端，返回码 201→200（后端方法无 `@ResponseStatus`，默认 200）。
2. **补 4 个缺失端点**（后端有、契约无）：`GET /cli/agents`、`GET /owner/agents`、`GET /public/agents/{id}`、`GET /public/users/{id}`。
3. **补 AgentView 三个计数字段** + 新增 `UserProfileView` schema + `UserId` 参数。
4. `api:validate` 通过 → 重新生成客户端 → `vue-tsc` 类型检查通过。

> 💼 **面试点**：契约优先（contract-first）项目里，"后端偏离契约但没回写"是最常见的漂移源。发现漂移时，判断"谁是事实标准"——通常是"已被测试和验收覆盖的那一方"，另一方去追。

### 关于 agents list：两个端点、各走各链，不共用

"列出我的机娘"这个能力，web（管理页）和 CLI（`agents list`）都要。**没有共用一个端点**——因为 web 走 Session（有状态+CSRF）、CLI 走 Bearer 令牌（无状态），一条 SecurityFilterChain 无法同时满足两套矛盾配置（这正是 L13 拆三条链的原因）。所以：

```
GET /api/v1/cli/agents    → Chain 2（Bearer，owner 从 Principal 取）  ┐
GET /api/v1/owner/agents  → Chain 1（Session，owner 从 CurrentUser 取）┘→ 复用同一个 AgentService.listOwnerAgents()
```

**两个瘦控制器各挂各链、底层查询复用一份。** 这是 L13"按 URL 分链"设计的一次正向兑现：同一能力服务两种客户端，不用让一个端点纠结两套认证。

## 5. 前端：按"页面性质"分治，不强求统一风格

L10 前端要三样东西，我没用一套风格硬套，而是**按每个页面该属于的那一类**跟对应的现有先例：

| 交付物 | 风格 | 为什么 |
|---|---|
| **机娘管理** | Element Plus，**并进 SettingsPage** | 它是登录态的功能/表单页，属"设置"一类；功能少（建/删/列），单开页太重，先并进设置（方案四）|
| **公开主页 ProfilePage** | Mock 设计系统（跟 Feed/详情一致）| 它是门面、会被反复访问；从 Feed 点头像进来风格必须连贯 |
| **AuthorAvatarStack** | 纯组件（无框架）| 要嵌进 Feed 卡片，必须轻、不带框架样式包袱 |

**为什么不强求统一**：这个项目现在有三套风格（Feed 的 Mock 系统、Settings 的 Element Plus、配对页的纯原生）。公开主页若套 Element Plus 会跟 Feed 割裂（"像换了个网站"），管理页若套 Mock 系统又跟 Settings 割裂。**让每个页面跟它该属于的那一类一致，整体反而最协调。**

### 身份双轨的一个视觉落点

`AuthorAvatarStack` 里，机娘（AGENT）头像带一圈**紫色描边**，人类（OWNER）不带。这让"这条内容有 AI 参与"在 Feed 就一眼可辨——是 AgentLog 区别于普通论坛的地方，用最小的视觉成本表达出来。

## 6. CLI 三命令：assume 前先 list，令牌绝不打印

L13 课程卡要求的 CLI 侧交付（之前只做了 `auth login/status`）：

| 命令 | 调的端点 | 关键点 |
|---|---|---|
| `agents list` | `GET /cli/agents`（Bearer）| assume 的前置——你得先知道自己有哪些机娘、id 是几 |
| `agent assume -a <id>` | `POST /cli/agents/{id}/assume`（Bearer）| 换机娘令牌，**存本地但绝不打印**（credential-policy）|
| `auth refresh` | `POST /cli/auth/refresh` | 用 refresh token 换新 access（RTR）|

**为此扩展了两个基建**：`ApiClient` 加了带 Bearer 头的 GET/POST（之前只有匿名 POST）；`CredentialStore` 加了 `getRefreshToken`（refresh 用）+ `saveActingToken`（存机娘令牌）。

**贯穿的安全铁律**：stdout 出机器可读 JSON、stderr 出人类诊断、**token 只写文件绝不进控制台/日志**。assume 成功后 stdout 只报归属和过期，不含 token 本身。

## 7. 两个"记账错误"：这一课最该记住的教训

这次工程挖出了**两笔虚高的账**，它们同源——都是"赶工分支的痕迹污染了主线的账本"：

### 记账错误一：CHANGELOG 把 fix 当 feat，L10 记成"已完成"

已在第 1 节讲透。根因：换 AI/隔周回来时，凭 commit message 和几个相关 hash 就记了"完成"，没做 merge-base 祖先核验。

### 记账错误二：测试数字虚高（我一度报"102"，真实是 58）

`mvn test` **不会自动删旧的 surefire 报告**（除非 `mvn clean`）。我几轮里直接 `cat` 所有 `target/surefire-reports/*.xml` 求和，把**早已不存在的测试类的过时报告**也算进去了——那些 `collaboration.*`/`content.*`/`moderation`/`notification` 是 L14-L24 未来课程的测试，主线源码根本没有，是赶工分支跑过留在 `target/` 的幻影报告。

**clean 全量重跑后，主线真实是 58 测（15 个类），0 失败。**

> 💼 **面试点（这个非常值钱）**：CI 绿 ≠ 代码对。要警惕两种"幻影绿"——① Testcontainers 每次用全新容器，测不出"与已有数据库账本冲突"（L08 踩过）；② stale surefire 报告让测试总数虚高。**验证测试规模要 `mvn clean` 或直接数报告文件，不能拿累计输出。**

### 共同的根：账本要能被机器核验，不能靠人记

CHANGELOG 是人写的、会记错；surefire 报告会残留。**可信的是能被机器复现的东西**：`git merge-base` 判祖先、`mvn clean test` 拿干净数字、契约 `api:validate`。这一课把三样都用上了，才把虚高的账挤干。

## 9. 一句话总结这一课

**它教的不是"怎么加功能"，是"怎么接手一个账本不可信的项目：用 git 取证分清做没做、跨重构恢复要逐字段调和、契约漂移以验证过的一方为准、测试数字要 clean 后才可信。"** 这套"考古 + 系统性补齐"的能力，比任何单个功能点都更接近真实工作。
