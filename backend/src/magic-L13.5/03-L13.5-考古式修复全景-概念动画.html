L13.5 · 一次考古式修复

从「上过课等于没上课」到系统补齐 —— 一次真实的债务侦查与偿还
缘起 破案时间线 架构决策 契约对账 前端三方案 两个记账教训 面试怎么讲

缘起 本来只想补 L13 前端，却挖出一个空洞

这一节不是讲一个新功能，而是复盘一次真实的「维护型工程」——它比顺利做完一课更能教会你东西。

L13（三条认证链 + 机娘 assume）后端做完、测绿、Postman 验收通过。按交付顺序，下一步是前端。可当我去查「L13 的前端该怎么做」时，一路顺藤摸瓜，挖出了一连串问题：

  • L13 设计上根本没有 web 前端（它是纯 CLI + 令牌课，"前端"就是 CLI 命令）；
  • 要做的"机娘管理页"其实属于 L10——而 L10 在主线上从没真正做过，只是账记成做了；
  • assume 端点的契约和实际后端早已漂移（路径/传参/返回全不同）；
  • 我之前报的测试数字 102 是被污染的幻影，真实只有 58。
一句话

这一课教的是：当"文档说做了、代码却没有"时，怎么用证据破案、怎么安全地把债还上、怎么防止再记错账。这是真实工作里最常见、也最考验人的一类活。

1 破案时间线：L10 到底发生了什么

点「下一步」逐步推进，看我怎么从一句怀疑走到铁证。

1

疑点：路由表里没有 ProfilePage

设计文档（Master Pack）说 L10 要交付 ProfilePage.vue 和 AuthorAvatarStack.vue，但前端 router/index.ts 里根本没有主页路由。

web/src/pages/ 只有 Feed/Detail/Login/Settings/DevicePairing —— 无 ProfilePage
2

但 CHANGELOG 说 L10「已提交」，还列了 commit

账面上 L10 是完成的。文档与代码矛盾——必须用 git 取证，不能猜。

git log 里确有：feat(l10) 机娘账号后端 / feat(l10) 主页前端
3

关键取证：那两个 commit 不是当前分支的祖先

用 git merge-base --is-ancestor 判定——L10 的 feat commit 只存在于赶工分支 lessons/L07-onward，从没进过主线 L07-restart。

❌ 30cdeb1 不是 HEAD 祖先；只被 lessons/L07-onward 包含
4

真相：主线从 L06 末切出重做，L10 的重做被跳过了

L07/L08/L09 都在主线以导师模式重做了，唯独 L10 漏了。CHANGELOG 引用的那几个 hash 其实只是 fix 小提交，被误当成"L10 已完成"的证据。

分叉点 = b992303（L06 完成点）
✓

好消息：文件完整躺在 git 对象里，可恢复

赶工分支的 commit 对象还在，git cat-file 能读出源码。所以不用从零重写——有一份当年可用的实现作参照，只需跟当前代码调和。

git show 30cdeb1:.../OwnerAgentController.java ✅ 可读
方法论

破案靠的不是记忆，是可复现的证据链：文件系统看现状 → git log 看历史 → merge-base 判血缘 → cat-file 验对象还在。每一步都留下别人能复算的命令。「文档说了不算，git 说了算」。

2 架构决策：agent_account 该归哪个模块？

恢复 L10 要引入机娘的领域层（DO/Mapper/Service），但它放 identity 还是 forum，是个真问题。点卡片看推理。

🧬
判断准则
谁负责它的生命周期和核心不变量，它就归谁——不是"谁用得多"。
机娘能被认证、能行动、有 owner、有 status（ACTIVE/DISABLED/DELETED 生命周期）——它是一个 principal（可行动的主体）。
👥
决定性类比
agent_account 是 user_account 的兄弟。
人类账号走 session 认证、机娘走 acting-token 认证；两者都有 owner、status、社交计数。没人会把 user_account 搬去 forum，机娘同理 → 归 identity。
📊
"它有粉丝，很 forum 啊？"
社交计数是 forum 借住的"派生列"，不是归属依据。
follower_count / received_like_count 物理上在 agent_account 行上，但由 forum 按"自己的计数自己维护"更新——和 user_account 上的计数一模一样。核心归 identity，计数是 forum 的派生列。
🎁
顺手还的一笔债
assume 从"裸 SQL"升级成调领域层。
L13 的 assume 之前用 JdbcTemplate 裸查 agent_account（因为"没领域层"）。现在领域层补上了，assume 改调 AgentService.findOwnedActiveAgentOrThrow——把"只能代入自己名下 ACTIVE 机娘"这条不变量收敛到一处。
一处拥有，多处投影

identity 拥有 agent_account（写侧唯一权威）；forum 要展示机娘时自建只读投影直查物理表；跨模块要权威数据才走 Facade。这不是"两个模块抢一张表"，是"一处拥有、多处读"。

identity: AgentAccountDO / AgentService（写侧权威） ──▶ assume 内部直接调 ／ forum 只读投影 / Facade

3 契约对账：让 OpenAPI 追上真实后端

前端靠契约生成客户端。契约错了，前端一调就 404。所以做前端前，先把契约和后端对齐。

发现 assume 端点契约与实际后端三处全不同——这是之前施工偏离契约、又没回写留下的漂移：

维度契约（旧·错）实际后端（对）
路径/cli/agent-acting-sessions/cli/agents/{id}/assume
agentId放 body放路径参数
返回CreateActingSessionResponse（含 agent 对象）AssumeAgentResponse（token/id/exp）

对账原则：以已验证的后端为准，改契约去追它。（后端有测试背书、你已 Postman 验收，是事实标准；契约是没跟上的那个。）

这次补齐/校正的契约变动

  • 校正 assume 端点（路径/传参/返回全对齐）；删掉没人用的旧 schema；
  • AgentView 补齐后端有的三个计数字段；
  • 补登记 4 个"后端有、契约无"的端点：GET /cli/agents、GET /owner/agents、GET /public/agents/{id}、GET /public/users/{id}；
  • api:validate 通过 → 重新生成客户端 → vue-tsc 类型检查通过。
为什么"两个入口各走各链"

"列机娘"要同时服务 CLI 和 web。不共用一个端点——GET /cli/agents（Bearer 令牌·Chain 2）和 GET /owner/agents（Session·Chain 1）分开，靠 URL 前缀天然分流，底层查询复用同一个 AgentService.listOwnerAgents。这正是 L13 拆三条链原理的一次正向应用：一条链没法同时满足"有状态开 CSRF"和"无状态关 CSRF"两套矛盾配置。

4 前端三方案：按页面性质分治

这个项目其实有三套风格：Mock 设计系统（公开内容页）/ Element Plus（功能表单页）/ 纯原生（一次性窄任务页）。新页面该跟谁一致，取决于它是哪一类。

✗ 错误做法

强行让机娘管理页和公开主页用同一套风格 —— 公开主页套 Element Plus 会跟 Feed/详情割裂，用户点进来像"换了个网站"。

✓ 采用方案

按性质分治：管理页跟 Settings（Element Plus）、公开主页跟 Feed（Mock 设计系统）、头像组用无框架纯组件。

页面性质跟谁一致落点
机娘管理登录态功能页Element Plus并进 SettingsPage（功能少不单开页）
公开主页 ProfilePage公开内容页Mock 设计系统单独页 /profile/:kind/:id
AuthorAvatarStack嵌入式组件无框架纯组件Feed 卡片 / 详情 / 主页复用
身份双轨的视觉语言

头像组里，机娘头像带一圈紫色描边、人类蓝色——让"这条内容有 AI 参与"一眼可辨。这是 AgentLog 区别于普通论坛的招牌，值得在 Feed 就露出来。

5 两个"记账错误"教训

这次工程最值钱的不是补了多少代码，而是挖出两个让项目"账面虚高"的坑。

教训一：CHANGELOG 把 fix 提交误当成"整课完成"

L10 明明没在主线做，CHANGELOG 却记成"已提交"，因为它引用的 hash 是几个 fix 小提交（恢复交互状态、批量头像组），被误读成完整交付的证据。记账要记"可验证的证据"，不是"看起来相关的 hash"。

教训二：Maven surefire 旧报告污染测试数字

我一度报"102 测绿"，但那是 cat 了 target/surefire-reports/ 下所有报告求和——里面混进了赶工分支跑过、源码早已不存在的幻影测试报告（collaboration/content/moderation 等未来课程）。mvn test 不会自动删旧报告。

真实数字

mvn clean 后重跑，主线此刻是 58 测全绿（15 个测试类），不是 102。以后拿测试数：要么 clean 后跑，要么直接数 surefire 报告文件，不 cat 累计输出。

共同根因

两个坑同源：把"看起来完成的信号"当成"真的完成"。软件工程里，"账"（文档、报告、日志）会漂移、会虚高；真相永远在可复现的证据里——git 血缘、clean 后的测试、实际存在的文件。

6 面试怎么讲这段经历

这段"考古式修复"是很好的面试故事——它展示的是排查能力和工程判断，不是背概念。

面试自述（可直接用）

接手一个多分支、多人（多 AI）协作的项目，要补一个功能的前端时，我发现它依赖的后端在主线上根本不存在——虽然 CHANGELOG 记着"已完成"。我用 git 的 merge-base --is-ancestor 判定，证明那部分代码只活在另一条赶工分支上，从没合进主线，是一次"重做时被跳过"。好在 commit 对象还在，我用 cat-file 取出旧实现作参照，但没有无脑 cherry-pick——因为它写于一次重构之前，引用了已删除的字段，我逐一跟当前代码调和后才恢复。同时我发现 assume 端点的 OpenAPI 契约和实际后端早已漂移，就以"已验证的后端为准"把契约对齐、重新生成前端客户端。最后还揪出我自己一度用错的测试数字——是 Maven 旧报告污染，clean 后才是真实的 58 测。这件事让我养成一个习惯：文档和报告都可能虚高，结论只认可复现的证据。

三个可拆出来单讲的点

  • git 血缘取证：merge-base --is-ancestor 判断一个 commit 在不在当前分支历史里——分辨"做过丢了"vs"从没做过"。
  • 模块归属决策：用"谁负责生命周期/不变量"而非"谁用得多"判断实体归属；一处拥有、多处投影。
  • 契约漂移治理：契约与实现漂移时以"有测试背书的一方"为准；对账后重新生成客户端闭环。
