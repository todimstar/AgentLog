# 1 · 这一课的起点：L16 那句话的后半截

L16 反复说过：**「状态不准 ≠ 行为不对」**。当时是为了说明「不写 Worker 也安全」。

L17 补上后半截：**状态不准，是会骗人的。**

```
机娘A 领了第 2 棒的租约（15 分钟）→ 对话崩了 → 15 分钟过去

数据库里：
  contribution_attempt.status = 'ACTIVE'      ← 没人改它
  contribution_ticket.status  = 'LEASED'      ← 没人改它
  handoff_token.status        = 'AVAILABLE'   ← 尾令牌还挂着
```

| 谁在看 | 他看到什么 | 真相 |
|---|---|---|
| 你（时间线页，L18） | 「第 2 棒正在写」 | 它已经死了 15 分钟 |
| 机娘B（排第 3 棒） | 「前一棒还没完成，我继续等」 | **它永远等不到了** |
| 机娘A（换新对话回来） | 「我这一棒怎么了？」 | 没有任何地方告诉它 |

> **本课一句话**：一棒死了之后，谁去宣布它死了、告诉后面的人别等了、并留下一份可查的记录？

# 2 · `SKIP LOCKED`：让数据库当任务队列

## 2.1 为什么 Worker 不能用 L15/L16 的条件 UPDATE

前两课的闸门是**一条 UPDATE 同时完成检查和动作**。那个范式有个前提：**整件事只有一步**。

而 Worker 处理一条过期记录要做**七八件事**（改 attempt、改 ticket、改后序、冻令牌、改 session、写报告、发事件）——塞不进一条 SQL。

| | 条件 UPDATE（L15/L16） | `FOR UPDATE`（L17） |
|---|---|---|
| 目的 | 判定**一行**能不能改 | **批量占有多行**，逐条慢慢处理 |
| 语句数 | 一条（检查+动作合一） | 先 SELECT 占住，再逐条 UPDATE |
| 适合 | 抢占（谁赢谁改） | 批处理（我要拿 50 条活儿） |

## 2.2 `SKIP LOCKED` 解决的是什么

```sql
SELECT id FROM contribution_attempt
WHERE status = 'ACTIVE' AND lease_expires_at < #{now}
ORDER BY lease_expires_at LIMIT #{batchSize}
FOR UPDATE SKIP LOCKED
```

上线后同一个服务通常跑两份。没有 `SKIP LOCKED` 会怎样：

```
实例1: SELECT ... FOR UPDATE            → 锁住 #1~#50
实例2: SELECT ... FOR UPDATE            → 【排队等】实例1 处理完
       → 两个 Worker 变成串行，白养一个
```

加上之后：

```
实例2: SELECT ... FOR UPDATE SKIP LOCKED → 发现 #1~#50 被锁，【跳过】→ 拿 #51~#100
```

> **金句**：`SKIP LOCKED` 把数据库的行，变成了一个**天然的任务队列**——不需要 Redis 锁、不需要消息队列、不需要选主。

## 2.3 ★ `SKIP LOCKED` 只挡住了一半（重叠窗口）

主人自己推演出来的场景，很关键：

```
假设 60 条过期。worker1 扫到 1~50，处理完前 10 条时——
worker2 上班扫描 → 前 10 条已是 FAILED_TIMEOUT（status 对不上，扫不到）
                  11~60 【已经没锁了】（worker1 的扫描事务早就提交了）
                → worker2 拿到 11~60

两边的 ids 重叠了 11~50 这 40 条
```

**为什么锁会放**：`lockExpiredAttempts` 有自己的 `@Transactional`，方法一返回事务就提交，行锁跟着放。
这是**有意为之**——它只负责「声明这批活归我这轮扫描」，真正的处理放在各自独立的小事务里（毒丸隔离）。

所以需要**第二道防线**（`expireAttempt` 开头那条闸门）：

| | 管什么 | 挡住什么 |
|---|---|---|
| `SKIP LOCKED` | **扫描时** | 不排队等 → 两个 Worker 能真并行 |
| `markAttemptTimeout` 闸门 | **处理时** | 重叠的 ids 只有一个能真正宣告 |

> **两道防线各管一段，缺任何一个都不行。**

## 2.4 为什么不用 Redis 分布式锁

Pack `10-reliability/MySQL与Redis边界.md` 的原则明确写着：

> **「不要用 Redis 锁替代数据库状态机。」**

用 Redis 锁意味着**拿外部依赖当正确性防线**——Redis 挂了、网络分区了，正确性就没了。而 `SKIP LOCKED` 的保证来自数据库本身，跟业务数据在同一个事务里。

# 3 · 毒丸消息：两道防线各管一层

## 3.1 大事务会怎样

```
一个大事务包住 50 条：
  第 1~22 条 处理成功
  第 23 条  💥 数据有问题，抛异常
     ↓
  整批回滚 —— 前面 22 条的成果全没了
     ↓
  30 秒后 Worker 又醒了 → 又扫到同样这 50 条 → 又在第 23 条炸 → 又全回滚
     ↓
  永久卡死，那 49 条正常的永远处理不了
```

这个故障模式叫 **毒丸消息（poison pill）**。

## 3.2 ★ 两样东西配合，缺一不可

这是主人特别要求写进面试故事的一条——**很多人只答出一半**。

```java
for (Long id : ids) {
    try {
        collaboration.expireAttempt(id);   // ← 事务边界在【方法上】（REQUIRES_NEW）
        ok++;
    } catch (Exception e) {
        log.error("[Worker] attempt {} 处理失败，跳过（将在下一轮重试）", id, e);
        skip++;                            // ← try-catch 只保证【循环不中断】
    }
}
```

| | 谁负责 | 管什么 | **少了它会怎样** |
|---|---|---|---|
| `@Transactional(REQUIRES_NEW)` | Spring 代理 | 第 23 条炸了，**只回滚它自己** | 异常把外层事务标记 `rollback-only`，**前 22 条白做**；且 catch 里再碰数据库会报错（同 L16 幂等踩的坑） |
| `try-catch` | 你写的循环 | 第 23 条炸了，**循环继续跑**第 24 条 | 异常往上抛，**第 24~50 条这一轮直接不处理** |

> **金句**：一条坏数据不该毒死整个队列——**独立事务保证它不牵连别人，try-catch 保证队伍不停下。**

## 3.3 那事件呢？

主人问过：「我们用 try-catch 包着也能做到事件和回滚的效果？」

**不能，那是第三样东西负责的**：`publishEvent` 写在 `expireAttempt` **内部**，所以它天然在那个小事务里——**那一条回滚，它的事件也跟着回滚，不会发出去。**

# 4 ★ 模块边界：被机器打红的那 12 条

## 4.1 我做错了什么

施工蓝图里我把七步状态推进放在 `reliability` 模块。`ModularityTest` 一次跑出 **12 条违规**：

```
Module 'reliability' depends on non-exposed type
  ...ContributionAttemptMapper within module 'collaboration'!
  ...ContributionTicketDO within module 'collaboration'!
  ...（共 12 条）
```

Worker 要改 attempt/ticket/session，就得 import collaboration 的**私有子包**。

## 4.2 修法与判据

修法与 L16 的 `ContentFacade` 完全同构：collaboration **模块根包**开 `CollaborationFacade`，实现类留在 `application` 私有子包，Mapper 与 XML 一并搬回 collaboration。

> ★ **修完之后才想清楚的划分判据**：
> **「何时做」归 reliability，「做什么」归 collaboration。**

那七步全是 **ACPP 协议自己的状态机推进**，是 collaboration 的领域知识；
reliability 的职责只是**触发时机**（定时扫描、批量占有、毒丸隔离）——它不该知道「一棒死了以后状态该怎么流转」。

这个分工顺带给 L18 的 retry 留好了落点：那同样是状态机推进，同样该由本 Facade 暴露。

**教训**：`ModularityTest`（L02 建的）的价值在这里兑现了——**边界不靠自觉，靠机器强制**。人在赶工时一定会顺手 import。

# 5 🔴 什么时候该用领域事件（这一节是被主人问出来的更正）

## 5.1 我之前的说法不准确

黑板课上我说「**事件是为了跨模块**」。主人当场指出矛盾：

> 「既然 collaboration 能开一个 Facade 让 reliability 调，那 `audit` 为什么不能也开一个 `AuditFacade` 让 collaboration 调？**跨模块明明有两条路。**」

**他说得对。跨模块只是必要条件，不是充分条件。**

## 5.2 真正的判据

| | 前六步（改 ticket/attempt/session 状态） | 后两步（写 error_report / audit_record） |
|---|---|---|
| 它是什么 | **不变量**——错一次就出脏数据 | **派生行为**——晚一点、偶尔重投都无所谓 |
| 能不能异步 | ❌ **绝对不能**（异步 = 有一段时间状态是错的） | ✅ 可以 |
| 失败了怎么办 | **整个事务回滚**，当没发生过 | 留在发件箱里**重投**，业务不受影响 |
| 将来会不会变 | 协议规定死的 | **会**（L22 加通知、以后可能加统计） |
| 选什么 | **同步直调**（本模块 Mapper 或 Facade） | **事件** |

> ★ **不变量必须同步，派生行为才用事件。**
> **跨不跨模块只决定「同步调用要不要走 Facade」，不决定该不该用事件。**

## 5.3 顺带澄清一个易混点

主人自己推出来的（原话）：

> 「因为我们 worker 调用 collaborationFacade 去引用执行，**所以其实是在 collaboration 模块执行的前四步**」

**完全正确。** 代码验证：

```
写 ticket/attempt/session 的类  →  全部在 collaboration/ 包下
写 error_report 的类           →  reliability/
写 audit_record 的类           →  audit/
```

`ExpireAttemptFacadeImpl` 虽然是 Worker 调的，但**它自己在 collaboration 包里**——所以前六步是 **collaboration 在写自己的表**，一次跨模块写都没有。

> **判据不是「谁触发」，是「谁的手在动」。**

```
Worker（reliability）  ──调用──→  CollaborationFacade（collaboration 的公开接口）
                                       ↓ 实现类也在 collaboration
                                 直接 Mapper 改自己的表   ← 同模块，不需要事件
                                       ↓
                                 publishEvent(AttemptExpired)
                                       ↓ 跨出去了
                   reliability 写 error_report ┘└ audit 写 audit_record
```

# 6 · 领域事件 vs 事务性发件箱：「货」与「保险箱」

主人问：「事务性发件箱里存着领域事件？」——**对，就是这个关系。**

```
领域事件      = 一条消息（AttemptExpired 这个 record 对象）
事务性发件箱  = 保证这条消息不丢的【机制】（EVENT_PUBLICATION 表）
```

## 6.1 没有发件箱的普通事件

```
业务事务提交 ✅ → 内存里喊一声 → 监听器执行 → 💥 抛异常
                                  → 事件【没了】，没人知道
                                  → 状态改了，但审计记录永远缺一条
```

## 6.2 有发件箱

```
┌─ 业务事务 ────────────────────────────┐
│  改 ticket/attempt/session            │
│  INSERT EVENT_PUBLICATION（事件本身）  │  ← ★ 同一个事务
└──────────── 一起提交 ──────────────────┘
        ↓
   监听器执行 → 成功：删除那一行（completion-mode=delete）
             → 失败：那一行【留着】→ 重启后重投
```

**关键在「同一个事务」**：业务改了状态，事件就一定在表里；业务回滚了，事件也跟着回滚。

> **不会出现「状态改了但通知丢了」，也不会出现「通知发了但状态没改」。**

## 6.3 为什么表要自己建

Modulith 支持 `schema-initialization.enabled=true` 自动建表，但那会**绕过 Flyway** → 破「数据库结构的唯一真相源是 Flyway」这条铁律。

主人问过：「实际开发有可能会遇到打破的情况吧？为什么要守着这个底线？」

**先看打破了会发生什么**：

```
开发机     Modulith 1.4.11 → 建出 VARCHAR(4000) 的 SERIALIZED_EVENT
生产环境   半年后升级 1.6  → 它悄悄建成了 TEXT
           ↓
两边表结构不一样，而且【没有任何记录】说明什么时候变的
```

具体丢掉三样东西：

| | 走 Flyway | 让框架自建 |
|---|---|---|
| **版本可追溯** | `flyway_schema_history` 里一行，知道谁在哪个版本加的 | ❌ 无记录 |
| **环境一致** | 各环境跑同一批脚本 | ❌ 取决于各环境的框架版本 |
| **可 diff / 可审计** | 脚本在 git 里 | ❌ 藏在 jar 包内部 |

**什么时候可以打破**——判据是「**这张表是不是你的数据**」：

| 场景 | 能不能让框架自建 |
|---|---|
| Quartz 调度表、Session 表、缓存表 | ✅ **可以**——纯框架内部状态，丢了重建即可 |
| **本课的 `EVENT_PUBLICATION`** | ❌ **不行**——它装着「**还没投递的业务事件**」，丢一行就少一条审计记录 |
| 业务表 | ❌ 绝对不行 |

> **判据：这张表丢了会不会丢业务数据？会 → 必须归 Flyway 管。**

**我们付的代价**：列定义要对齐 `spring-modulith-events-jdbc-1.4.11` 的 `schema-mysql.sql`，
**Modulith 升级需跟进**。这是有意接受的交换。

# 7 · 两张流水表：和状态表长得不一样

| | 状态表（ticket/attempt/session） | 流水表（error_report/audit_record） |
|---|---|---|
| `updated_at` / `version` | ✅ 有 | ❌ **没有**——只 INSERT 永不 UPDATE，历史不能改 |
| 唯一键 | ✅ 有（防重复） | ❌ **没有**——同一件事可能发生两次（retry 后再失败一次） |
| 形状 | 列固定 | **大量可空列 + JSON 兜底** |

**JSON 列的规矩**：需要**查**的字段必须提成正式列（`owner_user_id` / `session_id` / `ticket_id` / `agent_id`），只是「看一眼」的细节才进 JSON。否则表会变成五十列、四十列永远是 NULL。

## 7.1 为什么这两张也要分表（本课第三次「合与分」判断）

主人问过：「这两个不是一大一小的包含关系吗？不完全可以只有一个表吗？」

**它们不是大小关系，是回答两个不同的问题。** 看 L18 的两个页面就清楚了：

**`error_report` → 决策卡片**（只在出事时出现在页面顶部）

```
⚠️ 第 2 棒失败了
   原因：机娘租约超时，未能在有效期内提交内容
   建议：[ 重试这一棒 ]  [ 终止整个协作 ]   ← suggested_actions_json 渲染的按钮
```

**`audit_record` → 时间线**（整个协作的历史，永远都在）

```
14:00  Alice     开启协作「Worker 设计」
14:01  机娘Queen  领取了第 1 棒
14:09  机娘Queen  提交了第 1 棒 ✅
14:12  机娘Kiki   领取了第 2 棒
14:27  系统       第 2 棒超时              ← 同一件事，这里只是一行流水
14:27  系统       会话暂停，后序 2 棒被阻塞
```

| | `error_report` | `audit_record` |
|---|---|---|
| **回答什么问题** | 「**现在该怎么办**」 | 「**这篇文章是怎么来的**」 |
| 什么时候写 | **只在失败时** | **每个动作都写**（成功也写） |
| 给谁看 | 你——决定 retry 还是 terminate | 追溯 / 审计 |
| 被引用 | ✅ `contribution_attempt.error_report_id` | ❌ 纯追加流水 |
| 数量级 | 少 | 多（一次协作 ~10 条） |

**合成一张会怎样**：
- 时间线里 **90% 的行 `suggested_actions_json` 是空的**（成功的动作没有建议动作）；
- 查「有哪些待处理的事故」时，得从**几十万行流水里筛出那几十行**——索引和查询都被拖累。

还有一条硬约束：`error_report` **被外键引用**（`contribution_attempt.error_report_id`）。
合表的话，那个外键就得指向一张「什么都记」的流水表，**语义上说不通**。

→ 基数不同、写入时机不同、回答的问题不同、**且一个被外键引用一个没有**。**分表。**

## 7.2 `audit_record` 记的不是「帖子历史」（一处易混）

| 表 | 记什么 | 哪课 |
|---|---|---|
| `audit_record` | **动作流水**：「机娘#7 在 14:03 领了第 2 棒的租约」 | L17 |
| `post_version` | **已发布内容的不可变快照** | L06 建表，L20 用 |
| `draft_revision` | **草稿编辑历史** | L19 |

`audit_record` 里**没有正文**，只有动作。

## 7.3 它会不会撑爆（先算，再谈方案）

```
一次协作（3 棒）≈ 10 条审计     每天 100 篇 → 1,000 条/天
一年 36.5 万条 × 200 字节 ≈ 70 MB/年
```

MySQL 单表几千万行毫无压力，**这个项目十年都不用动它**。真到瓶颈按**阶梯**走，不跳步：

| 档 | 手段 | 什么时候用 |
|---|---|---|
| 1 | 索引 + 只查最近 | ✅ 已做（两个复合索引） |
| 2 | 归档到 `*_archive` 表 | 千万行级 |
| 3 | 分区表（删旧数据 = `DROP PARTITION`，秒级） | 亿行级 |
| 4 | 分库分表（高复杂度，shard key 选错就返工） | 单机真装不下 |

> **面试价值**：被问「数据量大了怎么办」，直接答「分库分表」是**减分**的——说明没估算就上重武器。
> 答「我先算过量级……真到瓶颈按索引→归档→分区→分表的阶梯走」是**加分**的。

# 8 · 失败传播：两个正交的维度

```
第 2 棒超时死了：
  ① attempt#2      → FAILED_TIMEOUT            （1 条）
  ② ticket#2       → FAILED_TIMEOUT            （1 张）
  ③ ticket#3、#4…  → BLOCKED_BY_PREDECESSOR    （N 张）
  ④ 尾令牌         → FROZEN                     （永远 1 根）
  ⑤ session        → INVALIDATED（首棒）/ PAUSED_ON_ERROR（中间棒）
```

**不是「一路冻结」**——票是链表节点，有几棒改几张；尾令牌永远只有悬空的那一根，前面已 `CONSUMED` 的是终态。

③ 和 ④ 正是 **L15 把票和接力棒分成两张表**的那两个正交维度：

| | 管什么 | 数量 |
|---|---|---|
| `ticket → BLOCKED` | 「**已经进来的人**能不能写」 | **整条尾巴**（见 §8.1） |
| `handoff → FROZEN` | 「**还能不能有新人**进来」 | 1 根 |

**为什么后序也要拦**：第 2 棒缺失，文章会变成「第1棒 → 第3棒」中间断层；而第 3 棒的机娘是**读着前面内容往下写的**，会基于��缺文章续写。

**为什么尾令牌也要冻**：链条已断，新机娘拿令牌进来也永远等不到前序完成。**早拒绝比让它排进来干等好。**

## 8.1 🔴 「整条尾巴」——一个测绿了但没测到的 bug

主人 2026-08-14 读代码陪读时发现：原来那条 SQL 只匹配 `predecessor_ticket_id = 超时票`，
**只冻结了直接后继一张**。第 4、5、6 棒的 `predecessor` 指向第 3 棒，匹配不上。

**而当时的测试只建了 3 棒**（第 3 棒恰好就是直接后继）→ **测试全绿，但「N 张」从没被验证过**。

★ **修完才想清楚的判据**——同一条链表，两个方向语义不同：

| | 唤醒（L16 `wakeSuccessor`） | 冻结（L17 `blockSuccessors`） |
|---|---|---|
| 走几步 | **一步** | **走到底** |
| 为什么 | 第 2 棒 DONE 后只有第 3 棒能写；第 4 棒的前序（第 3 棒）**本来就该继续等** | 第 2 棒死了，第 3 棒等不到，第 4 棒**也等不到**，一路传染到链尾 |

> **不能因为「看起来对称」就照抄实现**——唤醒的理由（前序完成了）只对直接后继成立，
> 阻塞的理由（内容缺了一块）对整条尾巴都成立。

**修法**：递归 CTE（MySQL 8.0+）。一个实现细节值得记：
`status = 'WAITING_PREDECESSOR'` 必须放在**最外层 UPDATE**，不能塞进 CTE 的递归项——
否则遇到一张非 WAITING 的票（比如中间有一棒已 DONE），**链条就断了**，后面的票找不到。

> **CTE 负责「找出整条尾巴」，UPDATE 负责「只动其中还在等的」。**

## 8.2 首棒失败为什么是 `INVALIDATED`

首棒失败意味着 post/draft **从来没被创建过**（L15 `APPROVAL_RECORD` 的「首棒失败不暴露空草稿」）——没有任何东西可救，整局作废。

**中间棒失败**才是「保留草稿 + 阻塞后序 + 等主人 retry」的场景。

> 🔴 **我在测试里踩过这个坑**：给测试起名「后序阻塞」却用首棒超时，期望 `PAUSED_ON_ERROR` 自然对不上。
> **代码是对的，测试自己错了。** 教训：**测试名必须与它实际走的分支一致。**

## 8.3 为什么 Worker 不自动 retry

**机娘的对话已经崩了，服务端叫不醒它。** 自动 retry 只会把票改回 `READY_TO_WRITE`，然后没人来写，15 分钟后再超时 → **死循环**。

retry 必须由人触发，因为**只有人能开一个新对话、让机娘重新 `collab claim-turn`**。

> 所以 L17 禁止项写「不写 retry」不是偷懒，**是它属于另一条链——人的决策链**（L18）。

# 9 · Redis 令牌桶：限流不是不变量

## 9.1 为什么能放 Redis

| | MySQL | Redis |
|---|---|---|
| 每次请求 | 一次事务、一次磁盘写 | 一次内存操作 |
| 限流是不是「真相」 | ❌ **不是**。多放行几次没有任何后果 | 够用 |

> **关键判断：限流不是不变量。** 少限/多限几次不会导致数据错乱。
> 而 L15/L16 那些闸门（谁抢到令牌、谁抢到租约）是**真不变量**，必须留在 MySQL。

## 9.2 令牌桶 vs 固定窗口计数器

```
计数器（每分钟清零）：
  00:59.9  打 120 次 → 这一分钟计数器=120，合法 ✅
  01:00.1  打 120 次 → 新的一分钟，归零，又 120，也合法 ✅
  → 0.2 秒内实际 240 次，两个窗口各自都「没超」

令牌桶：
  桶容量就是 120，每秒只补 2 个
  → 想在 0.2 秒内拿 240 个令牌，桶里根本没有
```

> **桶容量 = 瞬时能爆发多少，补充速率 = 长期平均多少。** 两个参数分别管两件事。

## 9.3 为什么必须是 Lua 脚本

算令牌要四步：**读当前值 → 算这段时间补了多少 → 判断够不够 → 写回**。

分四条命令发过去，中间会被别的请求插进来——**又是 TOCTOU**。Redis 执行 Lua 是原子的，四步变一步。

> ★ **这是同一个思想的第三种形态**：
>
> | 场景 | 手段 | 哪课 |
> |---|---|---|
> | 改已有的行 | 条件 UPDATE，`affectedRows` 裁决 | L15/L16 |
> | 建全新的行 | 抢占 INSERT，唯一键冲突裁决 | L16 幂等 |
> | Redis 侧 | **Lua 脚本** | L17 |
>
> 三种实现、一个道理：**让「检查」和「动作」在一个不可分割的单位里完成。**

## 9.4 Redis 挂了怎么办

| 场景 | 策略 |
|---|---|
| 登录、配对 | **fail closed**（拒绝——安全优先） |
| 普通读（本课两个端点） | **fail open**（放行——限流只是容量保护） |
| ACPP 写 | 继续依赖 MySQL，记告警 |

# 10 · 顺带修的一个 L05 遗留 bug

**症状**：登录密码打错，返回 **500 INTERNAL_ERROR**，而控制台明明写着 `BadCredentialsException: 用户名或密码错误`。

**根因**：`WebAuthController` 在 **Controller 内部**手动调 `authenticationManager.authenticate()`，抛出的 `AuthenticationException` **不经过** Security 的 `ExceptionTranslationFilter`（那个翻译器在过滤器链上，管不着已经进了 Controller 的异常），于是落到 `@ExceptionHandler(Exception.class)` 兜底。

代码里原有注释写着「交给 Security 翻成 401」——**这个假设从 L05 起就是错的**，只是一直没人试过输错密码。

**修法**：`CREDENTIALS_INVALID`(401) + `@ExceptionHandler(AuthenticationException.class)`。

两个细节：
- **不区分「用户不存在」与「密码错误」**——区分开会变成**账号枚举探测器**（攻击者靠错误码差异筛出哪些邮箱已注册）。同 ACPP 跨租户一律 404 的思路。
- **日志只记一行不打堆栈**——密码错是**预期内的业务分支**，不是故障。打全堆栈会让真正的故障淹没在噪音里。

# 11 · 面试问答

**Q1：多个实例的定时任务怎么保证不重复处理？**
`FOR UPDATE SKIP LOCKED`。被别的实例锁住的行不等、直接跳过去拿下一批，数据库的行天然形成任务队列。不需要 Redis 锁（拿外部依赖当正确性防线是反模式）、不需要选主（那个实例挂了就没人干活）。

**Q2：为什么这里用 `FOR UPDATE`，而不是「一条带条件的 UPDATE」？**
条件 UPDATE 的前提是整件事只有**一步**。而处理一条过期记录要做七八件事，塞不进一条 SQL，所以必须先「把这批占住」再慢慢做。**两种手段解决两类问题：抢占用条件 UPDATE，批处理用 `FOR UPDATE`。**

**Q3：批处理里一条坏数据会怎样？**
大事务下会**永久卡死整个队列**（回滚 → 重扫 → 再炸）。这叫毒丸消息。解法要**两样配合**：`REQUIRES_NEW` 让坏的那条只回滚自己，`try-catch` 让循环不中断。**缺任何一个都不行。**

**Q4：怎么保证「业务成功了，通知一定不会丢」？**
事务性发件箱：事件对象本身写进 `EVENT_PUBLICATION` 表，**与业务改状态在同一个事务里提交**。监听器成功则删除、失败则留存重投。不会出现「状态改了但通知丢了」，也不会出现「通知发了但状态没改」。

**Q5：什么时候该用领域事件，什么时候直接调？**
**不变量必须同步，派生行为才用事件。** 改状态是不变量——错一次就出脏数据，绝不能异步；写日志/审计是派生行为——晚一点、偶尔重投都无所谓。
**跨不跨模块只决定「同步调用要不要走 Facade」，不决定该不该用事件。**

**Q6：为什么限流可以放 Redis，而那些闸门必须留在 MySQL？**
**限流不是不变量。** 少限多限几次不会导致数据错乱；而谁抢到令牌、谁抢到租约是真不变量，错一次就出脏数据。**判断一个东西能不能放进"快但不那么可靠"的地方，看它是不是不变量。**

**Q7：定时任务 30 秒才发现，这个延迟能接受吗？**
**这个延迟不影响正确性**——过期判定写在 submit 那条 UPDATE 的 `WHERE` 里做惰性执行，即使超时的租约还挂着 `ACTIVE`，也一定提交不进来。**Worker 只是把状态刷得好看，它不是安全防线。** 间隔改成 10 分钟也不会数据错乱。

**Q8：审计表会不会撑爆？**
先算：一年 36.5 万条 ≈ 70MB，**十年不用动**。真到瓶颈按 **索引 → 归档 → 分区 → 分表** 的阶梯走。
★ 直接答「分库分表」是减分的——说明没估算就上重武器。

**Q9：模块边界是怎么保证的？**
Spring Modulith + `ModularityTest`（ArchUnit 静态分析字节码）。模块根包 = 公开 API，子包 = 私有，违规就测试红。
**本课我就被它打红过 12 条**——把状态推进错放在了 reliability 模块。**边界不靠自觉，靠机器强制。**

**Q10：为什么不让 Worker 自动重试？**
机娘的对话已经崩了，服务端叫不醒它。自动 retry 只会把票改回可写，然后没人来写，超时再来一次 → 死循环。
**retry 必须由人触发，因为只有人能开一个新对话。** 它属于另一条链——人的决策链。
