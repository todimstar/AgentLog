## 先把模块的事讲清（面试点）

你问"模块怎么划分、有啥依据"——一句话：**按业务能力竖着切，不按技术层横着切**。

```
你旧论坛横着切：controller层/service层/mapper层（所有业务挤在一个service层互相调）
AgentLog 竖着切：identity(我是谁) / content(写内容) / forum(读内容+互动) /
                 collaboration(AI协作) / media / notification / moderation …
              每个模块各管一摊，互不串门
```

依据是 **DDD 的限界上下文**——每个模块管一个业务领域，模块内代码只关心自己领域的事。
怎么保证不串？**机器强制**：L02 建的 `ModularityTest.verify()` 扫代码，一个模块 import 别的模块
内部子包，测试就红。所以边界靠机器不靠自觉。
好处（能讲）："改 content 的发布逻辑，绝不会把 forum 的 Feed 搞坏，因为 forum 根本看不见 content 内部。
这是高内聚低耦合的落地版。"

## 三道门 revisit：Feed 归 forum 不归 content

换个角度看你 L06 学过的三道门：
- **content 模块**管"写"：建草稿、发布、快照复制（TX-01/TX-02 重事务）。
- **forum 模块**管"读"：Feed 列表、看详情、评论、点赞（高频只读）。

设计文档 `module-contracts.md` 把 `ForumFacade.listFeed` 和 `ForumFacade.getPost` 都放 forum——
意思是**所有"读帖子"都归 forum**。所以本课要做两件读东西：
1. **Feed 列表**（本课主菜）→ forum 新建。
2. **单篇详情 `getPublicPost`** → L06 当时没 forum 模块，偷放在 content 了，本课顺手迁回 forum。

两个都迁完，forum 成为完整"读模型"模块。这就是面试词 **CQRS** 的落地。

## CQRS 是啥？（你专门问了）

四个字母：**C**ommand 写 / **Q**uery 读 / **S**eparation 分离 / **R**esponsibility 职责。
中文"命令查询职责分离"。大白话：**写入和读取用两套不同的代码模型，哪怕操作同一张表**。
- content 管写 → 它有 `PostDO`（全字段 + 乐观锁，适合改）。
- forum 管读 → 它有 `PostFeedRow`（只有卡片需要的几个字段，适合查）。
同一张 post 表，两个模型，各自优化。这就是写读分离，简历能讲。

为什么拆？写要事务/锁/全字段，读只要快、只要展示字段。揉一起一个 Service 又背写又背读，又乱又慢。

## 跨模块只读 vs 写怎么协作（你问 Facade 干啥的）

这个规则也值钱：
| 跨模块做什么 | 怎么做 | 为什么 |
|---|---|---|
| **只读对方的数据**（如 forum 读 channel 名字展示） | forum 自建一份 DTO + 自己 Mapper 直接读物理表，**零 import 对方代码** | 只读不该让对方为你暴露接口，自建换零耦合 |
| **写对方的数据**（如 AI 投稿要往 content 草稿写） | 调对方根包暴露的 **Facade**（L16 建 ContentFacade），不许碰对方内部 Mapper | 写要对方掌控写入规则，防别人乱写脏数据 |

**一句话**：**跨模块只读→直查物理表自建投影；跨模块写→走 Facade**。L07 Feed 是只读，所以自建 ChannelView 不调 content。
Facade 真登场在 L16。别把 Facade 和只读混了——Facade 是"写操作的合法通道"。

### 顺手建：`FeedQuery`（forum/api/dto 根，**第一个 DTO，立刻用上**）
**干嘛的**：Controller 把零散参数打包成它，传给 Service/Mapper。XML 里 `#{q.channelId}` 取值干净。
**什么场景用**：`?channelId=1&page=1&size=20` 进来 → 打包成 FeedQuery → 传下去。
**为啥打包**：将来 L21 加 keyword/tagId、L23 加 sort，只往这 record 加字段，方法签名不变（扩展性）。
`offset()` 是帮手方法,把 page/size 算成 LIMIT 偏移。

<details>
<summary>📦 FeedQuery 参考实现（撞到了才建，建了立刻用）</summary>

```java
package com.agentlog.forum.api.dto;

/** L07 只 channelId+分页；sort/keyword/tagId 留 L21/L23 扩展。 */
public record FeedQuery(Long channelId, int page, int size) {
    public int offset() { return Math.max(0, (page - 1) * size); }   // LIMIT 偏移
}
```
</details>

✅ 这个文件我已经建好了。Controller 现在改成 `feedService.listFeed(new FeedQuery(channelId, page, size))` 接着走。

> 注意 sort/keyword 本课**故意不放**——L23 才做 HOT 排序，现在不放避免越界（守边界原则）。

### 第②层：`FeedService.listFeed`（forum/application，业务核心）
Controller 调它。返回啥？Controller 要返给前端"一页卡片 + 分页信息"——**这又撞到一个 DTO 需求:`PostPage`**。
Service 干三件事：查一页 → 查总数 → 批量补作者/分区 → 拼装返回。

我先把 Service 的"骨架想法"摆出来，每个组件用到啥再回头建：

```
PostPage listFeed(FeedQuery q):
  1. List<PostFeedRow> rows = postFeedMapper.selectFeed(q);       // 查一页扁平行
  2. long total           = postFeedMapper.selectFeedCount(q);    // 查命中总数
  3. 收集所有 channelId → postFeedMapper.selectChannelsByIds(ids) // 一次 IN 查分区（防 N+1）
  4. 收集所有 ownerUserId → (作者批量本课先占位或简化查)
  5. 内存按 postId/channelId 分组拼装 → List<PostCardView>
  6. return new PostPage(items, new PageMeta(q.page, q.size, total));
```

这个骨架里有 5 个东西要建:`PostFeedRow`(SQL行)、`PostCardView`(出参卡片)、`PageMeta`/`PostPage`(分页)、
`PostFeedMapper`(查SQL)、`ChannelView`/`AuthorView`(子对象)。**自顶向下一个个推**。

## 🎯 你亲码 ① 块下移前，先把"为啥要 PostFeedRow"讲清

Service 第 1 步要 `selectFeed` 返回一行行 post 表数据。为啥不是直接返 `PostCardView`？
**因为拼装卡片需要 owner_user_id 去**批量查作者**，但 PostCardView（给前端的）不该有 owner_user_id
（那是内部拼装用的，给前端泄露没意义）。所以需要一个**临时承载对象 PostFeedRow**——它比 PostCardView 多
owner_user_id/channel_id 两个字段，是"内部行"，XML 查出它，Service 再补 channel/authors 转成 PostCardView。

**这是 CQRS 读模型写照**：content 的 PostDO 给写（全字段+锁），forum 的 PostFeedRow 给读（投影）。同一张表。

## 🎯 你亲码 ② 块：`FeedService.listFeed`（N+1 防范）

XML 写完，这块 Service 把"查一页 → 收集 id → 一次 IN 查分区/作者 → 内存分组拼装"写出来。
**N+1 防范结构是简历点的另一半**。

<details>
<summary>📦 FeedService.listFeed 参考骨架（你先读再默写）</summary>

```java
// forum/application/FeedService.java
@Service
public class FeedService {
    private final PostFeedMapper postFeedMapper;
    public FeedService(PostFeedMapper postFeedMapper) { this.postFeedMapper = postFeedMapper; }

    public PostPage listFeed(FeedQuery q) {
        // 1. 查一页扁平行
        List<PostFeedRow> rows = postFeedMapper.selectFeed(q);
        // 2. 命中总数
        long total = postFeedMapper.selectFeedCount(q);
        if (rows.isEmpty()) return new PostPage(List.of(), new PageMeta(q.page(), q.size(), total));

        // 3. 批量查分区（N+1 防范：收齐 channelIds 一次 IN，不逐卡查）
        Set<Long> channelIds = rows.stream().map(PostFeedRow::getChannelId)
                                    .filter(Objects::nonNull).collect(Collectors.toSet());
        Map<Long, ChannelView> channelMap = channelIds.isEmpty() ? Map.of() :
            postFeedMapper.selectChannelsByIds(channelIds).stream()
                .collect(Collectors.toMap(ChannelView::id, c -> c));

        // 4. 作者批量（本课骨架：先简化查 user_account，L10 做头像组完整拼装）
        //    ← 这里你先写一个批量查 user 的逻辑,我用 AuthorNameLookup 占位;也能直接返空 authors 占位
        //    详见下面"本课作者尺度"

        // 5. 内存拼装：每行 → PostCardView
        List<PostCardView> items = rows.stream().map(row -> {
            PostMetrics metrics = new PostMetrics(row.getViewCount(), row.getLikeCount(),
                    row.getCommentCount(), row.getCollectionCount(), row.getHotScore());
            return new PostCardView(
                row.getId(), row.getTitleCache(), row.getSummaryCache(),
                channelMap.get(row.getChannelId()),     // 一次查到的分区
                List.of(),                                // 作者骨架：本课先空数组占位(L10 头像组)
                row.getContentOriginCache(), row.getIterationCount(),
                metrics, row.getPublishedAt(),
                row.getIsPinned(), row.getIsEssence());
        }).toList();

        return new PostPage(items, new PageMeta(q.page(), q.size(), total));
    }
}
```
</details>

> **本课作者尺度（骨架）**：L07 课程卡说"批量作者查询**骨架**"——上面 `authors: List.of()` 占位即可，
> 不在 L07 拼头像组。但要保证 channel 的批量 IN 真做（已经做了），把"不逐卡查"的结构立住。完整头像组是 L10。
