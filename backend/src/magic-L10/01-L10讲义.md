# L10 作者头像组 · 讲义（对话版）

> **一句话**：把 L07 Feed 卡片里空着的 `authors` 补成真实作者头像组。
>
> 本课不用急着做用户主页、关注、粉丝数那些大功能。你先把这一条链路看透：
> `post.owner_user_id` 怎么从数据库里的一个数字，变成 Feed 卡片上能显示的作者头像和名字。

---

## 一、本课到底补什么

L07 的 Feed 已经能查帖子列表，但卡片里有一个占位：

```java
List.of() // authors
```

所以前端只能兜底显示“佚名”。这不是前端没写好，而是后端根本没有告诉前端“这篇帖子是谁发的”。

L10 补的就是这件事：

```text
post.owner_user_id
  -> 批量查 user_account
  -> 拼成 AuthorView
  -> 放进 PostCardView.authors
  -> 前端显示头像组 + 作者名
```

你问“是不是就看收集作者的路径流程就好了？”  
**对，主线就看这条路径。** 但不要只记“收集 id 再查表”，要顺手理解它背后的四件事：

- `PostFeedRow` 是数据库扁平行，不是前端 DTO。
- `AuthorView` 是 forum 自己的读投影，不依赖 identity 模块 Java 类。
- 批量 `IN (...)` 是为了防 N+1。
- 前后端契约要对齐，后端返回的字段必须和 OpenAPI/生成类型一致。

---

## 二、完整路径图

先看全链路，后面再拆开讲：

```text
浏览器打开 Feed
  |
  v
GET /api/v1/public/posts?page=1&size=20
  |
  v
FeedController.listFeed()
  |
  v
FeedService.listFeed(q)
  |
  +--> postFeedMapper.selectFeed(q)
  |      返回 List<PostFeedRow>
  |      每行有：post id / title / channelId / ownerUserId / metrics...
  |
  +--> 收集 channelIds
  |      postFeedMapper.selectChannelsByIds(channelIds)
  |      得到 Map<Long, ChannelView>
  |
  +--> 收集 ownerIds       <-- L10 新增核心
  |      postFeedMapper.selectAuthorsByUserIds(ownerIds)
  |      得到 List<AuthorLookupRow>
  |      转成 Map<Long, AuthorView>
  |
  v
组装 PostCardView
  channel = channelMap.get(row.channelId)
  authors = List.of(authorMap.get(row.ownerUserId))
  |
  v
返回 PostPage.items
  |
  v
PostLogCard.vue
  显示头像首字 + displayName
```

你可以把 L10 想成 L07 频道批量查询的第二遍练习：  
频道是 `channel_id -> ChannelView`，作者是 `owner_user_id -> AuthorView`。

## 三、为什么 Feed 不直接返回 PostFeedRow

`PostFeedRow` 是 SQL 查出来的“扁平行”，它长这样：

```text
id
title_cache
summary_cache
channel_id
owner_user_id
like_count
comment_count
...
```

但前端真正想要的是：

```text
postId
title
summary
channel: { id, slug, name }
authors: [{ authorType, userId, displayName, avatarMediaId, deleted }]
metrics: { viewCount, likeCount, commentCount, collectionCount }
```

这两个不是一回事。

所以 L07/L10 的模式是：

```text
Mapper XML 查扁平行 PostFeedRow
  -> Service 批量补子对象
  -> 转成前端 DTO PostCardView
```

这就是读模型组装。Mapper 负责把数据库查出来，Service 负责把“数据库形状”翻译成“接口形状”。

---

## 四、L10 新增的后端三件套

### 4.1 AuthorLookupRow：作者查找行

它不是接口返回值，只是 Mapper 查 `user_account` 后给 Service 用的中间行。

```java
public class AuthorLookupRow {
    private Long userId;
    private String displayName;
    private String avatarMediaId;
    private String status;
}
```

为什么不直接返回 `UserAccount`？

因为 forum 模块不应该 import identity 模块里的实体。我们只需要展示字段，不需要用户模块的完整领域对象。

> **面试说法**：forum 是读模型消费者，只读 `user_account` 的展示投影，不依赖 identity 的 Java 类型，避免模块边界被读接口打穿。

### 4.2 selectAuthorsByUserIds：一次 IN 查一页作者

SQL 重点是 `WHERE id IN (...)`：

```xml
<select id="selectAuthorsByUserIds"
        resultType="com.agentlog.forum.infrastructure.persistence.dataobject.AuthorLookupRow">
    SELECT id AS user_id, display_name, avatar_media_public_id AS avatar_media_id, status
    FROM user_account
    WHERE id IN
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</select>
```

为什么要批量查？

如果一页 Feed 有 20 篇帖子，错误写法是：

```text
查帖子列表 1 次
然后每张卡片查一次作者 20 次
总共 21 次 SQL
```

这就是 N+1。

L10 的写法是：

```text
查帖子列表 1 次
收集 ownerUserId
批量查作者 1 次
总共固定 2 次作者相关 SQL
```

帖子越多，差别越明显。

### 4.3 AuthorView：接口契约里的作者

L07 后端的 `AuthorView` 只有：

```java
Long id;
String displayName;
```

但 OpenAPI 和前端生成类型早就是 L10 形状：

```java
public record AuthorView(
        String authorType,
        Long userId,
        Long agentId,
        String displayName,
        String avatarMediaId,
        boolean deleted
) {}
```

这里不是“想加几个字段让它高级点”，而是**把后端 DTO 拉回契约**。

`authorType` 现在只有 `OWNER`，但它是为未来 AI Agent 作者预留的。

```text
OWNER 作者：userId 有值，agentId 为空
AGENT 作者：agentId 有值，userId 为空（后续课程再做）
```

`deleted` 是展示兜底：如果用户不是 ACTIVE，或者极端情况下作者查不到，就返回“已注销”这种安全占位，不把异常数据直接炸到前端。

## 五、FeedService 这段代码怎么读

先把帖子查出来：

```java
List<PostFeedRow> rows = postFeedMapper.selectFeed(q);
```

再像频道一样收集作者 id：

```java
Set<Long> ownerIds = rows.stream().map(PostFeedRow::getOwnerUserId)
        .filter(Objects::nonNull).collect(Collectors.toSet());
```

这里用 `Set` 有两个好处：

- 自动去重，同一个作者发了多篇帖也只查一次。
- `IN (...)` 参数更短。

批量查并转成 Map：

```java
Map<Long, AuthorView> authorMap = ownerIds.isEmpty() ? Map.of() :
        postFeedMapper.selectAuthorsByUserIds(ownerIds).stream()
                .collect(Collectors.toMap(AuthorLookupRow::getUserId, this::toAuthorView));
```

为什么要 Map？

因为后面组装每张卡片时，要按 `row.ownerUserId` 快速找到作者：

```java
AuthorView author = authorMap.getOrDefault(
        row.getOwnerUserId(),
        AuthorView.deletedOwner(row.getOwnerUserId())
);
```

最后塞进卡片：

```java
new PostCardView(
    row.getId(),
    row.getTitleCache(),
    row.getSummaryCache(),
    channelMap.get(row.getChannelId()),
    List.of(author),
    ...
)
```

为什么是 `List.of(author)`，不是直接 `author`？

因为接口契约设计成 `authors` 数组。现在一篇帖子只有 OWNER 一个作者，未来可能有：

- owner 本人；
- AI Agent；
- 协作者；
- 审稿/共创贡献者。

所以 L10 只填数组里的第一个 OWNER，不把未来结构堵死。

## 六、为什么不用 JOIN 一次查完

你可能会问：既然只查 OWNER，一个 SQL JOIN `user_account` 不就完了吗？

可以。对当前最小需求，JOIN 是可行的。

但本课选择“先查 post，再批量查作者”，是为了延续 L07 的读模型组装套路：

```text
post 主行保持扁平
channel 用批量查询补
authors 也用批量查询补
```

这样好处是：

- 频道、作者、后续标签/头像组都能走同一类拼装思路。
- `authors` 本身是数组，未来不是一个简单 JOIN 字段。
- Service 层能清楚表达“主行 + 子投影”的组装边界。

所以别把它理解成“JOIN 不会用”。这里是课程有意训练批量投影和 N+1 防范。

---

## 七、前端这课只做展示，不做主页

前端 `PostLogCard.vue` 这次只做两件事：

```text
authors 有值：
  显示头像首字 + displayName

authors 没值：
  显示 ? + 未知作者
```

头像现在不是图片，而是首字头像：

```ts
const initials = (name?: string) => Array.from((name || '?').trim())[0] || '?'
```

这很合理，因为 `avatarMediaId` 只是媒体 id，不是可直接 `<img src="">` 的 URL。真正从 mediaId 换成可访问图片地址，要等媒体模块的公开读取规则接上。

所以 L10 的前端验收不是“头像图片能显示”，而是：

- Feed 卡片不再显示“佚名”。
- 能看到作者名。
- 作者区域有头像位。
- 多篇帖子可以显示不同作者。

## 八、你本课应该怎么复盘

建议你按这 5 个文件走一遍：

1. `PostFeedRow.java`  
   看懂为什么它有 `ownerUserId`，但 `PostCardView` 没有。

2. `PostFeedMapper.xml`  
   看 `selectFeed` 查出 `owner_user_id`，再看 `selectAuthorsByUserIds` 怎么批量查用户。

3. `FeedService.java`  
   从 `rows` 开始，一路看 `ownerIds -> authorMap -> PostCardView.authors`。

4. `AuthorView.java`  
   看接口最终要给前端什么字段。

5. `PostLogCard.vue`  
   看前端只消费 `authors`，不关心后端怎么查出来。

这一课你真正要背下来的不是某行代码，而是这个句式：

> Feed 主查询只拿帖子扁平行，Service 收集本页 `owner_user_id`，一次 `IN` 批量查 `user_account` 的作者投影，再用 `Map<userId, AuthorView>` 拼回每张 `PostCardView`。这样既避免 N+1，又保持 forum 模块只依赖读投影，不直接依赖 identity 的 Java 对象。

## 十、面试讲法

> L07 的 Feed 卡片先把作者留成空数组，L10 我补的是作者读投影。实现上不是每张卡片单独查用户，而是 Feed 查出一页 `PostFeedRow` 后，收集所有 `owner_user_id`，用一次 `IN` 批量查 `user_account`，再转成 `Map<userId, AuthorView>` 拼回 `PostCardView.authors`。这样一页 20 篇帖子也不会变成 20 次作者查询，属于典型的 N+1 防范。同时 forum 模块只拿用户展示字段，不 import identity 的实体类，模块边界更干净。
