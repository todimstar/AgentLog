## 一、背景课:`user_account` 表到底有几个「名字」?(面试常问)

L10 要显示作者名和头像,这些数据都在 `user_account` 表里(L03 的 V001 建的)。跟"身份"有关的有**三个**字段,你必须分清,不然面试一问就露怯:

```
user_account 表(节选)
┌────────────────────────┬──────────────────────────┬──────────────────────┐
│ 字段                    │ 是什么                    │ 谁在用                │
├────────────────────────┼──────────────────────────┼──────────────────────┤
│ username                │ 登录账号名(唯一,像@handle)│ 登录/注册            │
│ display_name            │ 展示名(可重复/可改)       │ 卡片、评论上露出的名  │
│ avatar_media_public_id  │ 头像的媒体id(可为空)      │ 头像(本课重点)       │
└────────────────────────┴──────────────────────────┴──────────────────────┘
```

### `username` vs `display_name`:为什么一张表要两个名?

- **`username`**:你**登录**时打的那个名,全站唯一(V001 有 `UNIQUE KEY uk_user_username`)。它是你的身份锚点,像 Twitter 的 `@某某`。
- **`display_name`**:**露出来给别人看**的名,不唯一、随时能改、能是中文能是 emoji。像 Twitter 那个加粗的昵称。

**为什么必须分两个字段?**(面试三连答)
1. **唯一性诉求相反**:登录名必须唯一(否则登录时系统不知道是你还是别人),展示名允许一堆人都叫"张伟"。合成一个字段就得二选一,都难受。
2. **可变性相反**:`username` 一般不让改(改了别人 @ 不到你),`display_name` 随便改。
3. **字符集不同**:`username` 常限英文数字下划线(方便放进 URL),`display_name` 啥都行。

**登录到底认哪个?认 `username`。** 看 [AppUserDetailsService.java:33](backend/src/main/java/com/agentlog/identity/application/AppUserDetailsService.java#L33):

```java
public UserDetails loadUserByUsername(String username) {
    UserAccount account = userAccountMapper.selectOne(
            Wrappers.<UserAccount>lambdaQuery().eq(UserAccount::getUsername, username));  // WHERE username = ?
    ...
    return new User(String.valueOf(account.getId()), account.getPasswordHash(), ROLE_USER);
    //              ↑↑↑ 注意这里:principal 的 name 存的是【数据库 id】,不是 username!
}
```

> **💡 深水点(面试高分)**:登录成功后,Spring Security 内部记住你的那个"身份令牌"(principal 的 name)存的**既不是 username 也不是 display_name,而是数据库主键 `id`**。所以系统里其实有**三层身份**:
> - `username` → 给人用,登录打的
> - `id` → 给系统用,`CurrentUser.requireId()` 拿它做"这条数据是不是你的"授权(`owner_user_id = ?`)
> - `display_name` → 给读者用,卡片上显示的
>
> **面试官问"你 Service 里怎么拿当前用户 id"**,你答:"从 SecurityContext 拿 principal,那里存的是 user id 不是 username,直接用于行级授权,前端传什么 owner id 我都不信"——这就比"我从 session 拿用户名再查一次库"高一档。

**本课用哪个?** 卡片显示用 `display_name`(你截图里的 Alice/Bob/Carol 就是它)。`username` 卡片上**不露**。

## 二、线1【查作者】:从 `owner_user_id` 到 `AuthorView`

### 1. 问题:post 表只存了个数字

L06 建的 `post` 表,作者信息只有一列 `owner_user_id`(比如 `1`)。卡片要显示"Alice",就得拿这个 `1` 去 `user_account` 表查出 `display_name='Alice'`。这就是"翻译"。

### 2. `AuthorView` 是什么?(本课新建的 DTO,先认识它)

**DTO**(Data Transfer Object,数据传输对象)= 专门用来"装数据发给前端"的壳子。`AuthorView` 就是"一个作者在卡片上需要的所有信息"。看 [AuthorView.java](backend/src/main/java/com/agentlog/forum/api/dto/response/AuthorView.java):

```java
public record AuthorView(
        String authorType,     // "OWNER"(人类作者)。以后有 AGENT(机娘作者)
        Long userId,           // 作者的 user_account.id
        Long agentId,          // 机娘 id(本课人类作者,恒 null)
        String displayName,    // 展示名 "Alice"
        String avatarMediaId,  // 头像的媒体 id(线3 用,细讲见下)
        boolean deleted        // 是否已注销
) {
    // 两个"静态工厂方法"—— 就是两个方便的构造快捷方式:
    public static AuthorView owner(Long userId, String displayName, String avatarMediaId) {
        return new AuthorView("OWNER", userId, null, displayName, avatarMediaId, false);
    }
    public static AuthorView deletedOwner(Long userId) {   // 注销用户的占位:名字变"已注销",头像清空
        return new AuthorView("OWNER", userId, null, "已注销", null, true);
    }
}
```

> **背景注解 · `record` 是什么**:Java 16+ 的语法,一行声明一个"只读数据类",自动生成构造器、getter。适合 DTO 这种"造出来只读不改"的数据。(对照:DO 数据对象用普通 class,因为要 setXxx 分步赋值。)

> **背景注解 · 为什么 forum 自己建 `AuthorView`,不直接用 identity 模块的 User 类?** 这是模块化铁律:forum 模块**不许 import identity 模块的内部类**(否则模块边界被打破,`ModularityTest` 会判红)。forum 要展示作者,就自己定义一个"只含展示字段"的投影 `AuthorView`,然后用自己的 SQL 直查 `user_account` 物理表。**读别人的数据 → 自建投影直查表;写别人的数据 → 才走 Facade**。这叫"读写不对称",是 L07 就立下的规矩。

### 3. 批量查 SQL:一次 `IN` 查回一页所有作者

看 [PostFeedMapper.xml](backend/src/main/resources/mapper/forum/PostFeedMapper.xml) 的这段(线1+线2 的地基):

```xml
<select id="selectAuthorsByUserIds" resultType="...AuthorLookupRow">
    SELECT id AS user_id, display_name, avatar_media_public_id AS avatar_media_id, status
    FROM user_account
    WHERE id IN
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</select>
```

- `WHERE id IN (1, 3, 4)` —— **一次**把这一页所有作者查回来,不是一个一个查。
- `avatar_media_public_id AS avatar_media_id` —— 把库里的列名改个名喂给 Java 字段 `avatarMediaId`(线3 的头像 id 就在这被查出来了)。
- 查回来的一行装进 `AuthorLookupRow`(一个只用于"读"的行对象,含 userId/displayName/avatarMediaId/status)。

> **背景注解 · `<foreach>`**:MyBatis 的标签,把 Java 传进来的 `ids` 集合展开成 `(1,3,4)` 这种 SQL 片段。没有它你没法动态拼 `IN` 列表。

## 三、线2【防 N+1】:那两句 Map 代码逐字拆解(你卡住的地方)

这是你问得最多、也是最该讲透的。先说结论:**`authorMap` 是字典(Map),`author` 是从字典里取出的一个值(单个 AuthorView)。你把这俩搞混了,是因为之前没人给你拆。**

### 先讲背景:什么是 N+1?

**N+1 问题** = "查 1 次列表 + 对列表里每一条再各查 1 次" = 1+N 次数据库往返。一页 20 篇帖:

```
❌ 笨办法(N+1):
  查 20 篇帖              → 1 次 SQL
  第1篇: 查它作者          → +1
  第2篇: 查它作者          → +1
  ... 共 20 次查作者
  合计 1 + 20 = 21 次 SQL —— 数据库连接池被打爆,页面卡
```

躲法:**把 20 篇帖的作者 id 收集起来,一次 `IN` 查回来,在内存里做成"字典"随用随取。**

### 第一句:把 List「压」成字典 Map

[FeedService.java:42](backend/src/main/java/com/agentlog/forum/application/FeedService.java#L42):

```java
Set<Long> ownerIds = rows.stream().map(PostFeedRow::getOwnerUserId)
        .filter(Objects::nonNull).collect(Collectors.toSet());   // ① 收集本页所有作者id,去重

Map<Long, AuthorView> authorMap = ownerIds.isEmpty() ? Map.of() :
        postFeedMapper.selectAuthorsByUserIds(ownerIds).stream()  // ② 一次 IN 查回 List<AuthorLookupRow>
                .collect(Collectors.toMap(                        // ③ 把 List 压成 Map
                        AuthorLookupRow::getUserId,               //    key   = userId
                        this::toAuthorView));                     //    value = 转成 AuthorView
```

逐块看:
- **①** `ownerIds` = 这一页所有帖子的作者 id,去重后的集合。比如 `{1, 3, 4}`。
- **②** `selectAuthorsByUserIds({1,3,4})` = 一次 SQL 查回 `List<AuthorLookupRow>`(3 行,每行一个作者)。
- **③** `Collectors.toMap(keyFn, valueFn)` = **把 List 变成 Map 的收集器**。它遍历每一行,用 `keyFn` 算出 key、`valueFn` 算出 value,组装成字典。这里:
  - key = `AuthorLookupRow::getUserId`(拿这行的 userId)
  - value = `this::toAuthorView`(把这行转成 AuthorView,顺便处理注销逻辑)

> **背景注解 · `Collectors.toMap`**:Java Stream 的收集器,签名 `toMap(键函数, 值函数)`。作用是"List → Map"。
> **背景注解 · `this::toAuthorView` 这个 `::`**:方法引用,等价于 `row -> this.toAuthorView(row)`。就是"对每行调用 toAuthorView 方法"。

结果 `authorMap` 长这样(真实数据):
```
{ 1 → AuthorView(OWNER, "Alice", 头像id, ...),
  3 → AuthorView(OWNER, "Bob",   头像id, ...),
  4 → AuthorView(OWNER, "Carol", 头像id, ...) }
```
**这就是一本"输入 userId、输出作者视图"的字典。**

`toAuthorView` 干的活([FeedService.java:65](backend/src/main/java/com/agentlog/forum/application/FeedService.java#L65)):
```java
private AuthorView toAuthorView(AuthorLookupRow row) {
    if (!"ACTIVE".equals(row.getStatus())) {          // 注销/封禁用户
        return AuthorView.deletedOwner(row.getUserId());  // → "已注销"占位,头像清空
    }
    return AuthorView.owner(row.getUserId(), row.getDisplayName(), row.getAvatarMediaId());  // 正常作者
}
```

### 第二句:从字典里按 key 取一个值

[FeedService.java:52](backend/src/main/java/com/agentlog/forum/application/FeedService.java#L52),在**遍历每张卡片**的循环里:

```java
AuthorView author = authorMap.getOrDefault(row.getOwnerUserId(), AuthorView.deletedOwner(row.getOwnerUserId()));
```

- `row` = 当前这篇帖。`row.getOwnerUserId()` = 这篇帖的作者 id(比如 `3`)。
- `authorMap.getOrDefault(k, d)` = **字典里有 key `k` 就返回它的值,没有就返回兜底 `d`**。
- 所以 `author` = 从字典里按 `3` 取出的那个 `AuthorView`(Bob)。**它是单个 AuthorView,不是 Map!**
- 兜底 `d = deletedOwner(...)`:万一某作者不在字典里(比如被删了、没查到),给个"已注销"占位,卡片不至于崩。

> **背景注解 · `getOrDefault(key, default)`**:Map 的方法。查得到返回对应 value,查不到返回你给的默认值(而不是 null)。省掉了 `if (map.containsKey(k)) ... else ...` 的啰嗦。

> **🎯 回答你的原话疑问**:"为什么这两句使得 author 能接收一个 Map?" —— **`author` 没接收 Map**。第一句造了一本字典 `authorMap`(Map 类型);第二句从字典里**取出一个值**赋给 `author`(AuthorView 类型)。字典是中间的"查找加速结构",`author` 是从里面掏出来的一个作者。你被"authorMap"和"author"这俩长得像的名字绊住了,这是命名没帮上忙 + 之前没拆开讲的锅,不是你的问题。

### 为什么非得先做字典?

因为要 **O(1) 查表**。一页 20 篇帖循环拼卡片,每张卡 `getOrDefault` 是常数时间。不做字典的话:要么每张卡再查一次库(N+1),要么在 List 里线性 `find`(每张 O(n),整体 O(n²))。字典是"用一点内存换查表速度"。

> **面试官会这么追**:"Feed 一页多篇帖,作者名怎么查才不打爆数据库?"
> **满分答**:"收集本页所有 `owner_user_id` 去重,一次 `IN` 批量查作者,用 `Collectors.toMap` 在内存做成 `Map<userId, AuthorView>` 查找表,每张卡片 `getOrDefault` 是 O(1)。分区名、标签也这套。全页恒定 3~4 条 SQL,与帖子数量无关。"
> 再补一刀显深度:"这是典型的**读多写少场景的批量化**,和 ORM 的 `@BatchSize`、GraphQL 的 DataLoader 是同一个思想——把 N 次单点查询合并成 1 次批量查询。"

## 四、线3【接头像】:本课最大的坑——头像其实**没接线**

你的直觉极准:"感觉展示时没对头像有用到啊"。**对,前端确实没用它。** 这是个真实缺口,不是你看漏了。

### 头像本该怎么流动(设计意图)

```
user_account.avatar_media_public_id  ("med_xxx" 或 NULL)
   │ SQL: avatar_media_public_id AS avatar_media_id
   ▼
AuthorLookupRow.avatarMediaId
   │ toAuthorView → AuthorView.owner(userId, displayName, avatarMediaId)
   ▼
AuthorView.avatarMediaId ──进字典──进 PostCardView.authors──> JSON 吐给前端
   │ 前端【本应】: <img src="/api/v1/public/media/{avatarMediaId}">
   ▼
GET /public/media/med_xxx (L11 的端点) → 302 重定向 → MinIO 吐真图
```

**关键澄清 · `avatarMediaId` 是什么?** 它**不是** MinIO 的 URL,是 **media_object 表的 `public_id`**(那个 `med_xxx` 字符串)。前端要拿它拼成 `/api/v1/public/media/med_xxx` 这个地址,浏览器请求这个地址,后端(L11 的 `PublicMediaController`)再 302 重定向到 MinIO 的真图。

### 坑在哪:前端只画了首字母

看 [PostLogCard.vue:35](web/src/components/PostLogCard.vue#L35):

```vue
<span class="avatar" :title="author.displayName">
  {{ initials(author.displayName) }}   <!-- ← 只取 displayName 首字母!avatarMediaId 被无视 -->
</span>
```

`initials('Alice')` = `'A'`。所以**现在所有头像都是首字母色块**(你截图里的 A/C/B),`avatarMediaId` 是"流到了前端却没人用"的死字段。

**"头像没被利用到"的真相**:后端一路把 `avatarMediaId` 带到了 `PostCardView`,一点没漏;是**前端 `PostLogCard.vue` 没写 `<img>` 那段**。后端的活是对的,前端的活缺一块。

### 该怎么补(L10→L11 的桥)

前端 avatar 那段应该是:
```vue
<span class="avatar" :title="author.displayName">
  <img v-if="author.avatarMediaId" :src="`/api/v1/public/media/${author.avatarMediaId}`" />
  <template v-else>{{ initials(author.displayName) }}</template>  <!-- 没头像才回退首字母 -->
</span>
```
补上这段,你在 L11 上传的头像才会真的显示在 Feed 卡片上。**这正是 L10(产出头像 id)和 L11(提供媒体读端点)的接缝。**

> **两个诚实的现状**:① 种子用户 `avatar_media_public_id` 全是 NULL(没人传过头像),所以就算前端接了 `<img>`,现在也还是回退首字母——要先有人上传头像(L11)才看得到效果;② 这段前端接线是个**该补的活**。要不要我把它接上(你写我审)?接了之后,"上传头像 → Feed 卡片显示真图"就闭环了,L11 的媒体端点也第一次有了看得见的用途。
