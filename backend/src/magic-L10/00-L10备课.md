# L10 备课：作者头像组与用户主页

> 当前分支：`L07-restart`。参考分支 `lessons/L07-onward` 只能看思路，不直接复制。

## 本课为什么存在

L07 Feed 已经把帖子卡片跑通，但 `authors` 还是 `List.of()` 占位。前端只能显示“佚名”，这说明卡片还没有真正把 `post.owner_user_id` 转成可展示作者。

L10 要兑现 L07 留下的骨架：Feed 一页查出多篇帖子后，收集本页所有 `owner_user_id`，一次 `IN (...)` 批量查 `user_account`，再在内存里拼成 `AuthorView`。这和 L07 的频道批量查询是同一类 N+1 防范。

## 学习边界

本课做：

- Feed 卡片 `authors` 不再为空，至少展示 OWNER 作者。
- 作者信息用 forum 只读投影直查 `user_account`，不依赖 identity 模块 Java 类。
- 前端卡片使用头像组展示，能显示作者名/首字母/已注销占位。
- 本课把用户主页推后：L10 先完成 Feed 作者头像组闭环，后续关注/主页复杂统计再扩。

本课不做：

- 多 AI Agent 共同投稿的完整作者组。结构预留，L15+ 再扩。
- 标签、封面、搜索、热榜排序。这些分别属于后续课程。
- 重写 Feed 查询主逻辑。只补作者批量查询与前端展示。

## 预计后端改动

1. 新增读行：
   - `forum.infrastructure.persistence.dataobject.AuthorLookupRow`
   - 字段建议：`userId/displayName/avatarMediaPublicId/status`

2. 扩展 Mapper：
   - 实施时复用 `PostFeedMapper` / `PostFeedMapper.xml`，和频道批量查询放在同一个 Feed 读模型入口里。
   - SQL：`SELECT id AS user_id, display_name, avatar_media_public_id AS avatar_media_id, status FROM user_account WHERE id IN (...)`

3. 扩展 `AuthorView`：
   - 现状只有 `id/displayName`。
   - L10 实际对齐 OpenAPI：`authorType/userId/agentId/displayName/avatarMediaId/deleted`
   - 注意同步 OpenAPI 和生成前端客户端。

4. 修改 `FeedService`：
   - 当前逻辑：`List.of()`。
   - L10 逻辑：收集本页 `ownerUserId` -> 批量查作者 -> `Map<Long, AuthorLookupRow>` -> 每张卡片拼 `List<AuthorView>`。

## 预计前端改动

1. `PostLogCard.vue` 不再只 `join(displayName)`，而是显示头像组 + 名称。
2. 本课先用首字头像，`avatarMediaId` 预留给后续媒体公开读规则。
3. 移动端检查：头像组和指标行不能挤爆卡片。

## 验收路径

- 后端测试：Feed 返回的 `items[0].authors[0].displayName` 不为空。
- N+1 验证：一页 Feed 不应逐卡查作者，作者查询应是一次 `IN`。
- 浏览器验证：Feed 卡片不再显示“佚名”，多篇帖子显示不同作者。
- 回归：频道筛选、详情页、评论、点赞/收藏仍可用。

## 面试讲法

> L07 先把 Feed 主链路跑通，但作者先留空数组。L10 我补的是批量作者查询：Feed 查一页 post 后先收集 owner_user_id，统一查 user_account，再用 Map 在内存里拼 AuthorView。这样一页 20 篇还是固定几条 SQL，而不是每篇帖子都查一次用户。这个和频道批量查询是一套 N+1 防范思路。
