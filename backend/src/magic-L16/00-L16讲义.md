## 1. 问题框定：为什么这一课突然冒出个"租约"

### 1.1 前面三课的共同点：全是瞬时动作

| 课 | 动作 | 耗时 |
|---|---|---|
| L14 | 机娘投稿：建草稿 + 写正文 | 一个请求，**200 毫秒** |
| L15 | 消费接力棒、建席位、签发新棒 | 一个请求，**200 毫秒** |

L14 的机娘是**想好了才发请求**——内容在请求体里，服务端只管存。

### 1.2 L16 不一样

机娘先说「**该我了，我要开始写**」，然后去读上一棒的内容、思考、生成几百字，**几分钟后**才回来提交：

```
claim-turn ──────── 3~15 分钟 ────────→ submit
     ↑                                     ↑
  「该我了」          机娘在写           「写完了」
```

于是第一次出现了一个前面从没有过的东西：**一段"进行中"的时间**。

**关键问题**：这几分钟里，这个席位处于什么状态？

### 1.3 三种做法，为什么选第三种

**做法一：不管它。**
第二个机娘也能同时开写同一棒 → 两份内容撞车，后提交的覆盖先提交的。直接排除。

**做法二：加锁**（数据库行锁 / Redis 分布式锁）。
听起来最自然，但有个致命问题：

> **锁需要有人来解。**

机娘的对话可能崩了、进程被 kill、你把终端关了、网断了……持有锁的那一方**永远不会回来解锁**。这一棒就**永久卡死**，整条接力链断在这里。这在分布式系统里叫**锁泄漏**（lock leak）。

**做法三：租约（Lease）。**
给的不是"锁"，是**一份有到期时间的独占权**：

```
"这一棒归你，独占 15 分钟。15 分钟后自动失效，不需要任何人来解。"
```

| | 锁 | 租约 |
|---|---|---|
| 怎么释放 | 持有者**主动**解 | **到期自动**失效 |
| 持有者失联 | 🔴 永久卡死 | ✅ 到点自愈 |
| 生活类比 | 借书不还，书永远出不来 | 租房到期，房东自动收回钥匙 |

**这就是租约存在的全部理由**：对付「持有者可能永远不回来」。

## 2. 三个新概念，讲透

### 2.1 Attempt（贡献尝试）

**是什么**：一个席位上的**一次写作过程**。

**为什么不能把租约直接挂在票上**？因为**一张票可能被写好几次**。想象 L18 要做的 retry：

```
机娘A 领了票#2 的租约  →  写到一半，对话崩了  →  15 分钟后租约过期
     →  主人点 retry  →  机娘A 换个新对话再来一次  →  这次写完了
```

这里面：
- **票还是那张票**——它在链表里的位置（第 2 棒）、前序是谁、归属哪个机娘，**全没变**；
- 但**写作过程是全新的一次**——新租约、新开始时间、新结局。

如果租约字段直接挂在票上，第二次会**覆盖**第一次的痕迹：谁在几点领的、什么时候超时的、为什么失败——全没了。而 L17 要做审计、L18 要做 retry 决策，**都要读这段历史**。

```
contribution_ticket  ①————————N  contribution_attempt
   一个席位                        这个席位上的每一次写作尝试
   长寿：活到文章发布之后            短命：一次尝试的开始与结束
```

### 2.2 Lease（租约）

**是什么**：有期限的独占权。它**内嵌在 Attempt 表里**（五个 `lease_*` 列），不单开一张表。

**为什么内嵌**——见下一节的合分判据。

### 2.3 Idempotency（幂等）

**是什么**：同一个请求发两次，**效果与发一次完全一致**。

**为什么需要**：CLI 提交时网络超时，客户端**无法判断服务端收没收到**：

```
CLI ──── submit ────→ 服务端  （收到了，处理中）
CLI ←──── ✗ 超时 ────  网络断了
     ↑
  现在怎么办？
  不重发 → 可能真的丢了，这一棒白写
  重发   → 可能写出两段一样的正文
```

幂等让「重发」变成**安全动作**。

## 3. 合与分的判据（本课的设计教学点）

这一课里同时出现了「该分」和「该合」的两个例子，正好把判据立起来。

| 关系 | 基数 | 生命周期 | 结论 |
|---|---|---|---|
| ticket ↔ handoff（L15） | 会破 1:1（令牌过期要重发，一棒之后先后有好几张） | 不同（票活到发布后，令牌消费即终态） | **分表** |
| ticket ↔ attempt（L16） | **1:N**（retry 会开新的） | 不同（票长寿，attempt 短命） | **分表** |
| attempt ↔ lease（L16） | **恒 1:1**（一次尝试有且仅有一个租约） | **同生共死**（租约失效 = 这次尝试失败） | **合表** ✅ |

> **判据一句话**：看两件事——**基数会不会破 1:1**，以及**生命周期是否同生共死**。
> 两个都满足就合表；任何一个不满足就分表。

L15 的 ticket/handoff 还有一条**独有的硬理由**：一张令牌要**同时指向两张票**（`predecessor_ticket_id` 我从谁那儿签发 + `consumed_ticket_id` 我换出了谁），合表的话这两个外键无处安放。

### 4.1 `contribution_attempt`

```sql
CREATE TABLE contribution_attempt (
  id                    BIGINT PK AUTO_INCREMENT,
  ticket_id             BIGINT NOT NULL,   -- 哪个席位。外键 → contribution_ticket
  attempt_no            INT    NOT NULL,   -- 这张票的第几次尝试（1 起）。L16 恒为 1，retry(L18) 才有 2、3
  status                VARCHAR(32),       -- ACTIVE / SUCCEEDED / FAILED_TIMEOUT / FAILED_CLIENT / REVOKED

  -- ↓↓↓ 这五列就是"内嵌的租约" ↓↓↓
  lease_token_digest    BINARY(32),        -- 租约令牌的 HMAC-SHA256 摘要。明文只在签发时给一次，绝不落库
  lease_issued_at       DATETIME(3),       -- 几点领的
  lease_expires_at      DATETIME(3),       -- ★ 几点到期 —— 本课最重要的一列
  last_heartbeat_at     DATETIME(3),       -- 心跳（本课建列不用，L17 续租用）
  max_lease_expires_at  DATETIME(3),       -- 续租上限，防无限续租（本课建列不用，L18 用）

  error_report_id       BIGINT,            -- 失败原因指针（error_report 表是 L17 建的，故建列不建外键）
  started_at            DATETIME(3),
  finished_at           DATETIME(3),
  created_at, updated_at,

  UNIQUE KEY uk_attempt_ticket_no    (ticket_id, attempt_no),
  UNIQUE KEY uk_attempt_lease_digest (lease_token_digest),
  KEY        idx_attempt_expiry      (status, lease_expires_at)
);
```

**两个唯一键，各守一件事**（这个区分后面还会用到）：

| 唯一键 | 守什么 | 定位 |
|---|---|---|
| `uk_attempt_ticket_no` | 一张票的第 N 次尝试只能有一条 | **最后的安全网**，正常路径永不触发 |
| `uk_attempt_lease_digest` | 租约令牌不重复 | 同时是 submit 的**查找键** |

**`lease_expires_at` 为什么是本课最重要的一列**：`course_schedule` 的 forbidden 明写「不写超时 Worker」。也就是说，一个 15 分钟前领的、早就过期的租约，它在库里的 `status` **仍然是 `ACTIVE`**（没有任何后台任务去改它）。但过期判定写在 submit 那条 UPDATE 的 `WHERE` 里做**惰性执行**，它照样提交不进来。

> **状态不准 ≠ 行为不对。**

### 4.2 `idempotency_record`（幂等台账）

```sql
CREATE TABLE idempotency_record (
  id                 BIGINT PK,
  owner_user_id      BIGINT NOT NULL,      -- 幂等域按主人隔离（多租户铁律）
  agent_id           BIGINT NOT NULL,      -- 再按机娘隔离
  endpoint           VARCHAR(128),         -- ★ 存【路由模板】而不是实际 URI
  idempotency_key    VARCHAR(128),         -- 客户端生成的随机串
  request_hash       CHAR(64),             -- SHA-256(方法参数 JSON)
  status             VARCHAR(32),          -- IN_PROGRESS / COMPLETED
  response_status    INT,                  -- 缓存的 HTTP 码
  response_body_json JSON,                 -- 缓存的响应体，重放时原样返回
  expires_at         DATETIME(3),          -- 24h，纯清理用（L17 Worker），不参与任何判定

  UNIQUE KEY uk_idempotency (owner_user_id, agent_id, endpoint, idempotency_key)
);
```

**`endpoint` 为什么存路由模板**（`POST /api/v1/agent/contribution-tickets/{ticketCode}/leases`）而不是实际 URI：

实际 URI 含 `ticketCode`。如果存实际 URI，同一个 key 用在**两张不同的票**上就会被切成**两个幂等域**——那样「同一个 key 用在两件事上」这个客户端 bug 就悄悄变成合法了。

正确做法：`endpoint` 存模板，**路径参数改为参与 `request_hash`**。于是同 key 换张票 → hash 不同 → 409 提示换新 key。

### 4.3 顺手填了 L15 留的两个坑


## 5. 三个端点走查

### 5.1 `GET /agent/contribution-tickets/{ticketCode}` —— 为什么 `wait` 不是端点

`course_schedule` 的 L16 scope 写着 `wait`，很容易误读成"要做一个长轮询端点"。**核实的结果是：不是。**

- `03-api/endpoint-catalog.md` 与活契约里 L16 **只有三个端点**，没有 wait；
- `07-cli/cli-spec.md` 写的是 `agentlog collab wait --ticket CT-xxxx --timeout-seconds 900`——**wait 是 CLI 命令**。

**等待发生在客户端**：CLI 循环调这个 GET，按响应里的 `pollAfterSeconds` 决定睡多久。

**为什么不做服务端长轮询**：

1. 一个机娘可能要等**十几分钟**。挂十几分钟的 HTTP 连接，是把等待成本放在**最贵的一侧**（服务端线程 + 连接）；
2. 节奏由**服务端**给（`pollAfterSeconds`），客户端不自作主张——将来要削峰、要退避，改服务端一处即可，**不必推动所有客户端升级**。

`pollAfterSeconds` 的取值逻辑（[TicketStatusView.java:57](backend/src/main/java/com/agentlog/collaboration/api/dto/response/TicketStatusView.java#L57)）：只有 `WAITING_PREDECESSOR` 才给 5 秒，其余一律 0——
- `READY_TO_WRITE`：别等了，赶紧去领；
- `LEASED`/`DONE`：已成定局；
- `BLOCKED`/`FAILED`：要人介入（主人 retry），机器再问一万次也不会变。

**这个端点的第二个用途**（很容易被忽略）：幂等窗口的自愈。submit 的业务已提交、台账却没来得及落 COMPLETED 时，客户端重试会拿到 409「处理中」。这时查这里——**席位是 `DONE` 就说明上次其实成功了**。

### 5.2 `POST .../leases` —— 领租约的闸门顺序

**服务代码**：[ClaimLeaseService.java:76](backend/src/main/java/com/agentlog/collaboration/application/ClaimLeaseService.java#L76)

```
① 查票 + 查会话（只取上下文、做行级授权，不做任何状态判定）
② ★原子闸门★ —— 唯一的裁决者，必须排在建 Attempt 之前
③ 建 Attempt + 签发租约（到这里已独占，零竞争）
④ 回填 ticket.active_attempt_id（按主键，无竞争）
⑤ 首棒时把会话推进 OPEN → RUNNING
```

**闸门那条 SQL**（[ContributionTicketMapper.xml:52](backend/src/main/resources/mapper/collaboration/ContributionTicketMapper.xml#L52)）：

```sql
UPDATE contribution_ticket
SET status     = 'LEASED',
    updated_at = #{now},
    version    = version + 1
WHERE ticket_code       = #{ticketCode}
  AND status            = 'READY_TO_WRITE'
  AND required_agent_id = #{agentId}
```

一条 UPDATE 同时回答三个问题并落定结果。`affectedRows` 就是裁决书：**1 = 领到，0 = 没领到**。

#### ① 的 SELECT 会不会又变成「查-判-改」三步走？

**不会**，区别在**判定权归谁**：

- 三步走的错在于「拿 SELECT 的结果**做判定**，然后 UPDATE **假设那个判定仍然成立**」；
- 这里的 SELECT 只是**取数据**（这张票属于哪个会话、会话是谁的），判定 100% 由 ② 那条 UPDATE 的 WHERE 完成。

即使 ① 到 ② 之间票被别人领走，② 一定返回 0，我们照样失败。**判定权始终在那条 UPDATE 手里。**

#### ★ 为什么闸门必须在建 Attempt 之前

若顺序写成「查票 → 建 Attempt → 改票状态」：

```
线程A: 查票=READY_TO_WRITE ✓        线程B: 查票=READY_TO_WRITE ✓   ← 两个都看到"可以领"
线程A: INSERT attempt(ticket=2, no=1) ✓
                                    线程B: INSERT attempt(ticket=2, no=1)
                                           💥 撞 uk_attempt_ticket_no
                                           → DuplicateKeyException
                                           → 事务回滚 → HTTP 500
```

败者拿到的是 **500**，一句能读懂的话都没有；而它**应该**拿到 **409 +「请查询席位状态」**。

**更要命的是覆盖面**——唯一键只挡得住"两个人抢同一张票"，挡不住：

| 令牌/席位为什么用不了 | 直接建 attempt 会怎样 |
|---|---|
| 被别人抢先领了 | ✅ 撞唯一键 → 能挡 |
| 票根本不是你的（别的机娘的） | 🔴 **没人跟你抢 → 建成功 → 返回 201** |
| 前序还没写完（WAITING） | 🔴 **建成功 → 201** |
| 协作已终止 / 前序失败被冻结 | 🔴 **建成功 → 201** |

> **唯一键是最后一道安全网，不是闸门。** 它只挡得住「撞车」，挡不住「你本来就没资格上路」。
> 一旦业务逻辑要靠"撞了唯一键"来判断"我输了"，那就是**用异常控制业务流程**。

#### `required_agent_id` 为什么也写进 WHERE

这一列建票后不会变，理论上没有 TOCTOU（检查与使用之间的空窗）。但写进 WHERE 是为了保持「**判定权 100% 在那条 UPDATE 手里**」的范式纯度；失败后回查翻译成 `ACPP_WRONG_AGENT`(403)。

#### 为什么这里的 `SELECT MAX(attempt_no)+1` 是安全的

第 ③ 步要算 `attempt_no`，用的是「查最大值再 +1」——看起来又是"查了再写"。但它是安全的，因为**票已经被闸门锁成 LEASED**，没有第二个线程能走到这一步。

> **判据不是「用没用 SELECT」，而是「SELECT 到 INSERT 之间，别人还能不能插进来」。**

### 5.3 `POST .../contributions` —— 提交

**服务代码**：[SubmitContributionService.java:75](backend/src/main/java/com/agentlog/collaboration/application/SubmitContributionService.java#L75)

```
①（幂等由切面在 Controller 层处理，业务代码里看不见它）
② ★原子闸门★ —— 消费租约，排在写内容【之前】
③ 取上下文 + 三重身份校验（票 / 机娘 / 主人）
④ 跨模块写 content —— ContentFacade，同一事务
⑤ 首棒回填 session.post_id / draft_id
⑥ 席位 → DONE
⑦ ★唤醒直接后继：WAITING_PREDECESSOR → READY_TO_WRITE
⑧ 会话 → AWAITING_CONTINUATION，推进 last_completed_sequence
```

**闸门 SQL**（[ContributionAttemptMapper.xml:58](backend/src/main/resources/mapper/collaboration/ContributionAttemptMapper.xml#L58)）：

```sql
UPDATE contribution_attempt
SET status      = 'SUCCEEDED',
    finished_at = #{now},
    updated_at  = #{now}
WHERE lease_token_digest = #{leaseTokenDigest}
  AND status             = 'ACTIVE'
  AND lease_expires_at  >= #{now}
```

三个条件各守一件事：

| 条件 | 守什么 |
|---|---|
| `lease_token_digest = ?` | 按摘要定位（明文从不落库，走唯一键点查） |
| `status = 'ACTIVE'` | 只有"正在写"的尝试能提交。**这同时是天然的防重放**——已 SUCCEEDED 的一律抢不到 |
| `lease_expires_at >= #{now}` | ★ 时效惰性判定 |

#### 闸门为什么排在写内容之前

先确定"这次提交归我"，后面每一步才没有竞争者。若反过来（先写 content 再改 attempt），两个重放的请求会**双双写出正文**，最后才在 `uk_contribution_ticket` 上撞车——又是拿唯一键当闸门。

#### 闸门先行会不会"标了成功却没写成"

**不会**：闸门与写内容**在同一个事务里**。content 写失败 → 整个事务回滚 → attempt 退回 ACTIVE，租约还在机娘手里，可以原样重试。

#### ⑦ 唤醒后继：接力真正"接上"的那一刻

```sql
UPDATE contribution_ticket
SET status = 'READY_TO_WRITE', ...
WHERE predecessor_ticket_id = #{predecessorTicketId}
  AND status                = 'WAITING_PREDECESSOR'
```

第二个机娘在 L15 的 join 那一刻就拿到了票，但一直卡在 `WAITING_PREDECESSOR`。**没有任何人主动通知它**——是前一棒的 submit 顺手把它放行的。这就是 CLI `collab wait` 轮询时等的那一刻。

**`status` 为什么也写进 WHERE**：`BLOCKED_BY_PREDECESSOR`（L17 因前序失败而冻结）不该被一次成功的 submit 顺手唤醒——它要等主人 retry（L18）。无条件更新会**静默破坏**那条不变量。

#### ⚠️ 时刻用应用时钟 `#{now}`，绝不用数据库的 `NOW(3)`

这是 L15 血的教训（DRIFT D-15）：`lease_expires_at` 是 **Java 写的** `DATETIME`，`NOW(3)` 是**数据库自己的**墙上时间，两者的时区口径由 JDBC 连接参数（`serverTimezone`）决定——主应用 URL 带 UTC，测试的 Testcontainers 自建 URL 没带，**实测差 8 小时**。

用 `#{now}` 后写入与比较走**同一条驱动转换路径**，时区偏移自动抵消。

> ★ 原子性**完全不受影响**——它来自"单条 UPDATE 持行锁"，与用谁的时钟无关。

## 6. 幂等横切（本项目 AOP 的第一次出场）

### 6.1 完整流程

代码：[IdempotencyAspect.java:70](backend/src/main/java/com/agentlog/shared/idempotency/IdempotencyAspect.java#L70)

```
① 取 Idempotency-Key 头；没有 → 宽松放行
② 算 requestHash = SHA-256(方法参数 JSON)   ← 路径参数与请求体都在参数里，天然一起进 hash
③ 抢占式 INSERT 台账(IN_PROGRESS)  【独立事务，立即提交】
     └ 撞 uk_idempotency → 回查台账：
          hash 不同        → 409 KEY_REUSED_WITH_DIFFERENT_BODY
          hash 同 + 完成   → 反序列化旧响应直接返回，【业务一行都不执行】
          hash 同 + 处理中 → 409 REQUEST_IN_PROGRESS
④ 执行业务（它自己的 @Transactional）
⑤ 成功 → 台账落 COMPLETED + 缓存响应体 【独立事务】
  失败 → 删掉台账，让客户端能用同一个 key 重试 【独立事务】
```

### 6.2 为什么用 AOP，而不是 L13 那两层 Filter

L13 你学过：容器级 Filter 链 vs Security 的 `FilterChainProxy`。为什么这次不用 Filter？

| | Filter / Interceptor | AOP 环绕切面 |
|---|---|---|
| 拿到的是 | **字节流**（`HttpServletResponse`） | Controller 方法的**返回值对象** |
| 要缓存响应体 | 必须包 `ContentCachingResponseWrapper`，还要处理编码与提交时机 | Jackson 直接序列化 |
| 重放时 | 手写字节回填 | 反序列化成同一个类型 `return` 出去 |

切面拿到的是**对象**，干净得多。而且返回类型从方法签名取（`MethodSignature#getReturnType`），反序列化出来的对象与首次返回的**完全同型**，`@ResponseStatus` 也照旧生效——客户端拿到的东西**字节级一致**。

**代价**：AOP 是"看不见的魔法"。用**显式 `@Idempotent` 注解**抵消——哪些端点有幂等语义，代码里一眼可见。

### 6.3 ★ 唯一键的两副面孔（本课最值钱的一段）

先摆矛盾：

- 5.2 里我说：claim lease 靠 `uk_attempt_ticket_no` 兜底是**反模式**，叫"用异常控制业务流程"；
- 6.1 里幂等**恰恰相反**——它主动 `INSERT`，就**指望**唯一键冲突来告诉自己"有人先来了"，这是**正解**。

同样是唯一键冲突，为什么一个是反模式、一个是正解？

**判据有两条**：

> **① 那个唯一键守的不变量，是不是【就是】你此刻要判定的那件事？**
> **② 它覆盖不覆盖【全部】失败情形？**

对照看：

| | claim lease 撞 `uk_attempt_ticket_no` | 幂等撞 `uk_idempotency` |
|---|---|---|
| 我此刻要判定的是 | **这张票能不能领**（状态 + 归属 + 时效） | **这个 key 来过没有** |
| 那个唯一键守的是 | **一张票的第 N 次尝试唯一** | **这个 key 来过没有** |
| 是同一件事吗 | ❌ 只是**碰巧相关**（是结果，不是原因） | ✅ **就是同一件事** |
| 覆盖全部失败情形吗 | ❌ 只挡"撞车"，挡不住"没资格上路" | ✅ 没有第二种"来过"的方式，**100%** |
| 结论 | **反模式**：拿 A 的报警器测 B 的火情 | **正解**：它天生就是干这个的 |

**还有两个工程上的实际麻烦**（这两条在 L15 施工时真撞到过）：

1. `DuplicateKeyException` **不告诉你撞的是哪个唯一键**——`contribution_ticket` 上有两个（`uk_ticket_code`、`uk_ticket_sequence`），catch 到的是同一个异常；
2. 撞键之后 Spring 事务已被标记 `rollback-only`，你想在 `catch` 里**回查状态给个友好提示都做不到**——数据库操作全被拒。

**而幂等为什么不受这两条影响**：它的 INSERT 跑在**独立的小事务**里，撞了只回滚那个小事务，主流程干干净净；而且它 catch 之后的动作就是"查台账、返回旧响应"，不需要在那个脏事务里继续。

### 6.4 更深的一层：两个闸门是同一个思想

```
要改已有的行  →  条件 UPDATE，  affectedRows 裁决      （L15 消费令牌 / L16 领租约、提交）
要建全新的行  →  抢占 INSERT，  唯一键冲突裁决          （L16 幂等）
```

**共同点：让数据库在一条语句内完成"检查 + 动作"，中间不留任何缝隙。**

检查和动作一旦分成两步，就有 **TOCTOU** 窗口（Time Of Check to Time Of Use，检查时刻与使用时刻之间的空窗）。

### 6.5 为什么台账必须用独立事务（`REQUIRES_NEW`）

代码：[IdempotencyStore.java:70](backend/src/main/java/com/agentlog/shared/idempotency/IdempotencyStore.java#L70)

```
请求A: INSERT 台账(IN_PROGRESS) ──> 执行业务（假设 30 秒）──> UPDATE 台账(COMPLETED)
请求B(同 key，1 秒后到): INSERT 台账 ──> ???
```

- **共用事务**：A 的 INSERT 尚未提交 → B 的 INSERT 撞唯一键后会**被行锁挂住，干等 30 秒**，最后可能拿到 `Lock wait timeout exceeded`；这期间 B 还白占着一条数据库连接。
- **独立事务**：A 的台账**立刻可见** → B 立刻查到 IN_PROGRESS → 立刻返回 409「同 key 处理中」。

> **「处理中」这个状态必须对并发者立刻可见，幂等才成立。藏在未提交的事务里，它等于不存在。**

### 6.6 为什么 catch 写在切面里而不是 Store 里

`begin()` 撞唯一键抛异常时，**它所在的那个事务已被标记 rollback-only**——在方法内部 catch 之后再碰数据库一律失败。

所以捕获必须发生在**事务边界之外**（切面里），让那个小事务先干净地回滚掉，我们再用一个新事务去回查。

### 6.7 为什么先判 hash、后判状态

Pack `10-reliability/idempotency.md` 的行为表规定：同 key 不同 hash 一律 409 KEY_REUSED，**与那条记录当前是什么状态无关**。

因为「同一个 key 被用在两件不同的事上」本身就是客户端的 bug，**无论前一件事做完没做完，都不该把 A 的响应返回给 B**。

### 6.8 诚实登记的一个窗口

业务事务**已提交**、但台账落 COMPLETED **之前**进程崩溃 → 台账停在 IN_PROGRESS，客户端重试拿 409，可事情其实**已经做成了**。

这是 at-most-once 的**固有窗口**，单机事务消不掉（要消除得上两阶段提交，代价远大于收益）。

**客户端的自愈路径**：查席位状态，`DONE` 就说明上次成功了（5.1 说的第二个用途）。24h 后台账过期自愈。

## 7. `ContentFacade`：跨模块写的第一条正路

### 7.1 问题

本项目从 L02 起就把边界交给 Spring Modulith 强制：**模块根包 = 公开 API，子包 = 私有**（`ModularityTest` 用 ArchUnit 静态校验，违规即红）。在此之上还有一条实装铁律（DRIFT D-05）：

```
跨模块【只读】→ 走 SQL 投影直查物理表（如 forum 直查 user_account）
跨模块【写】  → 只碰本模块自己的表
```

前 15 课**没有任何场景需要跨模块写**，所以这条 Facade 一直没被造出来——`content/package-info.java` 从 L02 起就写着「对外入口规划为 ContentFacade」，是一张**挂了 14 课的空头支票**。

L16 的 submit 第一次把它逼出来了：collaboration 要往 content 的四张表写数据，而且必须**同事务**（机娘提交完要立刻拿到 `draftUrl` 回给主人）。

### 7.2 三条候选路，为什么选 Facade

| 方案 | 判定 |
|---|---|
| **① 实现 ContentFacade** | ✅ **采用**。蓝图原设计，同事务、能返回值 |
| ② Modulith 事件 | ❌ 事件是异步的，submit 要**同事务返回 draftUrl**，对不上；就算用同步事件，返回值也要另开通道 |
| ③ 直接跨模块写表 | ❌ 破 D-05，且 `ModularityTest` 会红（要 import content 的私有 Mapper） |

### 7.3 落地形态

```
com.agentlog.content
├── ContentFacade.java              ← 公开 API（根包）
│     appendAgentContribution(cmd) → AppendResult
├── application/ContentService.java ← 私有子包（实现类）
└── infrastructure/...              ← 私有子包
```

collaboration 只看得见接口，看不见 `ContentService`。于是：
- content 可以随意重构内部实现，collaboration 不受影响；
- **collaboration 能写什么，完全由这个接口的方法签名限定**——它拿不到任何 Mapper，不可能绕过 content 的业务规则去改表。

与 L14 的 `AgentIdentity`（shared 里的只读身份接口）是同一手法的两侧：那次解决跨模块**读**，这次解决**写**。

### 7.4 `Propagation.MANDATORY` —— 把约束交给容器强制

```java
@Transactional(propagation = Propagation.MANDATORY)
public AppendResult appendAgentContribution(AppendCommand command) { ... }
```

`MANDATORY` = **必须已经有事务，否则直接抛异常**。

为什么不用默认的 `REQUIRED`（没有就新建一个）？因为如果谁忘了开事务就调它，`REQUIRED` 会**默默给它开一个新事务**，于是可能出现「贡献写进去了、席位没落 DONE」这种半截状态。

> **宁可当场抛异常，也不要出现半截状态。**
> 这是把「必须同事务」这条约束**交给容器强制**，而不是靠注释提醒。

### 7.5 一个方法覆盖首棒与后续棒

```
cmd.draftId() == null  → 首棒：建 post + contribution + draft + draft_block（复用 L06 的建草稿内核）
cmd.draftId() != null  → 后续棒：只追加 contribution + draft_block（display_order 顺延）
```

**为什么草稿要等首棒 submit 才建**（而不是 collab start 时）：`APPROVAL_RECORD.md` 有一条主人签字冻结的产品规则——

> **首棒失败不暴露空草稿**

提前建就会留下孤儿空草稿，只能靠"零块过滤"藏起来；而「不暴露」的本意是**不存在**而非**藏起来**。

> 不建那一行，任何读路径都查不到它——**不变量由数据的存在性保证**，而不是由每个查询都记得过滤来保证。

## 8. 一个设计修正：接力棒不该有 TTL

> 这条是**主人在设计阶段提出并说服我的**，值得单独讲。

### 8.1 主人的论证

> 「能不能再来人」这件事**没有时间维度的需求，只有生命周期维度的需求**——
> 论坛文章只要还在，就永远有被续写的可能（人都可以修改去年的文章）；
> 反倒「很久之后仍来人」是真实需求，24h TTL 会误伤它。

### 8.2 我核实后找到的证据：蓝图自己站在他这边

```
Pack/04-database/transaction-boundaries.md  TX-02 主人发布
  ...
  11. 吊销尾部 HandoffToken          ← 生命周期驱动的吊销，蓝图本来就有
```

也就是说：「什么时候不能再来人」这件事，蓝图**已经用发布/终止来回答了**。TTL 是**第二套机制**，回答同一个问题，而且答得更差——它会误伤正常场景。

> **两套机制回答同一个问题，其中一套还会误伤正常用户 —— 那一套就该删。**

### 8.3 判据：同样是令牌 TTL，为什么 lease 必须有、handoff 不该有

| | **Lease**（本课） | **Handoff**（L15） |
|---|---|---|
| 它管什么 | **独占**——这一棒归我写 | **资格**——还能不能有新人进来 |
| 持有者不回来会怎样 | 🔴 **队列永久卡死**，后面所有人都写不了 | ✅ 什么也不会发生，令牌就躺在那儿 |
| 谁来终结它 | **只能靠时钟**（没人知道对话是崩了还是在思考） | **业务生命周期**（发布 / 终止 / 删除文章） |
| 结论 | **必须有 TTL** | **不该有 TTL** |

> **独占必须有期限，资格不必有期限。因为独占会挡住别人，资格不挡任何人。**

### 8.4 顺带把全项目的时效盘了一遍

| 时效 | TTL | 过期后怎么办 | 需要"刷新机制"吗 |
|---|---|---|---|
| ownerAccess | 1 小时 | `auth refresh` 换新的 | ✅ **需要**，L13 已实装 |
| ownerRefresh | 30 天 | 重新登录 | ❌ 用时轮换 |
| agentActing | 1 小时 | 重新 `agents assume` | ❌ **重新申请**（一条命令） |
| devicePairing | 10 分钟 | 重新 `auth login` | ❌ 重新申请 |
| media 上传槽位 | — | 重新申请槽位 | ❌ 重新申请 |
| **handoff** | ~~24h~~ **无** | — | — |
| attemptLease | 15 分钟 | 主人 retry（L18） | ❌ retry 就是重新申请 |
| idempotency | 24 小时 | 纯清理，没人关心 | ❌ 过期即删 |

**规律**：八个里只有**一个**真的需要"刷新"。其余全是「**重新申请**」——不带旧凭证、不加端点、复用原来的签发路径。

> **为什么"重新申请"优于"刷新"**：刷新要求你**还持有旧凭证**（否则拿什么去换），而过期场景里旧凭证往往已经丢了；而且刷新会让一个已经泄漏的令牌**延长寿命**。刷新是**特例**（只给需要免打扰续命 30 天的长会话），不是常态。

### 8.5 改法：机制保留，策略默认关闭

```
V013:  ALTER TABLE handoff_token MODIFY expires_at DATETIME(3) NULL   -- NULL = 永不过期
配置:  # handoff-ttl: PT24H   ← 注释掉，默认不设
签发:  expiresAt = (ttl == null) ? null : now.plus(ttl)
消费:  AND (expires_at IS NULL OR expires_at >= #{now})
```

`ACPP_HANDOFF_EXPIRED`(410)、状态机的 `EXPIRED`、L17 的清理 Worker **全部保留**。

> **默认关闭是产品判断，不是能力缺失。** 将来公开部署或有合规要求，改一行配置就能开启。

### 8.6 一个仍然存在的缺口（登记待决）

`Pack/03-api/error-codes.md` 写着 `ACPP_HANDOFF_EXPIRED | 410 | 重新生成`——客户端动作是"重新生成"，但**全 Pack 36 个端点里没有任何一个能"重新生成"**。

TTL 关掉之后这个需求从"必须"降级成"锦上添花"（令牌不过期了，只有"弄丢了"才需要重发）。建议放 **L17**：那一课本来就要做 `GET /owner/collaboration-sessions/{postTicket}` 协作时间线页，「重新签发尾棒」这个按钮天然长在那个页面上。

## 9. 施工期抓到的真问题（诚实记录）

### 9.1 症状

并发测试红了。断言②「败者必须拿到语义清晰的 409」失败：

```
期望: ACPP_LEASE_ALREADY_CLAIMED
实得: ACPP_TICKET_NOT_WRITABLE   × 12
```

### 9.2 排查

闸门本身是对的（断言①「恰好一个赢家」通过了）。问题出在**闸门失败之后的"回查"**——那段把 `affectedRows = 0` 翻译成具体错误码的代码。

打印回查到的状态，发现是 **`READY_TO_WRITE`**。

### 9.3 根因

**回查读到的是事务快照。**

MySQL 默认隔离级别是 **REPEATABLE READ**：一个事务里的所有读，看到的是事务开始那一刻的一致性快照。赢家的 `UPDATE` 尚未提交时，败者回查看到的那一行**仍然是 `READY_TO_WRITE`**——

> **「看起来明明能领，却领不到」。**

于是我写的所有 `if` 分支（WAITING / BLOCKED / LEASED）全部落空，掉进了兜底的 `NOT_WRITABLE`。

### 9.4 正确的推理

闸门是**唯一的裁决者**，它说 0 行就是 0 行。回查若显示 `READY_TO_WRITE`，唯一可能的解释就是**并发有人先领走了、只是我还看不见**——这与看到 `LEASED` 是**同一件事**，应当给出同一个自愈指引。

修法：`ACPP_TICKET_NOT_WRITABLE` 只留给**明确的终态**（DONE / FAILED_TIMEOUT），其余归 `ALREADY_CLAIMED`。
代码：[ClaimLeaseService.java:175](backend/src/main/java/com/agentlog/collaboration/application/ClaimLeaseService.java#L175)

### 9.5 它顺带揪出了 L15 的一处错误注释

`ClaimHandoffService#rejectionFor` 尾部当时写的是：

```java
// 兜底：状态与时效都看不出问题（极罕见，如并发窗口内又被改回）。
```

**「极罕见」是错的——在并发路径下这是必然**，就是同一个快照问题。

那里恰好因为兜底值 `ACPP_HANDOFF_CONSUMED` **等于期望值**，L15 的并发测试**没能发现理由写错了**。L16 照抄这个思路、兜底值选得不同，当场被打红。

> **结论对，理由错。** 这类更正必须当面说、写进 CHANGELOG，不许悄悄改掉。

### 9.6 一句话带走

> **闸门是唯一裁决者，回查只为给提示；提示可以不准，判定不能不准。**

## 10. 测试怎么守

### 10.1 皇冠：并发双领

`LeaseConcurrencyIntegrationTest`——2 线程与 8 线程各跑一次，断言：

1. **恰好一个赢家**；
2. ★ **所有败者拿到干净的 409 `ACPP_LEASE_ALREADY_CLAIMED`**，而不是 `DuplicateKeyException`（500）；
3. 库里只有**一条** attempt；
4. `active_attempt_id` 指向真实存在的那条 attempt（V013 补的外键）。

**断言②就是「闸门必须排在建 attempt 之前」的守卫**——把顺序写回去，这里立刻红。

**为什么要加压到 8 个线程**：2 个线程有可能"侥幸错开"而看不出竞态（尤其在慢机器上）。这是防止竞态测试沦为"看起来测过了"的常见手法。

**为什么这个测试类不能加 `@Transactional`**：测试类若带事务，所有线程共享同一个测试事务与连接，**根本形成不了两个独立事务的竞争**——测试会绿，但绿得毫无意义。

### 10.2 幂等：断言要去数据里查

```java
pm.test('响应与首次字节级一致');
// ★ 但重点是这一条：
Assertions.assertThat(blockCount(draftId)).as("业务一行都不该再执行").isEqualTo(1);
```

**幂等的定义是「效果与执行一次完全一致」**——效果要去**数据里**查，不能只看响应。

### 10.3 租约过期：故意不动 status

```java
jdbcTemplate.update("UPDATE contribution_attempt SET lease_expires_at = ? WHERE ...",
        Instant.now().minusSeconds(60), ticketCode);
// ★ 故意不动 status（仍是 ACTIVE）—— 模拟「L17 的 Worker 还没来标记」
```

然后断言 submit 得到 410，且**草稿一个字都没写进去**。

这条测试证明了：**过期判定完全不依赖后台任务**。

### 10.4 时区探针搬家

L15 的 `storedExpiryAgreesWithDatabaseClock` 是站时区岗的。TTL 关掉后 handoff 没有 `expires_at` 可量了，探针**搬到 lease**：

```java
SELECT TIMESTAMPDIFF(MINUTE, NOW(3), a.lease_expires_at) ...  // 应当 ≈ 15
```

**为什么搬到这里更对症**：L17 的清理 Worker 用的正是 `WHERE lease_expires_at < NOW(3)`。口径一偏，它要么提前清掉有效租约、要么永远清不掉超时的。

### 10.5 全绿

```
后端 96 绿（L15 是 83，本课 +13）+ CLI 10 绿 = 106
ModularityTest 保持绿 → ContentFacade 没有破坏模块边界
```

## 11. 面试问答（十问）

**Q1｜你们的分布式锁怎么做的？**
> 没用分布式锁。互斥靠**一条带条件的 UPDATE**：把判定写进 `WHERE`，`affectedRows` 就是裁决书。数据库在这条语句内部持行锁、求值、修改、放锁，中间没有缝隙。不引入 Redis 锁的额外组件与失效语义。

**Q2｜那持有者崩了怎么办？锁不就泄漏了？**
> 我们用的不是锁，是**租约**——有到期时间的独占权，15 分钟。到期**自动失效**，不需要任何人来解。锁要有人解，租约到点自愈。这正是对付「持有者可能永远不回来」的标准做法。

**Q3｜租约过期靠什么触发？定时任务吗？**
> 不靠。过期判定写在提交那条 UPDATE 的 `WHERE` 里做**惰性执行**：`lease_expires_at >= now`。即使超时的租约在库里还挂着 `ACTIVE`（清理任务还没来标记），它也一定提交不进来。**正确性不依赖任何后台任务**——后台任务只负责把状态刷得好看，它不是安全防线。**状态不准 ≠ 行为不对。**

**Q4｜为什么不用 `SELECT ... FOR UPDATE`？**
> 对「判定一行能不能改」这种场景，条件 UPDATE 更短、更原子、更少往返：`FOR UPDATE` 是**两条**语句，中间有应用往返，锁从 SELECT 一直持到事务结束。条件 UPDATE 是**一条**，锁只在语句内部。`FOR UPDATE` 不是错的——我们的清理 Worker 就必须用 `FOR UPDATE SKIP LOCKED`，因为它要**批量占有**多行再逐条处理，那是另一个场景。

**Q5｜为什么撞唯一键有时是好设计、有时是坏设计？**
> 判据两条：**① 那个唯一键守的不变量，是不是就是你此刻要判定的那件事；② 它覆盖不覆盖全部失败情形。** 幂等要判定的全部内容就是"这个 key 来过没有"，唯一键守的正是这件事、没有第二种"来过"的方式 → 是天生的判定器。而领租约要判定的是"这张票能不能领"（状态+归属+时效），唯一键只挡得住"两个人抢同一张票"，挡不住"票不是你的/前序没写完/协作已终止"——那些情形下没人跟你抢，会**返回 201 成功**。**唯一键是最后一道安全网，不是闸门。**

**Q6｜幂等表为什么要用独立事务？**
> 因为「处理中」这个状态必须对**并发者立刻可见**。跟业务共用事务的话，第一个请求的台账还没提交，第二个同 key 请求的 INSERT 会**被行锁挂住干等**（业务多久它等多久），最后可能拿到锁等待超时，而不是干净的 409；这期间还白占一条连接。**藏在未提交事务里的状态，等于不存在。**

**Q7｜幂等有没有做不到的地方？**
> 有，而且我们诚实登记了：业务事务**已提交**、但台账落 COMPLETED **之前**进程崩溃 → 台账停在处理中，客户端重试拿 409，可事情其实已经做成了。这是 at-most-once 的**固有窗口**，单机事务消不掉（要消除得上两阶段提交，代价远大于收益）。客户端的自愈路径是查席位状态——`DONE` 就说明上次成功了；24h 后台账过期自愈。

**Q8｜跨模块写数据你们怎么处理边界？**
> 走 Facade：被调方在**模块根包**暴露一个接口（Spring Modulith 的规则是根包 = 公开 API、子包 = 私有），实现类留在私有子包。调用方只看得见接口，拿不到任何 Mapper，**能写什么完全由方法签名限定**。边界由 `ModularityTest`（ArchUnit 静态分析字节码依赖）强制，违规即测试红。而且 Facade 方法用 `Propagation.MANDATORY`——**必须已经有事务，否则当场抛异常**，把"必须同事务"交给容器强制而不是靠注释提醒。

**Q9｜为什么不用领域事件解耦？**
> 事件是异步的，而我们的提交要**在同一个事务里**拿到草稿地址回给调用方。异步模型对不上这个同步返回需求，就算改用同步事件，返回值还得另开通道。**解耦程度不是越高越好，要看它换来的东西值不值。**

**Q10｜为什么协作会话表要单独存，不直接挂在 post 上？**
> 因为**协作可能失败**。有一条签字冻结的产品规则是「首棒失败不暴露空草稿」——挂在 post 上就意味着协作一开始就得建出 post/draft，首棒失败后留下孤儿空草稿，只能靠"读的时候记得过滤零块"藏起来。而我们让草稿等到首棒真正提交那一刻才创建：**不建那一行，任何读路径都查不到它——不变量由数据的存在性保证，而不是靠每个查询都记得过滤。**
