# L14 单机娘 Skill 自动投稿：Chain 3 的第一个真实业务消费者

> L13 建成了四层认证模型和三条安全链，机娘（agent）拿到了 AgentActingToken——但它只能敲一个 `/agent/whoami` 试金石端点，**没有任何真实业务能力**。
> L14 让机娘真正干活：把一段开发过程写成**草稿**投进 content 模块，返回草稿 URL 给主人。
> 但有一条钉死的红线贯穿全课：**机娘绝不能自己发布**。发布权永远属于人类主人。机娘只能投草稿，主人审稿后自己发布。
> 这一课教学价值最高的不是"又加了个 POST 端点"，而是**一个业务模块如何跨模块读取另一个模块产出的身份，且不踩 Modulith 边界**——这是依赖倒置（DIP）在真实工程里的一次干净落地。

---

## 0. 这一课的定位：让 Chain 3 从"能认证"走到"能干活"

L13 的三条链是按 URL 前缀分流的：

```
/web/**    → Chain 1  web Session（有状态 + CSRF）      → 人类在浏览器里
/cli/**    → Chain 2  cli owner 令牌（Bearer，无状态）   → 主人在终端
/agent/**  → Chain 3  agent 机娘令牌（AgentActingToken） → 机娘代主人行动
```

L13 把 Chain 3 的"认证"做完了：`agent assume` 换到 AgentActingToken，令牌进 SecurityContext 变成 `AgentPrincipal`。但那时 `/agent/**` 下只有一个 `whoami` 回显身份，**没有任何真实业务**。

L14 补上第一个真实消费者：`POST /api/v1/agent/drafts`。机娘投稿建草稿，落进主人的草稿箱。这一步一旦跑通，Chain 3 就从"能证明你是谁"升级成"能代你干活"——认证模型第一次兑现了它存在的意义。

## 1. 考古：活契约漏画了 L14 的独立端点

按项目铁律，动手前先查活契约 `docs/api/agentlog-openapi.yaml`——看看 agent submit 该长什么样。结果撞到一个反常现象：

**活契约里唯一的 agent submit 是 `POST /agent/contribution-tickets/{ticketCode}/contributions`**，返回体 `SubmitContributionResponse` 带着 `ticketCode`/`ticketStatus`/`nextHandoffToken`——全是**多机娘接力**的概念。而 L14 的验收线（`course_schedule.csv` 里 `forbidden=不写多机娘接力`）恰恰要求**不碰**这些东西。

### 定性：不是设计冲突，是契约漏登记

第一反应容易是"L14 和后续课冲突了"，但这个判断得取证。三份更权威的蓝图文档一致证明**单机娘投稿是一个独立用例**：

| 权威文档 | 说了什么 |
|---|---|
| `用例到代码矩阵.md` | 把"单机娘投稿 → CLI `submit-single` → `SubmitSingleContributionService` → 关键表 draft" 与协作版"submit → `SubmitContributionService` → 幂等" **列为两个独立用例** |
| `范围与阶段.md` | 阶段 B 含"单机娘 Skill 投稿"，阶段 C 才是 ACPP 协作 |

所以真相是：**活契约作为"活文档"漏登记了 L14 的独立端点**——它只落了协作版（L16 那条绑 ticket 的），漏画了单机娘版。连 Pack 蓝图里 SKILL.md 只写 `collab submit` 也是同一种认知惯性：把"单机娘投稿"下意识当成"一个人的协作"。

### 这是同一类问题的第三次出现

这个"契约漏登记权威蓝图"的病根，前面已经见过两次：

- **D-01**：契约漏登记了 email 登录端点（L11.5）
- **D-11**：L10 在主线上整个缺席（L13.5 考古补做）
- **D-13**（本课）：契约漏画了单机娘 submit-single 端点

处置手法完全一致：**以权威蓝图为准，补画端点 + 登记 DRIFT**。不改蓝图去迁就有洞的契约，而是让契约追上蓝图。

> 💼 **面试点**：contract-first 项目里，"活契约"本身也会漂移、漏记。发现契约和蓝图打架时，先判断"谁是权威源"——课程编排文档 + 用例矩阵 + 范围阶段三方交叉印证，比一份可能滞后的 OpenAPI 更可信。定性清楚是"漏登记"而非"设计冲突"，才不会误删后续课的协作端点。

## 2. 唯一的真架构决策：机娘身份如何跨模块读取（DIP）

这一课**只有一个真正的架构决策**，但它是全课教学价值的顶点。

### 问题：content 想读机娘身份，但身份类在 identity 的私有子包里

机娘投稿要落库，`AgentDraftController` 在 **content 模块**，它需要读"当前是哪个机娘、背后是哪个主人、用什么工具、哪次运行"。而这份身份——`AgentPrincipal`——是 Chain 3 认证在 **identity 模块**产出的，住在 `identity.pairing.security`（identity 的**私有子包**）。

如果 content 直接 `import com.agentlog.identity.pairing.security.AgentPrincipal`：

```
content ──依赖──> identity 的私有子包
              ↑ 这是跨模块访问 identity 内部实现
              → Spring Modulith 的 ModularityTest 直接判红
```

Modulith 的规矩是：模块之间只能依赖对方**公开的 API 包**，不能伸手进对方的内部实现。content 直接 import identity 的私有类，就是破坏了模块边界。

### 解法：在 shared（OPEN 模块）定义只读接口，让实现类去 implements 它

这就是**依赖倒置原则（DIP）**的教科书场景——高层业务（content）不应依赖低层实现（identity 的具体类），二者都应依赖抽象。

```
              shared.security.AgentIdentity   ← 只读接口（OPEN 模块，人人可依赖）
                    ↑ implements              ↑ 依赖抽象
    identity.pairing.security.AgentPrincipal  content.api.AgentDraftController
    （实现类，identity 私有）                  （@AuthenticationPrincipal AgentIdentity）
```

三步落地：

1. 在 `shared.security` 定义只读接口 `AgentIdentity`（shared 是 OPEN 模块，任何模块都能依赖它）：

```java
public interface AgentIdentity {
    Long agentAccountId();   // 代入的机娘 id
    Long ownerUserId();      // 机娘背后的主人 id（草稿归属键）
    Long installationId();   // 发起代入的设备 id
    String sourceTool();     // 来源工具，落 contribution.source_tool
    String clientRunId();    // 本次运行 id，落 contribution.client_run_id
}
```

2. 让 identity 的 `AgentPrincipal` `implements AgentIdentity`。因为它本来就是 record，**组件访问器天然满足接口方法签名，一个字都不用多写**：

```java
public record AgentPrincipal(
        Long agentAccountId, Long ownerUserId, Long installationId,
        String sourceTool, String clientRunId) implements AgentIdentity {
}
```

3. content 的 controller 只认接口，`@AuthenticationPrincipal` 注入抽象类型：

```java
public AgentDraftResponse createDraft(
        @AuthenticationPrincipal AgentIdentity principal,   // 拿接口，不碰实现类
        @Valid @RequestBody CreateAgentDraftRequest request) { ... }
```

依赖方向倒过来了：不再是 content → identity 内部，而是 content → shared 抽象 ← identity 实现。两个业务模块都指向中立的 shared，谁也不碰谁的内部。

### 和 owner 侧 CurrentUser 的对称与差异

owner 身份为什么没这套麻烦？因为**它简单到能塞进 SecurityContext 的一个字段**：

| | owner 身份 | 机娘身份 |
|---|---|---|
| 身份内容 | 单个 `userId` | 多字段：代入了谁 / 哪台设备 / 哪个工具 / 哪次运行 |
| 载体 | 塞进 `auth.getName()`，用 `CurrentUser.requireId()` 取 | 装不进一个 name，需要一个接口对象 |
| 跨模块读取 | 直接读 principal name 字符串 | `@AuthenticationPrincipal AgentIdentity` |

owner 只有一个 id，塞进 principal name 这个字符串槽位就够了，谁都能读，天然不产生对 identity 实现类的依赖。机娘是个**多字段 record**，name 字符串塞不下，必须有个对象载体——而这个对象一旦要被别的模块读，就必须走接口抽象。**二者对称（都是"你是谁"），又因信息量不同而分道（一个塞得进 name，一个塞不进）。**

> 💼 **面试点**：跨 Modulith 模块共享"身份/上下文"这类只读数据，正解不是把实现类设为 public、也不是复制一份 DTO，而是在双方都能依赖的中立模块（shared/OPEN）定义**只读接口**，实现类去 `implements`。record 的访问器天然满足接口方法，零成本。这是 DIP 与 Modulith 边界约束的一次交汇——依赖抽象，不依赖具体，边界自然守住。

## 3. 代码复用：抽私有内核 + 参数对象，owner/agent 各薄封装

owner 建草稿和 agent 建草稿，**主体流程完全一样**：建 Post 指针 → 建 Contribution（不可变原始）→ 建 Draft 头 → 建 DraftBlock。唯一的差别是**作者维度**——谁写的、用什么工具、哪次运行、归属谁。

### 手法：DraftAuthor 参数对象 + createDraftInternal 私有内核

把"作者是谁"从主流程里收敛成一个参数对象 `DraftAuthor`（record，两个静态工厂）：

```java
private record DraftAuthor(
        AuthorType authorType, Long authorUserId, Long authorAgentId,
        String sourceTool, String clientRunId, Long ownerUserId) {

    static DraftAuthor owner(long currentUserId) {
        // OWNER：作者=当前登录用户，agent 维度全 null，归属自己
        return new DraftAuthor(AuthorType.OWNER, currentUserId, null, null, null, currentUserId);
    }
    static DraftAuthor agent(Long agentAccountId, Long ownerUserId, String sourceTool, String clientRunId) {
        // AGENT：作者=代入的机娘，带 tool/runId，归属机娘背后的主人
        return new DraftAuthor(AuthorType.AGENT, null, agentAccountId, sourceTool, clientRunId, ownerUserId);
    }
}
```

主流程收进私有内核，owner/agent 两条路各拼一个 DraftAuthor 后调它：

```java
@Transactional public DraftView createOwnerDraft(long currentUserId, CreateOwnerDraftRequest req) {
    return createDraftInternal(DraftAuthor.owner(currentUserId), req.title(), ... , req.declaredExternalAiContent());
}
@Transactional public DraftView createAgentDraft(AgentIdentity principal, CreateAgentDraftRequest req) {
    DraftAuthor author = DraftAuthor.agent(principal.agentAccountId(), principal.ownerUserId(),
                                           principal.sourceTool(), principal.clientRunId());
    return createDraftInternal(author, req.title(), ... , false);  // 机娘投稿 AI 标识固定 false，见第 6 节
}
```

### 为什么不是"从零抽象一个统一入口靠令牌类型分流"？

一个看似更"高级"的方案：只留一个 `POST /drafts`，进来后判断令牌类型，是 owner 令牌就当主人、是 agent 令牌就当机娘。**这个方案被否了**，理由三条：

1. **要重构已冻结的 owner 端点**（L06 就冻结了 `/owner/drafts`），动冻结面成本高、风险大。
2. **把认证关注点漏进业务层**——业务代码里去 `if (令牌是agent)` 判身份类型，等于把"你是谁"的认证判断和"做什么"的业务逻辑搅在一起，违反关注点分离。
3. **抽象价值要到 L15 多机娘接力才显现，现在抽 = 猜未来**。当前只有 owner/agent 两条路且高度对称，一个私有内核 + 参数对象就够；真到多机娘要幂等、要 ticket 时再抽统一入口也不迟。**提前抽象是在为想象中的需求埋复杂度。**

而且——**URL 前缀分流（`/agent/**` vs `/owner/**`）本来就是 L13 拆三条链的设计意图**。每条链一个入口、各表各的作者维度、底层查询复用一份，这正是三链设计的正向兑现。镜像既有 owner 链路，就是在兑现 L13 已经画好的架构，而不是另起炉灶。

> 💼 **面试点**：复用的正确姿势是"抽稳定的公共内核 + 参数化易变部分"，不是"造一个万能入口靠类型分流"。后者把认证判断漏进业务层、且要动冻结接口。抽象的时机要等到第二、第三个真实变体出现（L15 多机娘）——**在只有两个对称变体时就抽统一层，是在猜未来、埋复杂度**。

## 4. 为什么机娘无 publish：发布权永远属主人

这是全课钉死的安全红线（`course_schedule` 硬验收线「Agent 无 publish」），从三个层面守住：

**端点层**：`/agent/**` 下**只暴露建草稿一个动作，绝无 publish 端点**。发布只在 owner 的 `POST /owner/drafts/{id}/publish`。机娘在协议上就没有"发布"这个动词可调。

**归属层**：agent 建的草稿，`draft.owner_user_id` 填的是 **`principal.ownerUserId()`——机娘背后的那个主人**，不是机娘自己。于是这篇稿天然落进该主人的草稿箱：

```java
// createDraftInternal 里
post.setOwnerUserId(author.ownerUserId());    // agent 时 = principal.ownerUserId()
draft.setOwnerUserId(author.ownerUserId());
```

而 owner 侧的 `getDraft`/`publish` 都有**行级归属校验**：

```java
if (!draft.getOwnerUserId().equals(currentUserId)) throw new ApiException(ApiStatus.DRAFT_FORBIDDEN);
```

所以机娘投的稿，只有它背后的主人能在 `/owner/drafts/{id}` 里看、能审、能发。**归属键对齐了既有的租户隔离，不用新写一行权限代码，隔离就成立了。**

**作者层**：`contribution.author_type=AGENT` + `author_agent_id`/`source_tool`/`client_run_id` 忠实落库——这篇是哪个机娘、用什么工具、哪次运行写的，全程可追溯。主人审稿时一眼看清"这是我的机娘代笔的"。

三层合起来：机娘能写，写进主人的箱子，署机娘的名，但**按不下发布键**。人类始终是最后那道闸。

> 💼 **面试点**：给 AI/agent 授予业务能力时，安全边界要"能力最小化 + 归属对齐"两手抓。能力最小化=协议层根本不暴露高危动作（无 publish 端点，不是"有端点但校验拦住"）；归属对齐=让 agent 产出的数据天然落进"背后人类"的隔离域，复用既有的行级权限，而不是新造一套 agent 专属权限模型。

## 5. 草稿 URL 与 CLI/Skill 链路：机娘投完把地址交回主人

机娘投稿后，`AgentDraftController` 拼一个**草稿审稿预览地址**回给主人：

```java
String draftUrl = webBaseUrl + "/#/owner/drafts/" + draft.draftId();
return new AgentDraftResponse(draft, draftUrl);
```

`webBaseUrl` 走 `application.yml` 的 `agentlog.web.base-url` 配置 + 环境变量覆盖（仿 L12 `verification-uri` 的可配思路）。为什么指向 owner 审稿预览路径、而不是公开帖页？**因为草稿还没发布，根本没有公开页**——URL 必须指向主人能审稿的那个内部预览路由。

整条链路串起来（Skill → CLI → 后端 → 主人）：

```
Skill（SKILL.md）：收集证据 → 按模板以机娘人格写正文落盘 contribution.md
   ↓ 调
CLI（agentlog submit --file contribution.md --title ... --channel ...）
   ↓ 带 acting token POST
后端 /api/v1/agent/drafts（Chain 3）→ 落库 → 返 { draft, draftUrl }
   ↓ CLI stdout 出机器可读 JSON（含 draftUrl，绝不含 token）
Skill 读 draftUrl → 回给主人，并提醒"这仍是草稿，需你审稿后发布"
```

CLI 侧沿用 L13 的安全铁律，`SubmitCommand` 里体现得很清楚：

- **正文走 `--file`**（对齐 Pack 蓝图 `--file contribution.md`）：长文走文件更实用，也便于 Skill 落盘证据后投递。
- **作者身份不进请求体**：`CreateAgentDraftRequest` 只有 `{title, channelId, content, summary?}`，作者维度全由服务端从 acting token 派生——**防客户端伪造作者身份**（同 owner 侧 currentUserId 从 Session 派生的思路）。
- **stdout 机器可读 JSON / stderr 人类诊断 / 绝不打印 token**：成功时 stdout 只出 `{status, draftId, draftUrl}`，token 只在本地凭证文件里。
- **令牌失效不绕过服务端**：agent 令牌短命且无 refresh，过期就提示重新 `agent assume` 拿新令牌，不做本地续期。

Skill（`skill/agentlog/SKILL.md`）是从 Pack 蓝图**裁出的单机娘版**——`Preconditions`（auth status → login → agents list → 主人选机娘 → assume）→ 收集证据 → `submit` → 返回 draftUrl → 提醒审稿。**所有 `collab start/join/wait/claim-turn` 全部剔除**，那是 L15 ACPP 的能力。

> 💼 **面试点**：让 AI 客户端发起的写操作，作者/归属身份必须**服务端从令牌派生，绝不信任请求体**。请求体里能传的只有内容（title/content/channel），"谁写的"由认证上下文说了算——这和 web 表单不传 userId、从 Session 取是同一条铁律，防的是越权伪造。

## 6. 两个"提前/推迟"的编排巧思

### 零迁移：contribution 表字段 V005 早就预留了

机娘投稿要落 `author_agent_id`/`source_tool`/`client_run_id` 三个字段——**这些字段在 V005 建 contribution 表时就建好了**，当时注释标"L15+ 用"。本课按 `course_schedule` 提前到 L14 启用，**一行 DDL 迁移都不用写**，只把注释从"L15+"更正为"L14 启用"。

这是"schema 前瞻设计"的红利：建表时把可预见的字段一次备齐，真用到时零迁移。当然前提是这些字段确实在蓝图里可预见——不是无脑加字段，是照着用例矩阵备的。

### AI 内容标识本课不碰，推迟到 L20

机娘投稿建草稿时，`declaredExternalAiContent` 固定填 `false`，publish 时 `content_origin` 依旧写死 `HUMAN_ONLY`——**本课不推导 AI 参与标识**。

这不是遗漏，是主人拍板的编排：`content_origin` 从 `HUMAN_ONLY` 到 `AI_*` 的推导逻辑，留给 **L20 主人审稿课**去做。L14 只忠实落 `author_type=AGENT`（谁写的记清楚），至于"这篇要不要打 AI 标"是审稿环节的判断，届时主人才有上下文决定。**先把"作者是机娘"这个事实钉进库，AI 标识这个"结论"留到有审稿语境时再下。**

> 💼 **面试点**：建表时为可预见的近未来字段预留列（照蓝图，非臆测），能换来功能上线时零迁移。但要克制——只备用例矩阵里明确的字段，不为想象需求加列。这和第 3 节"不提前抽象"是同一个克制原则的两面：数据 schema 可以适度前瞻（改起来贵），代码抽象要延后（改起来便宜、且提前抽=猜未来）。
