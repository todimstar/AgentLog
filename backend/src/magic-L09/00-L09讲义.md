## 〇、先认识本课新建的两张表（这是后面一切讨论的物理基础）

本课在数据库里新建了两张表: `reaction`(点赞) 和 `collection_record`(收藏)。

### reaction 表 —— 存谁给谁点了赞

```
┌─ reaction ──────────────────────────────────────────────────────────┐
│ id          BIGINT     自增主键，每条点赞记录的唯一编号                │
│ user_id     BIGINT     谁点的赞（= user_account 表的用户 id）         │
│ target_type VARCHAR(16) 赞的是"帖子"(POST) 还是"评论"(COMMENT)        │
│ target_id   BIGINT     被赞的那个对象的 id（如果是帖子就=post.id，     │
│                         如果是评论就=comment.id）                      │
│ created_at  DATETIME(3) 什么时间点的赞                                │
│ ────────────────────────────────────────────────────────────────────│
│ ⭐ UNIQUE KEY uk_reaction_user_target (user_id, target_type,          │
│                                        target_id)                    │
│  ← 这是本表最关键的一行！意思：「同一个用户 + 同一种目标类型 +         │
│     同一个目标 id」的组合在整个表里不能重复出现两次。                  │
│     比如 Alice 对 post#1 只能有一条 reaction 记录。                   │
└────────────────────────────────────────────────────────────────────┘
```

**什么是 UNIQUE KEY（唯一键）？**  
唯一键是数据库层面的约束——它保证某几列的组合值在整个表里不重复。比如 `UNIQUE(user_id, target_type, target_id)` 的意思是: 整张表里不允许出现两行 `(user_id=1, target_type='POST', target_id=5)` 完全相同的记录。如果你试图 INSERT 第二行相同组合的数据,MySQL **直接报错拒绝插入**。但如果加了 `INSERT IGNORE`,MySQL 就**跳过不报错,静默忽略**。

**为什么需要它？**  
点赞的业务规则是「一个人对同一篇帖只能赞一次」。如果没有唯一键,只能靠代码写 `SELECT` 检查——但并发下两个请求同时查都发现"没有",就都插进去,造成重复点赞。唯一键是 **DB 层面的物理兜底**,无论代码怎么写,数据库绝不允许重复行存在。

### collection_record 表 —— 存谁收藏了哪篇帖

```
┌─ collection_record ──────────────────────────────────────────────────┐
│ id          BIGINT     自增主键                                      │
│ user_id     BIGINT     谁收藏的                                      │
│ post_id     BIGINT     收藏哪篇帖（收藏只针对帖,不针对评论）           │
│ created_at  DATETIME(3) 什么时间收藏的                                │
│ ────────────────────────────────────────────────────────────────────│
│ ⭐ UNIQUE KEY uk_collection_user_post (user_id, post_id)              │
│     同一用户对同一篇帖只能收藏一次                                    │
└─────────────────────────────────────────────────────────────────────┘
```

### 这两张表和已有表的关系

```
反应/收藏操作  →  修改反应/收藏表（存谁操作了谁）
             →  同时修改 目标表的计数字段（post.like_count / comment.like_count / post.collection_count）

记一个真实交互:Alice 点了 post#1 的「点赞」
┌──────────────────────────────────────────────────────────────────────┐
│ 1. INSERT IGNORE INTO reaction(user_id,target_type,target_id)        │
│    VALUES (1, 'POST', 1)                                              │
│ 2. 看 INSERT 返回的 affectedRows:                                     │
│    =1 → 以前没这条,第一次赞 → UPDATE post SET like_count = like_count+1
│    =0 → 以前有这条（唯一键冲突被 IGNORE）→ DELETE 那条 + count-1        │
│ 3. 返回给前端 {active: true/false, count: 目标当前总赞数}              │
└──────────────────────────────────────────────────────────────────────┘
```

## 一、toggle 模式是什么？（本课核心概念）

### 1.1 什么是「toggle」？
**toggle = 开关**。点一下「开」(加赞/加收藏),再点一下「关」(取消赞/取消收藏)。同一条业务,两次点同一个按钮,做的事相反。

以点赞为例:
```
Alice 打开帖子 post#1
  看到 ♡ 0（空心的爱心,数字是总赞数）
  → 点一下 ♡
  → 爱心变红 ♥ 1（填色的爱心,数字 +1,Alice 自己赞上了）

  Alice 想了一下觉得赞错了
  → 再点一下 ♥
  → 爱心变回空心 ♡ 0（数字 -1,赞被取消了）
```

### 1.2 「先查后插」为什么不对？
初学者的本能做法是先查数据库: "Alice 赞过 post#1 吗？没有就 INSERT,有就 DELETE"。这叫「先查后插」——两步操作,中间有时间差。并发下会出事:

```
时间轴 →

Alice 的请求                           Bob 的请求
───────────────────────────────────────────────────────────
SELECT * FROM reaction
WHERE user=1 AND target='POST' AND id=1
→ 查无记录 (reaction 表当前是空的)
                                        SELECT * FROM reaction
                                        WHERE user=2 AND target='POST' AND id=1
                                        → 查无记录 (Alice 还没 INSERT 完)

INSERT INTO reaction                      INSERT INTO reaction
(user_id,target_type,target_id)          (user_id,target_type,target_id)
VALUES (1,'POST',1)                      VALUES (2,'POST',1)
→ 成功 ✓                                 → 成功 ✓ ← 如果没唯一键,两条都能插!
                                          但 ALice/Bob 同时赞同帖,
                                          各自只有一条,逻辑正确。

真正出问题的是【同一个用户】的并发:
Alice 手快连点两次 ♡ 按钮
 请求A: SELECT → 查无 → INSERT → affectedRows=1 → count+1 (count变1)
 请求B: SELECT → 查无 → INSERT → affectedRows=1 → count+1 (count变2,但 Alice 一个人赞了两条!)
结果:Alice 的 reaction 记录有两行,like_count=2,但只有一个人点赞——脏数据。
```

> **关键**:同一用户并发点赞,「先查后插」会让两个请求在同一时间点都"查无",然后都 INSERT——重复记录。**唯一键能拦,但不用 IGNORE 的话直接抛异常,用户体验差;用 IGNORE 让 DB 静静跳过,代码根据 affectedRows 走不同分支。**

## 二、核心工具:INSERT IGNORE 和 affectedRows（掌握这两个,就掌握了 toggle）

### 2.1 什么是 INSERT IGNORE？

`INSERT IGNORE` 是 MySQL 的一条 SQL 指令。和普通 `INSERT` 的区别:
- 普通 `INSERT`:唯一键冲突 → **抛异常**,SQL 报错,事务可能回滚,用户看到 500 错误。
- `INSERT IGNORE`:唯一键冲突 → **静默跳过**,不报错,不说「插了没」,而是**返回 0 行受影响**。

```sql
-- Alice 第一次赞 post#1:成功插入,受影响行数 = 1
INSERT IGNORE INTO reaction (user_id, target_type, target_id, created_at)
VALUES (1, 'POST', 1, NOW());   -- → 返回 "1 row affected"

-- Alice 再赞同帖:唯一键冲突,被 IGNORE 跳过,受影响行数 = 0
INSERT IGNORE INTO reaction (user_id, target_type, target_id, created_at)
VALUES (1, 'POST', 1, NOW());   -- → 返回 "0 rows affected"
```

### 2.2 什么是 affectedRows（受影响行数）？

`affectedRows` 是 **INSERT/UPDATE/DELETE 执行后 MyBatis 返回的整数**。它告诉 Java 代码:刚才那条 SQL 影响了几行数据。
- `INSERT IGNORE` 成功插入 → affectedRows = **1**(一行新数据被写进去了)
- `INSERT IGNORE` 唯一键冲突被跳过 → affectedRows = **0**(没有写入任何行)

这就是 toggle 的判据:
```
Java 代码:
  int affectedRows = reactionMapper.insertIgnore(reaction);

  if (affectedRows == 1) {
      // 之前没赞过 → 新赞! like_count +1
  } else {
      // affectedRows == 0 → 之前有赞 → 取消! DELETE 记录 + like_count -1
  }
```

### 2.3 核心逻辑:一步操作同时完成「判断」和「插入」

```
┌─ 点击「点赞」按钮 ──→  Java 调用 insertIgnore() ──→ MySQL 执行 INSERT IGNORE
│                                                           │
│                                                     唯一键冲突？
│                                                      ├─ 否 → 插入成功, affectedRows=1
│                                                      │       → 这是新赞
│                                                      │       → like_count +1
│                                                      │       → 返回 {active:true, count}
│                                                      │
│                                                      └─ 是 → 被 IGNORE, affectedRows=0
│                                                              → 这是取消赞
│                                                              → DELETE 那条记录
│                                                              → like_count -1
│                                                              → 返回 {active:false, count}
└──────────────────────────────────────────────────────────────────────┘
```

> **面试金句**: "点赞 toggle 不用先 SELECT 查有没有——INSERT IGNORE 一句下去,看返回的 affectedRows 是 1 还是 0。1 = 以前没这条记录,新加的;0 = 唯一键冲突被跳过,说明已经赞过,现在要取消。一步操作完成判断和写入,并发下唯一键是物理兜底。"

## 三、收藏 toggle —— 和点赞完全同构

收藏的逻辑和点赞一模一样,只是表不同、目标单一(只针对帖子):

```
点击「收藏」→ INSERT IGNORE INTO collection_record(user_id, post_id)
              ├─ affectedRows = 1 → 新收藏 → post.collection_count +1
              └─ affectedRows = 0 → 取消收藏 → DELETE + post.collection_count -1
```

为什么收藏不需要 `target_type`？收藏只针对帖——没有「收藏一条评论」的业务需求。所以请求体只传 `postId`,不用像点赞那样区分 POST/COMMENT。

> **toggle 模式复用**——学会一个,两个都懂。这就是「一次学透,两处复用」。

## 四、GREATEST 防负计数（防御性写法）

### 4.1 它能解决什么问题？

正常操作下计数不会变负:点赞就 +1,取消就 -1,两个操作配对。但万一出现数据不一致——比如有人手动 SQL 把 `like_count` 改成了 0,但 reaction 记录还在——用户再点 cancel,代码走取消分支:

```
当前 like_count = 0,执行 UPDATE post SET like_count = like_count + (-1)
  → like_count = -1  ← 出现了「负赞数」!前端渲染 ♥ -1 就很丑。
```

### 4.2 GREATEST 怎么阻止的？

```sql
-- 本课 XML 里的真实 SQL（ReactionMapper.xml）:
UPDATE post SET like_count = GREATEST(0, like_count + #{delta}) WHERE id = #{postId}
--                            ^^^^^^^^
-- MySQL 函数:参数里最大的那个
-- GREATEST(0, 4)  = 4 ✅ (正常情况)
-- GREATEST(0, -1) = 0 ✅ (变负被钳到 0!)
```

无论怎么减,`GREATEST(0, x)` 保证结果永远 ≥ 0。

> **面试金句**: "计数原子增减用 `GREATEST(0, count + delta)`——万一数据不一致导致 count 已经是 0 还要再减,GREATEST 把结果钳在 0,永远不会出现 -1 赞。这是防御性写法,不依赖所有写入者都正确。"

## 五、完整的请求/响应流（顺一遍,你就知道接口怎么调了）

### 点赞接口
```
POST /api/v1/web/reactions/toggle        ← 需登录 (/web 走 authenticated)
Content-Type: application/json
Body:
{
  "targetType": "POST",   ← "POST" = 赞帖 / "COMMENT" = 赞评论
  "targetId": 1           ← 被赞目标的 id（post.id 或 comment.id）
}

→ Response 200:
{
  "active": true,         ← 这次操作后「我」是否处于点赞中（刚加上=true,刚取消=false）
  "count": 5              ← 这个目标当前的总赞数（前端直接用这个数字刷新按钮）
}

收藏同理: POST /api/v1/web/collections/toggle
Body: { "postId": 1 }
```

**active 和 count 一起返回的好处**: 前端一次请求同时知道「我赞了没」+「总赞数多少」,不用再发第二条查询。

## 六、一页纸面试速记

| 考点 | 答案 |
|---|---|
| toggle 怎么判加删 | `INSERT IGNORE` 一条记录,看 MyBatis 返回的 `affectedRows`:1=插入成功(加),0=唯一键冲突跳过(取消) |
| `INSERT IGNORE` 是什么 | MySQL 指令:尝试插入,唯一键冲突时不报错、静默跳过,返回 0 行受影响 |
| `affectedRows` 是什么 | INSERT/UPDATE/DELETE 后 MyBatis 返回的整数,表示 SQL 影响了几行数据 |
| 唯一键干嘛的 | `UNIQUE(user,target_type,target_id)`:保证同一用户对同一目标只能一条记录。INSERT IGNORE 靠它判断加删,并发兜底 |
| 为什么不用先查后插 | 并发下同一用户两个请求同时"查无"→都 INSERT→重复记录。INSERT IGNORE 一步完成判断和写入 |
| 收藏和点赞区别 | 收藏只针对帖(单列 post_id);点赞用 target_type 多态指 POST/COMMENT |
| GREATEST 防负 | `GREATEST(0, count+delta)`:万一数据不一致 count=0 还要减,GREATEST 钳到 0——防御性写法 |
