## 1. 这课到底在解决什么

L17 结束时，一次失败的协作是这样的：

```text
  第1棒 CT-8b21e0d4a7c93f60   DONE                    ✅ 内容在草稿里
  第2棒 CT-3f7a91c2e5d80b46   FAILED_TIMEOUT          ❄️ 死在这
  第3棒 CT-c04e6d1f8a72b935   BLOCKED_BY_PREDECESSOR  ❄️
  第4棒 CT-9d5b2087fc31e6a4   BLOCKED_BY_PREDECESSOR  ❄️
  尾令牌 handoff_xK9mP...      FROZEN                  ❄️
  会话   PT-008cf65c5affff99  PAUSED_ON_ERROR         ❄️
```

**冻得很整齐——每个状态都准确，每个后序都被正确通知了，但它永远不会自己活过来。**

### 为什么不让 Worker 顺手重启

```text
Worker 自动把票改回 READY_TO_WRITE → ……然后等谁来写？
原机娘的对话已经崩了。服务端【没有任何办法】叫醒一个已关闭的 AI 对话窗口。
15 分钟后再超时 → 又自动重启 → 又没人来 → 死循环，每轮往 error_report 写一条。
```

根因一句话：**服务端与机娘之间是「拉」不是「推」的关系。** 机娘来问「轮到我了吗」，服务端只能回答；它**永远无法主动发起**一次机娘的写作，连对方还在不在都不知道。

> ★ **human-in-the-loop 的判定标准**（记住这个，不是「人比机器聪明」）：
> **这一步需要的信息只存在于系统之外。**
>
> 系统不知道你还想不想继续写，也不知道你能不能把那个 AI 叫回来。

## 2. 本课的四个 owner 端点

```text
GET  /owner/collaboration-sessions/{postTicket}                        时间线（唯一只读）
POST /owner/collaboration-sessions/{postTicket}/tickets/{code}/retry   重试某一棒
POST /owner/collaboration-sessions/{postTicket}/stop                   结束协作（唯一出口）
POST /owner/collaboration-sessions/{postTicket}/handoff                重新签发尾令牌
```

**三个"第一次"**：
1. 第一次由**浏览器里的主人**驱动协作状态机（前 3 课全在 Chain 3 机娘链）；
2. 第一次让 `session.status` 承担**判定职责**（→ §6）；
3. 第一次出现「不做自动化是对的」这种设计决定。

### 为什么这些端点不走 `CollaborationFacade`

L17 的 Facade 注释写着「这个分工也让 L18 的 retry 有现成的落点」，很容易误读成"retry 要挂到 Facade 上"。

**不需要。** Facade 是**给别的模块调**的（reliability 的 Worker 在模块外，够不着私有子包）。而本控制器**本来就在 collaboration 模块内部**，直接调 Service 即可。

那句注释真正的意思是：**「状态机推进归 collaboration」这个分工是对的，retry 属于同一类，所以它也该写在这个模块里**——而不是"必须走 Facade 那道门"。

## 3. retry：解冻**不是**冻结的倒放

L17 冻了 5 样，retry 只解冻 3 样，而且目标状态各不相同：

| L17 冻的 | retry 怎么解 | 为什么 |
|---|---|---|
| attempt → `FAILED_TIMEOUT` | 🚫 **不解冻，永久保留** | 它是**历史**。这就是验收栏「错误历史保留」——新尝试以 `attempt_no=2` **另起一行** |
| 死的那张票 | → `READY_TO_WRITE` | 要能被重新领 |
| 后序整条尾巴 | → **`WAITING_PREDECESSOR`** | ⚠️ **不是 `READY_TO_WRITE`**——前一棒还没重写完 |
| 尾令牌 | → `AVAILABLE` | 新人又能排队 |
| 会话 | → `AWAITING_CONTINUATION` | ⚠️ **不是 RUNNING**——此刻没人在写 |

### 三条链表遍历，方向与深度全不相同

这是本协议**最容易写错**的地方，L17 已经错过一次：

| | 唤醒（L16 `wakeSuccessor`） | 冻结（L17 `blockSuccessors`） | 解冻（L18 `unblockSuccessors`） |
|---|---|---|---|
| 走几步 | **一步** | **走到底**（递归 CTE） | **走到底**（递归 CTE） |
| 目标态 | `READY_TO_WRITE` | `BLOCKED_BY_PREDECESSOR` | `WAITING_PREDECESSOR` |
| 理由 | 「前序完成了」只对直接后继成立 | 「内容缺了一块」对整条尾巴都成立 | 「阻塞的理由消失了」对整条尾巴都成立 |

> ★ **不能因为「看起来对称」就照抄实现。**

### 🔴 蓝图状态机的这条边画错了

`ACPP状态机.md` 原文：`BLOCKED_BY_PREDECESSOR --> READY_TO_WRITE: 前序恢复`

**"前序恢复"有两种含义，被合成了一步**：

| 情形 | 正确目标 | 谁负责 |
|---|---|---|
| 前序**被 retry 了**（可写但还没写） | `WAITING_PREDECESSOR` | L18 |
| 前序**真的写完了**（DONE） | `READY_TO_WRITE` | L16 `wakeSuccessor` |

若 retry 直接解冻到可写，第 3 棒会在第 2 棒还没重写完时就开始写，**基于一篇缺了一块的文章续写**。

### retry 不需要为「后面怎么继续」做任何准备

等原机娘重新写完，L16 的 `wakeSuccessor` 会自动唤醒下一棒。**恢复之后的流转靠原来那套机制自己跑**——这正是状态机设计对了的标志。

### ★ 闸门要选哪个对象

本课三个动作，三个答案：

| 动作 | 判定的是 | 闸门落在 |
|---|---|---|
| retry | 这张**票**是不是超时了 | `ticket.status='FAILED_TIMEOUT'` |
| 结束协作 | 这条**协作**是不是还在跑 | `session.status IN (...)` |
| 重新签发 | 那根**尾令牌**还在不在 | `handoff.status IN ('AVAILABLE','FROZEN')` |

> ★ **判据：闸门要选那个「能唯一代表这次操作发生过」的对象。**

**反例**：重签若拿 session 当闸门——session 状态在重签前后**根本不变**，它记不住"重签发生过"，两个并发请求会双双通过、签出两根令牌。

### 🔴 跨闸门竞态（施工期才想清楚的）

retry 的闸门在**票**上、stop 的在**会话**上——**两把锁管不同的行，互相拦不住**：

```text
retry 先 SELECT 看到 session=PAUSED_ON_ERROR
  → stop 提交（协作结束）
    → retry 才改票
      ⇒ 协作已收工，却有一张票被改回了「可写」——一个没有归属的活票
```

修法：把 `cs.status='PAUSED_ON_ERROR'` 写进 retry 那条 UPDATE 的 `JOIN` 后 WHERE。

> ★ **当两个操作的闸门落在不同对象上时，必须有一方把对方的条件纳入自己的 WHERE**，
> 否则两把锁各自都"成功"，合起来却破坏了不变量。

### 为什么 retry 不需要 `@Idempotent`

**先问「重发会不会造成第二次真实的改变」**：

```text
L16 submit：重发 → 可能写出【两段正文】   ← 真实副作用 ⇒ 需要幂等
L18 retry ：重发 → 闸门返回 0 行，什么都不发生 ⇒ 不需要
```

而且幂等键**由客户端生成**——浏览器点两次是**两个不同的 key**，幂等根本认不出它们是同一件事。

> ★ **幂等防的是「同一个请求被重发」，闸门防的是「这件事被重复执行」——不管来的是不是同一个请求。**
>
> 这句可以直接当面试答案。

## 4. 结束协作：一个出口，而且它**不删任何东西**

### 你推翻了蓝图

蓝图画了两条出边：

```text
AWAITING_CONTINUATION --> READY_FOR_OWNER_REVIEW   正常收工
PAUSED_ON_ERROR       --> TERMINATED               出错放弃
```

你的论证：*两者对**草稿**而言结果完全相同——协作不再占着它。内容是删是留，那是草稿模块（L19）与删除功能的事。*

> ★ **别让一个机制回答两个问题。**（与你在 L16 否决 handoff TTL 是**同一条判据**。）

额外收益：你少做一次选择，而那次选择**此刻根本没法做**——你还没看内容呢。

### 它的本质是**解锁**

协作运行中草稿是**只读**的（错误码 `DRAFT_LOCKED_BY_COLLAB` 的自愈动作正是「等待或 terminate」）。只要协作不结束，**你就永远不能编辑、也不能发布那篇文章**。

⚠️ `post / draft / draft_block / contribution` 四张表**一行都不动**。

### 四步收尾用上了三个"死状态"

```text
③ ★闸门★ session → READY_FOR_OWNER_REVIEW
④ 进行中的 attempt → REVOKED     ← V013 建了两课没人产生
⑤ 未完成的票 → CANCELLED         ← V015 本课新增
⑥ 尾令牌 → REVOKED               ← V012 建了三课没人产生
```

### ★ `CANCELLED` 存在的**全部意义**：让机娘停下来

不加这个状态值会怎样：

```text
你点「结束协作」→ session = READY_FOR_OWNER_REVIEW
   但第 3、4 棒还挂着 WAITING_PREDECESSOR（没人动过它们）
        ↓
第 3 棒的机娘在跑 collab wait，它查的是 TicketStatusService
        ↓
   那个服务【只读票】算 pollAfterSeconds（票是 WAITING → 答"5 秒后再来"）
        ↓
   它会一直问，直到 900 秒超时退出
        ↓
★ 服务端每一次都在【说真话，但骗了它】——
  "前一棒尚未完成"是事实，但真相是"这条协作已经收工了，你可以走了"
```

**靠 session 兜底行不行？** 那要求**每一个读票的地方都记得 join session**，而每写一个新查询都可能忘记。

> ★ 同 L15 判据：**不变量由数据的存在性保证，不由每个查询记得过滤来保证。**

### 命名：为什么叫 `CANCELLED` 而不是 `REVOKED`

- `REVOKED` = 吊销一张**凭证**（令牌、租约）——"这东西作废了"
- `CANCELLED` = 取消一个**席位**——"这个位置不再需要有人来坐"

票不是凭证，它是队列里的位置。**词要跟着语义走。**

### 唯一的真竞态

你按下按钮的同一毫秒，机娘正好 submit 成功。两条 UPDATE 争同一行，MySQL 行锁让它们串行：

| 谁赢 | 结果 |
|---|---|
| **机娘赢** | attempt→`SUCCEEDED`、票→`DONE`、正文进草稿。第④步影响 0 行，第⑤步的 WHERE 也排除了 `DONE` ⇒ **那一棒的内容保住了** ✅ |
| **stop 赢** | attempt→`REVOKED`。它的 submit 闸门 `WHERE status='ACTIVE'` 返回 0 → 干净的 409 |

**两边都不会出现半截状态**——这就是"一条 UPDATE 同时完成检查与动作"的价值。

## 5. 时间线：跨模块**只读**，不开 Facade

时间线要读三个模块的表：`audit_record`（audit）、`error_report`（reliability）、`agent_account`（identity），而服务在 collaboration。

L16 建 `ContentFacade`、L17 建 `CollaborationFacade` 都是为了跨模块——**为什么这次不建？**

> 项目的分工是按「**读 / 写 / 派生**」分的，**不是**按「跨不跨模块」分的：

| | 怎么跨模块 | 先例 |
|---|---|---|
| **读** | 只读 SQL 投影 | L14 跨模块查作者 |
| **写** | Facade | L16 `ContentFacade`、L17 `CollaborationFacade` |
| **派生行为** | 领域事件 | L17 写 error_report / audit_record |

**Facade 存在的理由是「写要保证事务边界与不变量」**（`appendAgentContribution` 用 `Propagation.MANDATORY` 强制必须在事务里）。**读不改变任何东西**，读错了最多显示错，不会写坏数据。

⚠️ 而领域事件在这里**根本用不了**：事件是「写」的派生机制（我做完了 → 喊一声 → 谁关心谁去做），而时间线要**现在立刻**拿到 20 条数据渲染页面。**你没法"发个事件然后等它把数据告诉你"。**

**代价要诚实说**：这几条 SQL 与别的模块的表结构**隐式耦合**了，编译器不会替你检查——对方改列名，这里运行时才炸。项目接受这个代价（D-05）。

### 为什么在内存里组装而不是一条大 SQL

票 : 尝试 = 1:N。若 join 成一张宽表，票的字段会随尝试次数**重复 N 遍**（笛卡尔膨胀），还要在 Java 里去重。分两次查、按 `ticketId` 归并，SQL 更简单、语义更清楚。一条协作的席位是个位数，数据量支持这么做。

## 6. 🔴 三笔"注释承诺了、代码没做"的旧账

这是本课**最值得记住的一节**，三个欠账是**同一个模式**：

| # | 欠账 | 谁承诺的 | 后果 |
|---|---|---|---|
| ① | session 从第 2 棒起**永远回不到 `RUNNING`** | `SessionStatus.java:17` + `SubmitContributionService.java:147`「等下一棒 claim lease 时再回到 RUNNING」 | 机娘正在写，状态却说"等人来接" |
| ② | `COLLAB_STARTED`/`HANDOFF_CLAIMED`/`LEASE_CLAIMED` **无人产生** | `V014` 的 CHECK 值集 | 时间线**凭空从「第 1 棒提交成功」开始** |
| ③ | `TicketStatusView.errorReportId` **恒为 null** | 该文件注释「L17 才会有值」 | 机娘读不到 `suggested_actions_json`，CLI 侧自愈链**是断的** |

> ★ **教训：注释是承诺，但没有任何机制保证它被兑现。**
> 测试只测「代码做了什么」，**测不出「代码答应了却没做什么」**。

### ★ 为什么 ① 能潜伏两课、两轮测试全绿

我核实了 `session.status` 在整个 collaboration 模块的使用：

```text
被【写】的地方：4 处（start=OPEN / claim=RUNNING / submit=AWAITING / worker=PAUSED|INVALIDATED）
被【读来做判定】的地方：★ 0 处 ★
SQL 的 WHERE 用到它的地方：★ 0 处 ★
```

唯一读它的 `ClaimLeaseService` 是 `if (OPEN) → 改成 RUNNING`——**读它只是为了写它**。

> ## L17 说「状态不准是会骗人的」。这是更狠的后半截：
> ## **一个从来没被读过的状态，连骗人的机会都没有——它只是静静地错着，直到有人把它显示出来。**

而 L18 的时间线页正是它的**第一个真正消费者**，stop 的闸门是它**第一次承担判定职责**。**在它变成"守卫"之前，必须先把这个 bug 修掉**——这比"状态机应该正确"是硬得多的理由。

### 顺带：`attempt.READY` 确认**永久不用**（推翻 D-16 的推测）

蓝图的完整设想其实是自洽的：原始契约 `RetryTicketResponse.attemptNo` **必填** + 状态机 `READY -> ACTIVE` + TX-04「创建 Attempt」，拼起来就是：

```text
retry → 建 attempt(attempt_no=2, status=READY) → 返回 attemptNo
机娘 claim-turn → READY → ACTIVE（此刻才写入租约）
```

**但它漏了一环**：`worker-parameters.yaml` 列了**全部 5 个 Worker**，**没有一个会扫 `READY`**——L17 那个扫的是 `status='ACTIVE' AND lease_expires_at < now`，而 `READY` 行**没有** `lease_expires_at`，**永远捞不到**。

⇒ 会长出「名额发了、原机娘再也不回来」的**僵尸行**，且无人回收。

**所以走 B 方案**：retry 只把票改回可写，attempt 由 claim-turn 时 `MAX+1` 自然长出。判据用的是项目自己的三条：L15「不变量由数据的存在性保证」· L16「状态要如实反映」· L17「状态不准是会骗人的」。

**连带**：契约的 `attemptNo` 从 retry 响应里**删掉**（那一行此刻不存在，返回预告值会误导），却给机娘侧的查票端点**加上了**（那里有真实的值）。

> ★ **同一个字段在不同端点的价值可以完全相反。**

## 7. 🔴 施工期真死锁：`updateById` 的隐藏代价

**症状**：给 claim lease 补上 `LEASE_CLAIMED` 事件后，集成测试开始随机报 `DeadlockLoserDataAccessException`，而报错的 SQL 只是一条极简单的 `UPDATE collaboration_session SET status='RUNNING'`。

### 第一层：`updateById` 会 SET **全部列**

```sql
UPDATE collaboration_session
   SET post_ticket=?, owner_user_id=?, planned_channel_id=?, tail_handoff_token_id=?, status=?, ...
        ↑ owner_user_id / planned_channel_id / tail_handoff_token_id 【三个都是外键列】
```

**即使值一个字都没变**，InnoDB 也会为它们做外键检查——对 `user_account`/`forum_channel`/`handoff_token` 的父行各加一把 **S 锁**。

改成精准 UPDATE 后，死锁从 2 例降到 1 例。**方向对，但没除根。**

### 第二层：审计表的外键

```text
T1 (claim lease 业务事务)：持 contribution_ticket 的 X 锁（闸门那条 UPDATE）
                          → 请求 collaboration_session 的 X 锁
T2 (AuditListener 异步事务)：INSERT audit_record 时
                          fk_audit_session 要 collaboration_session 的 S 锁（已持有）
                          fk_audit_ticket  要 contribution_ticket 的 S 锁（等 T1）
⇒ 成环
```

> ★ **外键不是"免费的完整性"，它是【隐式的锁】。**
> 每插入一行子表记录，InnoDB 都要去父表把被引用的那一行锁住，以防它在本事务提交前被删掉。
> 而 `audit_record` 一次插入要锁**四张**父表的行。

**而审计表是被业务事务的旁路【异步】写入的，它锁的恰恰是业务事务正在改的那些行**——两条路径关心同一批实体，加锁顺序却完全不同，是**天然的死锁温床**。

### 修法与两条判据

① 会话状态推进一律改**精准条件 UPDATE**；② **V016 去掉两张流水表的全部 9 个外键**（索引全部保留）。

> ★ **判据一：`updateById` 的代价不是"多写几列"，是"多锁几张表"。**
> 这与 L17 让 `ExpiredAttemptScanMapper` **故意不继承 `BaseMapper`** 是同一条思路（那次是为了不暴露绕过闸门的写法），只是这次的理由更硬——**它真的把系统锁死了**。
>
> ★ **判据二：流水表不建外键。** 它们每一列都由我们自己的代码写入，外键真正防的「用户传了个不存在的 id」根本不会发生；代价却是锁竞争 + 将来归档困难。这是 V014 已列的「流水表与状态表三处不同」的**第四处**。

### ★ 为什么 L15–L17 一直没炸

并发度不够。审计事件此前只有「超时」「提交」两种，稀疏。L18 补上 `LEASE_CLAIMED` 后，**每领一次租约就多一次审计写入**，撞车概率陡增。

> ★ **并发缺陷的暴露需要压力，而压力常常由一个看似无关的新功能提供。**

## 8. 重新签发尾令牌：UX 撞上安全模型

UX 规格（`06-web/owner-review-ux.md` 第 6 行）要求「**可查看**下一棒尾令牌」。

**这件事物理上做不到：**

```text
handoff_token 表里存的是  token_digest BINARY(32) = HMAC-SHA256(pepper, 明文)
摘要是【单向】的：有明文能算出摘要，有摘要【永远】算不回明文。

明文的一生：签发那一刻放进 HTTP 响应 → 你复制走 → 服务端内存里那份被 GC 回收
                                                 ↓
                                     ★ 从此世上只有你手里那一份 ★
```

L16 已经为这条铁律付过一次代价（D-16：submit 响应的 `nextHandoffToken` **恒为 null**）。

> ★ **判据：当 UX 需求撞上安全模型时，往往不是砍需求，而是换一个能满足它的机制。**
> 你真正要的是「**我能拿到一根可用的令牌**」，不是「我要看那一根特定的令牌」。

### 为什么存摘要（既然 CLI 每次都把明文发过来）

存摘要防的**不是传输被看到**，而是**数据库被脱库**：

```text
攻击者拿到 dump：
  存明文  → 直接冒充任何机娘 join 任何协作
  存摘要  → 需要 pepper，而 pepper 在【应用配置】里（AGENTLOG_TOKEN_PEPPER），不在库里
```

⇒ **纵深防御：数据库与应用配置是两个独立的攻击面，攻破一个不足以拿到凭证。** 同密码存 bcrypt——你登录时也发明文，但库里绝不能存明文。

### 三个使用场景，第三个最关键

1. 你把令牌弄丢了（关掉了显示它的页面）——最常见；
2. 怀疑泄漏，想作废重发；
3. 🔴 **retry 刚把尾令牌从 `FROZEN` 解冻回 `AVAILABLE`，但你手上早就没有那串明文了**。

⚠️ 旧令牌**必须真的吊销**，不能只是"不管它"——那串明文若已流到别人手里（被粘进公开的聊天记录），不吊销就等于留了一个可用的后门。

## 9. 🔴 你在验收时问出的缺口：下一棒读不到前面的正文

你在等第 2 棒超时的间隙问：

> 「领租约返回的 context 里有 PT- 会话票、计划标题和简介，**那之前的正文怎么传给后续接力的机娘呢？**」

核实结果：机娘侧**全部 7 个端点没有一个能读到前文**。`claim lease` 的 `writingContext` 里 `lastCompletedSequence` 只告诉它「前面写了 N 棒」，**不告诉它写了什么**。

`ClaimLeaseService` 的注释写着「草稿 URL 由主人给，机娘无读权」——**设计上靠你手动复制粘贴**。

### 为什么这是缺口而不是"零信任的必要代价"

```text
接力棒  51 个字符      复制一次不痛
正文    几百上千字     而且【每接一棒都要复制一次】
```

> ★ **"零信任"很容易被用来给"没想到"背书。** 真正该问的是：这个信任边界的**代价由谁承担、有多大**。
> 这不是必要代价，是 L15 定这条规则时**协作还没真正跑起来过**。

### 补上之后，最硬的判断是：**返回哪一层内容？**

`APPROVAL_RECORD` 冻结的两层结构：

```text
contribution.raw_content     机娘交的原文，【永不覆盖】    —— 不可变原始层
draft_block.rendered_content 文章【现在】的样子，主人润色只改这里 —— 可编辑渲染层
```

**选渲染层。** 因为**续写要基于「文章现在是什么样」，不是「当初交了什么」**——你润色过第 1 棒之后，第 2 棒若还读到原始版本，就会**基于一段已经不存在的文字**往下写，越写越偏。

**而且渲染层是严格优于的选择**（你问的那个问题的答案）：两层是在**同一次 submit、用同一个字符串**写的，所以

```text
机娘 submit 那一刻   raw_content = rendered_content   ← 两层【相同】
你润色之后          rendered_content 变了            ← 两层【分叉】
```

⇒ 渲染层在"没润色"时**等价**，在"润色过"时**才更对**，**没有任何情况下更差**。

### 连带三条

| 约束 | 为什么 |
|---|---|
| `is_hidden = FALSE` | 你隐藏一个块就是不要它出现在文章里，机娘更不该基于它续写 |
| `ORDER BY display_order` | L19 之后你可以拖拽调序，那时「第几棒写的」与「在文章里排第几」就分叉了；机娘要的是**阅读顺序** |
| 权限**按租户**划不按机娘划 | 沿用 L16「谁能写靠闸门、谁能看按租户」。**若按机娘过滤，第 3 棒就读不到第 2 棒写的东西，端点直接失效** |

`truncated` 字段**如实上报**截断：**沉默的截断会让机娘以为自己读到了全文**，然后基于残缺的上下文续写。

### 「只能读已完成的」不需要写任何过滤条件

`draft_block` 里只会有**已 submit** 的内容（submit 才写块）。因果链的串行性已经保证了「我后面的还没写」。

> ★ 又一次：**不变量由数据的存在性保证。**

### ★ 外部佐证：Raft（你 HR 推荐的那个）

`raft.build`（Botiverse）官网原话：

> "**What one agent figures out, the next one builds on.**"
> "A human or agent can be thrown into a totally new project with no context, because **they can get all the context from the agents who previously worked on that project**."

| | Raft | ACPP |
|---|---|---|
| 任务获取 | agents **claim tasks** | 机娘 claim lease ✅ **同构** |
| 交接 | hand work to each other | handoff 令牌 ✅ 但**必须经过人** |
| 身份 | persistent identity + **memory** | `agent_account` ✅ 身份有、**memory 没有** |
| 并行 | run in parallel | ❌ 严格**串行**（因果链） |
| **上下文传递** | **核心卖点** | ❌ → ✅ 本轮补上 |

> ★ **上下文传递不是加分项，是这类产品的基本盘。**

## 10. 机娘自报失败：把「症状」换成「原因」

`FAILED_CLIENT` 从 V013 起就在 CHECK 值集里（注释标着「L18」），但**在本课之前没有任何端点能产生它**。

### 为什么值得单开一个端点

不是为了省那 15 分钟：

```text
超时那条路径 → error_report.summary = "第 2 棒的机娘租约超时，未能在有效期内提交内容"
              ↑ 这是【症状】。服务端根本不知道为什么它没回来（对话崩了？需求不清？工具报错？）

自报失败     → error_report.summary = "第 2 棒的机娘主动报告失败：上一棒缺少关键前提，无法续写"
              ↑ 这是【原因】。你能立刻决定怎么办
```

> ★ **主要收益是把「症状」换成「原因」。** 省下的 15 分钟是次要的。

所以 `reason` 是**必填**——允许空的 reason 就等于允许它退化成"一个提前的超时"，那就没必要单开这个端点了。

### `FailurePropagation` —— 被第二个触发者逼出来的抽取

自报失败与 Worker 超时**后续要做的事完全相同**：票落失败态、后序整条尾巴阻塞、尾令牌冻结、会话暂停或作废。

⇒ 这恰好**验证了 L17 那条分工判据的价值**：

> **「何时做」归 reliability，「做什么」归 collaboration。**
>
> 把「做什么」独立出来之后，**加一个新触发者不需要复制任何逻辑**。
> 若当初写死在 Worker 里，L18 就只能复制粘贴一份——而复制出来的两份**一定会漂移**。

### 两道闸门是**互补**的

```text
Worker ：WHERE status='ACTIVE' AND lease_expires_at < now   （已过期才轮到我收尸）
自报   ：WHERE lease_token_digest=? AND status='ACTIVE'      （凭证对得上就认）
```

**故意不校验是否过期**：机娘说「我写不下去了」这件事，**租约过没过期都成立**。若恰好与 Worker 撞上，行锁让二者串行，谁先谁赢，另一个拿 0 行干净退出——而**两条路径后续做的事完全相同，所以谁赢都不影响正确性**。

## 11. CLI `resume`：为什么**不做**反向通信

你的质疑：*「我们服务端在主人网页点了 retry 还要自己再跑去跟他的 agent 说可以继续？这很不符合常理、不符合软件美学。」*

**你说得对，这里确实有个设计问题。** 我最初把 `resume` 定位成"接收 retry 通知"，那是错的。

### 退回 ACPP 的出发设计

`V012` 文件头第 8 行：「两个 AI 对话之间**零共享上下文**，**主人是唯一的传递媒介**」。

### 再调研业界

| 产品 | CLI 怎么接收服务端消息 |
|---|---|
| `stripe listen` | CLI 建**出站** WebSocket（CLI 在 NAT 后没有公网地址，Webhook 不可行） |
| `gh run watch` | 轮询 |
| `kubectl wait` | 客户端发起的 watch 长连接 |

**业界确实有成熟方案，但对 ACPP 收益极低：**

```text
场景 1  机娘的 wait 还在跑 → retry 后下次轮询就看到了，【不需要通知】
场景 2  wait 已超时退出   → 进程没了
场景 3  对话崩了（retry 的典型场景）→ 进程和上下文全没了
```

> ## ★ 推送的前提是接收方活着。
> ## 当你最需要通知的时刻恰好是接收方死掉的时刻，通信机制就不是答案——**人才是**。

第二层：`stripe listen` 是**常驻进程**，而机娘是**一次一条命令**的 AI 对话，挂不住长连接。

### 那 `resume` 到底解决什么

**替机娘省掉「我现在该跑哪条命令」这个判断**——这个判断对 AI 客户端特别贵。

| 查到的票状态 | resume 替它做什么 |
|---|---|
| `READY_TO_WRITE` | **自动领租约** + **打印前文** |
| `WAITING_PREDECESSOR` | 告诉你去 `wait` |
| `LEASED`（租约在本地） | 你上次领了没提交，接着写 |
| `CANCELLED` | 协作已收工，可以停了（退出码 **0**，不是错误） |
| `DONE` | 这一棒写过了，别重复写 |
| `FAILED_TIMEOUT`/`BLOCKED` | 要主人在协作页介入 |

Skill 文档因此能从"五分支决策树"简化成一句「跑 `resume`，照它说的做」。

⇒ 「通知」由**网页上的一键复制话术**承担（协作页给出整条 `agentlog collab resume --ticket CT-xxxx`），**经由主人**。与 L15 接力棒必须经过人手复制粘贴是**同一个架构决定**。

## 13. 面试问答（37-43，可直接背）

**Q：你们那个多 AI 接力系统，一个 AI 挂了之后怎么恢复？**

> 先说清楚一件事：**恢复必须由人触发，我们故意没做自动重试。**
> 因为服务端与 AI 之间是"拉"不是"推"的关系——AI 来问"轮到我了吗"，服务端只能回答，它无法主动叫醒一个已经关闭的对话窗口。自动重试只会把任务改回可写、15 分钟后再超时、再重试，**死循环**，而且每轮写一条事故报告。
> 判定标准不是"人比机器聪明"，而是——**这一步需要的信息只存在于系统之外**（用户还想不想继续、能不能把那个 AI 叫回来）。

**Q：那 retry 具体做了什么？**

> 一道闸门 + 三处解冻。闸门是一条带条件的 UPDATE，`affectedRows` 就是裁决书——**这道闸门本身就是幂等**，用户连点两次，第二次一定返回 0 行。
> 关键是**解冻不是冻结的倒放**：失败的那条尝试记录**不解冻**（它是历史，这是"错误历史保留"的验收项）；后序任务解冻到"排队中"而**不是"可以写"**，因为前一棒只是"可以重写了"、还没写完；会话落"等人来接"而**不是"运行中"**，因为那一刻没有任何人在写。

**Q：幂等和你说的"闸门"有什么区别？**

> **幂等防的是「同一个请求被重发」，闸门防的是「这件事被重复执行」——不管来的是不是同一个请求。**
> 具体到我们：提交内容需要幂等，因为重发会真的写出两段正文；而 retry 不需要，因为重发只是闸门返回 0 行、什么都不发生。而且幂等键是客户端生成的——浏览器点两次按钮是两个不同的 key，**幂等根本认不出它们是同一件事，闸门能**。

**Q：讲一个你排查过的死锁。**

> 我给一个高频接口加了条审计事件，之后集成测试开始随机死锁，报错的却是一条极简单的 `UPDATE ... SET status=?`。
> 两层原因：第一层，ORM 的 `updateById` 会 SET **全部列**，其中三列是外键——**即使值没变，InnoDB 也要做外键检查，给三张父表的行各加 S 锁**。第二层，异步的审计写入有四个外键，在抢同一批行的 S 锁，两边**加锁顺序相反**。
> 结论两条：**`updateById` 的代价不是"多写几列"，是"多锁几张表"**；**流水表不建外键**——它每一列都由我们自己的代码写入，外键真正防的"传了个不存在的 id"根本不会发生，代价却是锁竞争和将来的归档困难。
> 还有个元结论：**并发缺陷的暴露需要压力，而压力常常由一个看似无关的新功能提供**——这个隐患从三课前就埋着，是新加的一个审计事件把它逼出来的。

**Q：你们有没有过"状态字段写错了但没人发现"的情况？**

> 有，而且潜伏了两课。会话状态本该在"下一棒开始写"时回到 RUNNING，代码注释白纸黑字写着这句，但那个分支**从来没有被实现过**。
> 为什么两轮测试全绿——我核实过：这个状态字段**被写 4 处、被读来做判定 0 处**，没有任何 SQL 的 WHERE 用到它。
> **一个从来没被读过的状态，连骗人的机会都没有，它只是静静地错着，直到有人把它显示出来。** 我们做协作时间线页时它才暴露，而那一课它同时第一次承担了判定职责——所以必须先修。
> 引申：**注释是承诺，但没有任何机制保证它被兑现。测试测的是"代码做了什么"，测不出"代码答应了却没做什么"。**

**Q：产品要求"能查看令牌"，但你们存的是哈希，怎么办？**

> 不砍需求，也不改存储——**换一个能满足它的机制**：做成"重新签发"。用户真正要的是"我能拿到一根可用的令牌"，不是"我要看那一根特定的令牌"。旧的立即吊销，新的明文显示一次。
> 顺便：存摘要防的**不是传输被看到**（用的时候必然是明文），是**脱库**——摘要需要 pepper 才能验证，而 pepper 在应用配置里不在库里，**这是两个独立的攻击面**。

**Q：你们的多 AI 协作，下一个 AI 怎么知道前面写了什么？**

> 这是我们**跑了四课都没人问、直到真机验收才发现**的缺口。原设计是"AI 无读权，内容由人复制粘贴"——听起来是零信任，但代价没人算过：交接凭证 51 个字符复制一次不痛，**正文上千字、每接一棒都要复制一次**。
> **"零信任"很容易被用来给"没想到"背书。**
> 补的时候最硬的判断是**返回哪一层内容**：我们有不可变的原始层和可编辑的渲染层，用户润色只改后者。答案是**渲染层**——**续写要基于"文章现在是什么样"，不是"当初交了什么"**，否则下一棒会基于一段已经不存在的文字往下写。而且渲染层严格优于：两层在提交那一刻内容相同，只有润色过才分叉，**没有任何情况下更差**。
> 业界佐证：多 agent 协作平台 Raft 把"新人能从之前的 agent 拿到全部上下文"当核心卖点——**上下文传递不是加分项，是这类产品的基本盘**。
