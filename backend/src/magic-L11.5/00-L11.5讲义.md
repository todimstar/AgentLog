# L11.5 邮箱登录 + 验证码 + Redis（插入课）

> 一句话：把「用户名登录 + 双名字（username/display_name）」这笔**底层设计债**，重构成
> 「**邮箱登录 + 唯一 username（一个名到处用）+ 邮箱验证码（Redis 存）**」，对齐你旧论坛
> `springBootDemo` 的主流做法。这是你亲手点破的坑，值得单开一课认真还。

## 0. 这堂课为什么突然插进来（病情诊断）

你在验收 L09/L10 时点破了一个别扭：

```

                     ↑ 你登录要记这个            ↑ 但别人看到的是这个
```

**权威设计包（`AgentLog_Implementation_Master_Pack_v1.1`）从头到尾就没设计 email/验证码**——

## 2. 设计决策（四个对照——本课的"道"都在这）

### 2.1 双名字 → 单名字 + 邮箱（为什么这么合）

```
改造前                          改造后
─────────                       ─────────
username   = "demo_alice"  ┐    email    = "alice@demo.agentlog.local"  ← 登录凭据（唯一、不展示）
display_name="Alice"       ┘    username = "Alice"                       ← 展示名（唯一、到处显示）
password_hash                   password_hash
                                （display_name 列已删除）
```

**要点**：`email` 承接"登录凭据"职责（唯一、私密），`username` 收敛为"唯一展示名"（谁看到的都是它）。
一个用户从此只有一个"名字"给人看，一个"邮箱"给系统认——各司其职，不再一人两名。

### 2.2 对照旧论坛 `springBootDemo`（邮件 / Redis / 验证码怎么做）

你旧项目已经有全套，我们**照搬思路、按本项目规范落地**：

| 能力 | 旧论坛 `springBootDemo` 的做法 | 本项目 L11.5 的做法（差异） |
|---|---|---|
| 发邮件 | `JavaMailSender` + `SimpleMailMessage`，`@Async` 异步发 | 一样用 `JavaMailSender`；发失败**降级只记日志**不阻断 |
| SMTP 配置 | `spring.mail`：smtp.139.com:465 + SSL | **原样复用你这套 139 账号**（你说的"用旧项目配置即可"） |
| 验证码存哪 | `RedisTemplate<String,Object>` + Json 序列化 | **改用框架自带 `StringRedisTemplate`**（验证码就是字符串，零配置零魔法——透明>省事，见规则 6d） |
| 验证码校验 | key=`register:code:`+email，比对后 `delete` | 一样：key=`auth:register:code:`+email，校验通过即删（一次性） |
| 登录失败限流 | key=`login:fail:`+userId，5 次锁 15min | 一样思路，但 **key 用 email**（认证前还没 userId，用 email 更早拦） |
| 登录态 | JWT（无状态） | **本项目是 Session**（见 2.3），不发 token |

### 2.3 对照本项目 Session vs 旧项目 JWT（登录态存哪——别改错了）

这是**最容易写错的地方**：旧论坛登录成功发 JWT，我们**不发 token**。本项目 L05 定的是
**Web Session**（`ApiSecurityConfiguration`：`SessionCreationPolicy.IF_REQUIRED` + CSRF）。

```
旧论坛 JWT：  login OK → 生成 token → 前端存 localStorage → 每次请求带 Authorization 头
本项目 Session：login OK → 存进 HttpSession(服务端) → 浏览器持 Cookie → 刷新仍登录
```

所以 L11.5 只把"**用什么验证身份**"从 username 换成 email，**"验证通过后怎么记住你"完全不动**——
仍走 `authenticationManager.authenticate(...)` + 存 `HttpSession`。这条铁律不能因为抄旧项目而带歪。

### 2.4 机娘（`agent_account`）为什么完全不受影响

你担心"改 email 登录会不会影响机娘被 @ / 机娘发帖"。**不会**，三条证据：

```
① 机娘不登录：agent_account 只有 nickname，没有 password_hash —— 它根本没有"登录"这回事
② @机娘 不靠 username：评论的 @ 是 reply_to_comment_id（评论 id）渲染"回复@某"，不查 username
③ 机娘发帖走另一条路：靠主人的 agent-token 代理（原 L12-L14，本分支还没建），与人类 email 登录正交
```

一句话：email 登录只改**人类** `user_account` 这一条线，机娘那条线（nickname + owner 代理）纹丝不动。

## 3. 数据模型：V009 退避式改造（🔴 面试点）

难点：`email` 要 **NOT NULL + UNIQUE**，但表里**已经有数据**（V008 seed 的 alice/bob/carol），
直接 `ADD COLUMN email NOT NULL UNIQUE` 会因存量行 email 为空而失败。生产给存量表加强约束列的
**标准退避姿势**是"三步走"：

```sql
-- V009__add_email_login.sql
-- ① 先加可空列（存量行先容忍 NULL）
ALTER TABLE user_account ADD COLUMN email VARCHAR(255) NULL AFTER username;

-- ② 回填：给存量 demo 用户造邮箱；username 收敛成 display_name 的"好名"（一个名到处用）
--    注意顺序——email 先用 display_name 造，再把 username 覆盖成 display_name
UPDATE user_account SET email = CONCAT(LOWER(display_name), '@demo.agentlog.local') WHERE email IS NULL;
UPDATE user_account SET username = display_name WHERE display_name IS NOT NULL AND display_name <> '';

-- ③ 回填完了，再收紧成 NOT NULL + UNIQUE
ALTER TABLE user_account MODIFY COLUMN email VARCHAR(255) NOT NULL;
ALTER TABLE user_account ADD UNIQUE KEY uk_user_email (email);

-- ④ 砍掉 display_name（职责并入 username）
ALTER TABLE user_account DROP COLUMN display_name;
```

**两个巧思（面试可讲）**：
1. **退避式加约束**：可空→回填→收紧，是"给运行中的表加非空唯一列"的通用套路（零停机的雏形）。
2. **净零列数保测试绿**：加 `email`（+1）又删 `display_name`（−1），`user_account` 列数**仍是 13**，
   `FlywayMigrationTest` 断言 `columnCount==13` **自动继续绿**。对照 L24 只加 `role` 一列（13→14）
   当场把测试打红——这次一加一删刚好抵消，是"改表要同步想测试"的正反面教材。

## 4. 接口纵切（outside-in，三个接口逐个打穿）

按你的开发心智——**先看 Controller 接口，再倒推它要什么**。本课三个接口：

### 4.1 `POST /api/v1/web/auth/send-code`（发注册验证码）
```
请求  { "email": "me@x.com" }
  → SendCodeRequest(email)                        [DTO·record]
  → IdentityService.sendRegisterCode(email)       [应用服务]
      → 查 email 是否已注册（已注册直接拦）
      → EmailVerificationService.issue(email)
          → 防刷：Redis 已有未过期码 → 拒绝（60s 内重复发）
          → 生成 6 位码 → JavaMailSender 发邮件（失败降级记日志）
          → StringRedisTemplate 存 key=auth:register:code:{email}，TTL 10min
响应  204 No Content
白名单：permitAll + CSRF 忽略（没登录也没 token，属认证入口）
```

### 4.2 `POST /api/v1/web/auth/register`（邮箱+用户名+密码+验证码）
```
请求  { "email","username","password","verCode" }
  → RegisterRequest(email, username, password, verCode)   [DTO·record]
  → IdentityService.register(req)                          [应用服务·@Transactional]
      → EmailVerificationService.verify(email, verCode)    [Redis 取码比对，通过即删（一次性）]
      → email 唯一校验（uk_user_email 兜底）
      → username 唯一校验（uk_user_username 兜底）
      → bcrypt 加密 → UserAccount 落库
响应  201 UserView
```

### 4.3 `POST /api/v1/web/auth/login`（邮箱+密码，+Redis 失败限流）
```
请求  { "email","password" }
  → LoginRequest(email, password)                          [DTO·record]
  → WebAuthController.login()
      → LoginAttemptService.checkLocked(email)             [Redis：≥5 次 → 抛 LOGIN_LOCKED]
      → authenticationManager.authenticate(email, password)
            └ 内部调 AppUserDetailsService.loadUserByUsername(email) —— 现在按 email 查库
      → 失败：LoginAttemptService.recordFailure(email)     [Redis 计数 +1，首次错设 15min 过期]
      → 成功：清 Redis 失败键 + 存 SecurityContext 进 HttpSession（Session 铁律不变）
响应  200 UserView
```

> 注意：`AppUserDetailsService.loadUserByUsername` 这个方法名是 Spring 接口定的，改不了；
> 但**方法体里改成按 email 查**。传进来的"username"参数其实装的是 email——框架无所谓，认得就行。

## 5. Redis 三用（key 设计一览）

| 用途 | key | 值 | TTL | 谁写/谁删 |
|---|---|---|---|---|
| 注册验证码 | `auth:register:code:{email}` | 6 位码 | 10 min | 发码写 / 注册成功删（一次性） |
| 发码防刷 | 同上（存在即拒） | — | — | 复用验证码键的存在性判断 |
| 登录失败限流 | `auth:login:fail:{email}` | 失败次数 | 15 min | 失败 +1 / 成功删 / 满 5 锁定 |

**为什么用 Redis 不用数据库**：验证码/失败计数都是**短命、高频、带过期**的数据，塞 MySQL 又要建表又要
清理；Redis 原生 `SET key val EX 600` 一行搞定过期，读写还快。这正是 Redis 的典型场景。

## 9. 面试点（本课能讲的故事）

1. **给运行中的表加"非空唯一"列怎么办**？退避三步：加可空 → 回填 → 收紧约束。
2. **验证码/限流为什么用 Redis 不用 MySQL**？短命+高频+带过期，`EX` 一行搞定，读写快。
3. **登录失败限流为什么 key 用 email 不用 userId**？认证前还没查到用户，用 email 能更早拦住暴力枚举。
4. **抄旧项目最容易带歪的点**：旧项目发 JWT，本项目是 Session——"验证身份"可以换 email，
   "记住身份"必须仍走 HttpSession，别把无状态 token 抄进来。
5. **改表要同步想测试**：加一列删一列净零，`columnCount==13` 侥幸继续绿；对照 L24 加 `role`（13→14）
   当场打红——结构断言是"改表提醒器"。
6. **一人两名的建模债**：username/display_name 职责重叠 → 收敛成 email(认证)+username(展示) 正交双职责。

## 10. 2026-07-08 加固补丁（主人睡前拍板，AI 施工，全量测试 32 绿）

- **入参校验**：三个 record（SendCode/Register/Login）加 Jakarta 注解 + Controller `@Valid`，
  `IdentityService.validate()` 手写校验退役。邮箱正则单一事实源：`identity/domain/EmailRules`。
  登录邮箱非法格式直接 400 → **不再进 Redis 建垃圾失败键**（实测 email="1" → 400，Redis 零键）。
- **状态常量**：`media/domain/MediaStatus`（PENDING/ACTIVE）+ `identity/domain/UserStatus`（ACTIVE）
  消灭硬编码。跨模块投影读处按约定**不 import 对方枚举**，用本地 `private static final` + 对齐注释
  （`IdentityService.MEDIA_STATUS_ACTIVE` / `FeedService.AUTHOR_STATUS_ACTIVE`）——模块间零 Java 依赖不破。
- **真实邮箱修复**：根因是 yml 里 `spring.dotenv.*` 是 spring-dotenv 第三方库的配置项而 pom 从未引入，
  `.env` 从没被加载过。改为 Spring 原生方案：`application.yml` 默认激活 `local` profile，真实 SMTP 凭据放
  `application-local.yml`（已 gitignore，模板见 `.example`）。实测 139 邮箱真发成功。
  ⚠️ 本地常驻的旧后端进程需重启才吃到新配置。
- **验证码冷却**：`remainTtl`（驼峰化）逻辑确认正确——60s 内拒重发，满 60s 可再发一份新的 10min 码。
- **契约同步**：注解界限对齐 openapi（username 2~64 / password 8~128）；契约 verCode 补 `pattern: ^[0-9]{6}$`。
