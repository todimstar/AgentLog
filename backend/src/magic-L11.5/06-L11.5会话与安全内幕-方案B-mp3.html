📝 课后测验 · Session 登录最小单元

    
由浅入深 5 题。先自己说出答案再点开对照——能讲顺 = 真懂了，卡壳的题回到对应线重听。

    
①基础登录成功后，"记住你"靠哪两样东西配合？各存在哪一端？
      
柜子 = HttpSession，存在服务端（Tomcat JVM 堆内存的 Map）；钥匙 = JSESSIONID Cookie，存在浏览器。登录时 saveContext（WebAuthController L100）把 SecurityContext 放进柜子，并经 resp 发 Set-Cookie 把钥匙交给浏览器 → 对应视频「线2·存的一半」。

    
①基础为什么登录接口要同时传 HttpServletRequest 和 HttpServletResponse？
      
req 用来拿到/创建 HttpSession（柜子）；resp 用来写 Set-Cookie: JSESSIONID（把钥匙递出去）。只有 req 存不了新钥匙，只有 resp 找不到柜子——一存一发，缺一不可。

    
②链路从 authenticationManager.authenticate(token) 到密码比对，中间经过哪两层？你写的代码在哪一环被回调？
      
AuthenticationManager（接口）→ 默认实现 ProviderManager（只分发不干活）→ DaoAuthenticationProvider（真正干活）。它内部三步：① 回调你写的 AppUserDetailsService.loadUserByUsername(email)（L33）查库拿 UserDetails；② PasswordEncoder.matches(明文, bcrypt哈希) 比对；③ 对→返回已认证 Authentication，错→抛 BadCredentialsException（Controller catch 后计失败数再抛给 Security 翻 401）。

    
③原理后续请求为什么不用写任何"读 Cookie 恢复登录"的代码？是谁在哪个环节做了哪四步？
      
Security 过滤器链前排的 SecurityContextHolderFilter 自动做：① 用请求带来的 JSESSIONID 找到服务端 HttpSession；② 取出登录时存的 SecurityContext；③ 放回 SecurityContextHolder（线程上下文）——所以 CurrentUser.requireId() 才有值；④ 请求结束清空线程上下文防串号。你只写"存"，"取"是框架的——这就是在源码里找不到那段代码的原因。csrfController 与此无关：它只发 XSRF-TOKEN（防伪造请求），JSESSIONID 才管"你是谁"。

    
④设计服务器重启后用户为什么全掉线？要"重启不掉线"接什么？再一句话说清 Session vs JWT 的撤销差异（面试版）。
      
柜子是 JVM 堆内存的 Map，进程一停全清 → 全员重新登录。要不掉线：接 Spring Session + Redis 把会话搬进外部存储（蓝图排在多实例部署课）。面试一句话：Session 把状态放服务端，logout 时 invalidate() 即时作废、服务端说了算；JWT 把状态放令牌里，签发后收不回，只能等过期或额外维护黑名单。同源 SPA 选 Session 更简单。追问"换 email 登录要改多少"：只换 UserDetailsService 查法（eq(getEmail)），认证流水线零改动。
