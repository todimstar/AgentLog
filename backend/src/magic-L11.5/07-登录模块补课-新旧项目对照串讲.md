## 0. 一句话总纲

**两个项目做的是同一件事的两种答案：「验证你是谁 + 记住你是谁」。**
旧项目：手写验证 + JWT 令牌记忆（无状态）。新项目：框架流水线验证 + Session 柜子记忆（有状态）。
你觉得新项目"代码少得可疑"，是因为旧项目里**你亲手写的那些活，新项目交还给了 Spring Security 的内置流水线**——功能一个没少，只是搬进了框架。

## 1. 全链路时序对照（先看骨架再抠细节）

### 登录那一刻
| 环节 | 旧（JWT） | 新（Session） |
|---|---|---|
| 入口 | `UserController` L56-71 `/api/auth/login` | `WebAuthController` L72-102 `/auth/login` |
| 查用户 | **手写**：`UserServiceImpl` L103-104 先按 username 查、再按 email 查（双入口） | **框架回调**：`DaoAuthenticationProvider` 调 `AppUserDetailsService.loadUserByUsername` L33（方法体按 email 查 L36-37） |
| 比密码 | **手写**：L126-132 `passwordEncoder.matches(password, userInDb.getPassword())` | **框架**：Provider 内部调同款 `PasswordEncoder.matches`，你一行不写 |
| 防暴力 | **手写**：L118-124 Redis `login:fail:<userId>` 5 次锁 15 分钟 | **手写**（这段仍要自己写）：`LoginAttemptService` L29-48，`auth:login:fail:<email>` 5 次锁 15 分钟 |
| 发"凭证" | L142-144 `JwtUtil.generateToken(UserDetails)` → 返回 token 字符串给前端存 | `WebAuthController` L100 `saveContext` → 存 HttpSession + `Set-Cookie: JSESSIONID` |

### 之后的每一次请求（"记住你"的两种实现）
| 环节 | 旧（JWT） | 新（Session） |
|---|---|---|
| 凭证怎么来 | 前端 JS **手动**放 Header：`Authorization: Bearer xxx` | 浏览器**自动**带 Cookie: JSESSIONID |
| 谁来接 | **你手写的** `JwtAuthenticationFilter` L24-111（注册在 SecurityConfig L65） | **框架内置的** `SecurityContextHolderFilter`，零代码 |
| 怎么恢复身份 | 解析 token（L55 extractUsername）→ **查库** `loadUserByUsername`（L63）→ validateToken（L73）→ L91 `setAuthentication` | 拿 JSESSIONID 开内存柜子 → 取出登录时存的 SecurityContext 放回线程上下文 |
| 每次请求成本 | **每个请求查一次数据库**（loadUserByUsername） | 内存 Map 查一次，零 DB |
| 业务层取当前人 | 旧 `SecurityUtil.getCurrentUser()` L12-35：从上下文取 principal 后**再查一次库**拿完整 User | 新 `CurrentUser.requireId()`：principal 的 name 就是 id，`parseLong` 完事，零 DB |

### 登出
| | 旧（JWT） | 新（Session） |
|---|---|---|
| 做法 | **做不到真登出**——token 发出去就收不回，只能前端删存储/等过期（或额外做黑名单） | `logout` L109 `session.invalidate()`：柜子销毁，钥匙立刻全部失效，**服务端说了算** |

## 2. 你的三个具体困惑，逐个拆

### 困惑① "旧项目我也写了 loadUserByUsername，为什么还说我没用框架流水线？"
查证结果（旧 `UserServiceImpl` L41 + L292-314）：旧项目**确实实现了** `UserDetailsService`，
但它的调用方是 **JWT 过滤器**（每次请求重建身份用，L63），**登录接口根本没用它**——
登录走的是 L100-151 那套手写流程（自己查、自己 matches、自己发 token）。
所以准确说法是：**旧项目有零件，但没把零件装进 AuthenticationManager 流水线；登录是绕开流水线手搓的。**
新项目把登录也交给流水线：`authenticate()` 一行，Provider 自动回调你的 loadUserByUsername + matches。

### 困惑② "email 登录旧项目写了好多，新项目怎么就改一个查法？"
旧项目 email 登录 = 在**手写流程**里加双查询分支（L103-104 先 username 后 email、取非空者），
每处用到查用户的地方都要考虑两条路。
新项目：登录凭据只有 email 一种，`loadUserByUsername` 方法体里 `eq(UserAccount::getEmail, username)` 一处改完，
流水线上下游（比对、异常、401 翻译）全部不动。**这就是"换登录字段 ≠ 重写认证"的实证。**
（注意：方法名/参数名是 Spring 接口定死的，参数名义叫 username、实际装的是 email——框架不在乎名字。）

### 困惑③ "记住身份的代码在哪？我只看到 saveContext 一行"
因为**你只需要写"存"的一半**（`WebAuthController` L100），"取"的一半是框架过滤器：
- 旧项目：取的一半也是你写的（整个 `JwtAuthenticationFilter` 111 行）——所以你在旧项目里"看得见全链路"。
- 新项目：取的一半 = `SecurityContextHolderFilter`（Spring 内置），源码不在你的仓库里，**所以你找不到**。
  它做四步：JSESSIONID 找柜子 → 取 SecurityContext → 放回线程上下文 → 请求结束清空。
- `CsrfController` 与此**无关**：它只负责发 XSRF-TOKEN（防伪造请求），不参与"记住你"。

## 3. "你写的一堆去哪了"——搬家映射表

| 旧项目你手写的 | 行数 | 新项目的归宿 |
|---|---:|---|
| `JwtAuthenticationFilter`（取 Header→解析→查库→塞上下文） | ~111 | `SecurityContextHolderFilter`（框架内置，0 行） |
| `JwtUtil`（生成/解析/签名/过期） | ~90 | 不需要——Session 无令牌可管（Tomcat 管 JSESSIONID） |
| 登录手写查用户+比密码（`UserServiceImpl.login`） | ~50 | `authenticationManager.authenticate()` 1 行（Provider 内部完成） |
| `SecurityUtil.getCurrentUser`（上下文→再查库） | ~24 | `CurrentUser.requireId()`（principal 即 id，0 DB） |
| 自定义 `RedisTemplate<String,Object>`+JSON 序列化配置 | ~34 | 框架自带 `StringRedisTemplate`（验证码/计数本就是字符串，零配置） |
| **仍然要自己写的**：登录失败限流、验证码发送与校验、白名单规则 | — | `LoginAttemptService` / `EmailVerificationService` / 配置里的 permitAll——**框架不懂你的业务策略** |

> 规律：**通用机制（认证流水线、身份复原、密码比对）交框架；业务策略（限多少次、验证码几分钟、谁免登录）永远自己写。**
> 旧项目的问题不是"写多了"，是把通用机制也手搓了一遍。

## 4. 两个项目"相同的部分"——你已经会的直接迁移

这些你在旧项目写过、新项目思路完全一致（只换了键名/细节）：
1. **bcrypt 存哈希**：旧注册 L95 `passwordEncoder.encode` ↔ 新 `IdentityService` L84。永不存明文，bcrypt 自带盐。
2. **Redis 存验证码 + TTL**：旧 `REGISTER_<email>` 10 分钟（L193）↔ 新 `auth:register:code:<email>` 10 分钟。
   差异：旧防刷="上一条没过期就拒发"（等效 10 分钟一封）；新防刷=60 秒冷却（TTL 余量判断，L11.5 你亲手调的）。
3. **登录失败限流 5 次/15 分钟**：旧键 `login:fail:<userId>`（查到用户才计数）↔ 新键 `auth:login:fail:<email>`。
   新方案更早拦截（认证前），且 L11.5 加固后非法格式 400 直接进不来（@Valid），Redis 不会积垃圾键。
4. **邮件异步/降级**：旧 `EmailService` `@Async` 发信 ↔ 新 `sendOrLog` 优雅降级（没配 SMTP 打日志不阻断）。

## 5. 为什么旧项目关 CSRF、新项目必须开？（一条逻辑两种正确）

- 旧：token 放 **Header**，浏览器**不会自动携带** → 钓鱼站发不出带你凭证的请求 → CSRF 天然免疫 → `csrf().disable()`（旧 SecurityConfig L66）合理。
- 新：凭证是 **Cookie**，浏览器对同域请求**自动携带** → 钓鱼站能"借你的钥匙"发请求 → 必须开 CSRF（double-submit：XSRF-TOKEN Cookie 故意可读 + Header 回传比对，`ApiSecurityConfiguration` L31-45）。
- 同理：旧 `STATELESS`（旧 L62）↔ 新 `IF_REQUIRED`（新 L47-48）——会话策略跟着凭证形态走。

## 6. 面试答法（把两个项目串成你的故事）

**Q：Session 和 JWT 怎么选？**
「我两种都完整做过。旧论坛用 JWT：无状态好横向扩展，但每次请求要查库重建身份、且 token 发出去收不回，登出只能靠过期。新项目是同源 SPA，选了 Session：状态在服务端、`invalidate()` 即时撤销、CSRF 用 double-submit 补上。核心权衡是**撤销能力 vs 扩展成本**——要多实例时再上 Spring Session+Redis 共享会话。」

**Q：登录字段从用户名改邮箱要动多少？**
「如果用 Spring Security 流水线，只改 UserDetailsService 的查法一处；我旧项目手搓登录时为 email 写过双查询分支，每个环节都要照顾，两相对比才理解框架流水线的复用价值。」

**Q：Spring Security 登录内部发生了什么？**
「Controller 把邮箱密码包成 UsernamePasswordAuthenticationToken 交给 AuthenticationManager；默认实现 ProviderManager 分发给 DaoAuthenticationProvider；它回调我的 UserDetailsService 查库、用 PasswordEncoder 比对 bcrypt 哈希，成功返回已认证 Authentication，我再 saveContext 存进 HttpSession 并发 JSESSIONID；之后每次请求由 SecurityContextHolderFilter 用 JSESSIONID 恢复身份，请求结束清空线程上下文防串号。」
